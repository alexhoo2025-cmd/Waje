# 充值 `status=4` 语义审计｜2026年8月28日

## 结论

根据已确认的订单枚举，充值 `status=4` 的正式含义为 **`OrderRechargeStatusFailed`（失败）**。它是未实际收款的失败订单，不是已成功但尚未入账的充值。

## 证据

| 观察 | 结果 | 解释 |
|---|---|---|
| `status=4` 的 `pay_amount` | 近三日 opay、app_pp、pp_bk 均为 0 | 与“失败”正式枚举一致，未记录实际支付金额 |
| `status=4` 的 `fee` | 均为 0 | 无实际扣费或支付确认痕迹 |
| `status=4` 的引用和流水 | 每笔均有唯一 `reference`、`serial_num` | 是独立支付尝试，不是汇总空行 |
| 同一 `reference` 后续转 `status=3` | 8月26—28日均为 0 | 不像同一订单的“后续成功中间态” |
| `status=3` 的支付字段 | `pay_amount = amount`，且非0 | 符合成功收款的候选行为特征 |
| `status=1` 的支付字段 | `pay_amount = 0` | 正式枚举为 `OrderRechargeStatusWaitPay`（待支付） |

## 支付方式分布

`status=4` 主要来自：

- opay：8月26日约 268.90M；8月27日约 244.88M；
- app_pp：8月26日约 112.33M；8月27日约 110.55M；
- pp_bk：8月26日约 42.99M；8月27日约 47.06M。

这些金额是**失败订单金额**，不能加入成功充值分母，也不能因为金额大就解释为“充值漏记”。

## 对 TC 分析的影响

1. 当前 `status=3` 作为成功充值候选在行为特征上是合理的。
2. 不能把 `status=4` 加入充值分母来“修正”TC；那会把失败支付当作真实现金充值。
3. `status=4` 不产生到账资产，不能导致任何成功提现；它不是 TC 偏高的原因。
4. 仍需确认是否存在“失败后使用新引用号重试成功”的链路；这会影响支付转化率分析，但不会改变原 `status=4` 是失败订单的结论。
5. TC 高低的业务解释应回到成功提现的资产来源：期初余额、历史成功充值、游戏结算赢利、资产转换与已批准调整。

## 已确认状态机与仍需补齐内容

```text
充值状态：
0 Init；1 WaitPay；2 Paied（已支付，非最终成功）；3 Success；4 Failed；5 Fraud。

提现状态：
101 WaitPay；103 Success；104 Failed；105 Review（待审核）。
```

仍需确认：状态变更是否在同一条订单记录上覆盖更新、失败重试是否生成新 `reference`、以及 `time` 是创建时间、状态更新时间还是最终完成时间。
