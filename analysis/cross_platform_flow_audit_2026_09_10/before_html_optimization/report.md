# APP与H5用户流通：现有埋点与上报能力评估

## 执行摘要

**总体判断：部分支持，尚不足以验收完整跨端流通分析。** 账号、登录、页面与游戏事件已具备基础，但还需验证跨端身份一致性和事件发生端。现有证据不能确认“引导点击→另一端到达→登录→游戏／付费”的完整关联已上报。

**先做同账号两端活跃与行为顺序，再做明确跳转归因。** 前者可依靠统一账号与时间序列；后者还需要一次跳转的关联标识和目标端到达回执。两端都出现过的用户，不一定由下载或唤起引导转化而来。

**优先复用现有设计，补齐身份映射、运行环境和跳转关联。** 最新Whot一期与二期已要求用户、端、包、版本及牌局关联；H5补充方案已提出会话和入口来源。它们提供设计基础，尚无本次线上验收证明。

本次读取Whot一期飞书revision 37、二期revision 27全文，结合8月埋点盘点与9月4日查询回执评估。9月10日BigQuery只读接口返回Auth required，浏览器控制台停在Google登录验证，起源质量页跳转登录页；本次未执行线上业务数据查询，未产出当前跨端人数或转化率。

## 一、先明确“用户流通”要统计什么

| 分析层次 | 业务含义 | 当前判断 |
| --- | --- | --- |
| 两端重叠活跃 | 同一账号在同一窗口内分别在APP和外部H5有有效活动 | 条件支持：先核验统一账号与行为端 |
| 行为顺序切换 | 同一账号先在H5活动，后在APP活动，或反向 | 条件支持：需可靠时间、去重及前台会话；属于顺序观察 |
| 明确跳转／导流 | 点击某端引导后，到达指定另一端 | 当前证据不足：缺已核验的跳转关联与到达回执 |
| 安装与激活 | H5下载引导后安装APP并首次打开 | 当前证据不足：下载页配置、点击或唤起请求不能证明安装或首次打开 |
| 跨端后游戏、付费与留存 | 流入后开局、下注、充值、回访，以及原端是否仍活跃 | 条件支持：先确定流入人群，再关联事件及服务端结果 |
| 同一Whot牌局跨端续玩 | 同一参与者在同一牌局由一个端接续到另一个端 | 现有设计不足以单独证明：同桌有两端玩家与同一玩家切端是两回事 |

表中的“条件支持”表示已有可复用基础，并非已通过线上验收。建议先交付登录账号口径；匿名用户的跨端关联覆盖单列。

## 三、四个会直接改变结论的缺口

**1. 同名字段不等于同一账号。** 需要确认APP、H5、起源、Firebase、游戏服务端使用同一业务账号键，或能通过受控映射关联。若包体或产品有独立账号空间，键应包含账号空间。user_key、user_id、xl_id及浏览器／安装标识不能直接混用；BINDACCOUNT事件存在也不等于已有完整身份映射表。

**2. 必须按事件发生时的运行环境归属端。** 建议APP包括原生与APP内嵌WebView，外部H5包括浏览器与PWA，并另列四种运行形态。Android浏览器仍属于外部H5；APP里加载HTML游戏仍属于APP内嵌环境。该合并方式是本评估建议，最终报表保留四类明细便于按业务调整。

**3. 账号活跃顺序只能说明先后，不能证明导流。** 用户可能在两台设备同时在线，后台心跳可能交错，或自然返回另一端。分析应使用可识别的前台有效会话，合并同端连续活动，同时标出并发与无法排序的情况。服务器上报的事件来源不等于用户使用端，应关联该次会话／请求，而非套用账号最新登录端。

**4. 入口来源需要与目标端到达、最终业务结果连接。** source=deeplink、entry_source或来源域名只能解释入口类别。要归因到一次引导，需在源端点击和目标端到达之间传递受控关联标识，再与登录、游戏和交易请求连接。跨设备或匿名阶段无法确定关联时保留未关联，不通过IP或设备指纹猜人。

## 四、建议优先落地的指标

先定义窗口W内经过身份与端校验的真人登录账号：A为APP有效活跃账号集合，H为外部H5有效活跃账号集合。有效活跃建议使用前台打开／页面就绪／登录成功／主动游戏行为，具体事件白名单经覆盖核验后确定。后台APPONLINE与模块曝光不单独作为主动流转证据。

| 指标 | 算法与分母 | 当前落地条件 |
| --- | --- | --- |
| 两端重叠人数与占比 | 人数=去重A∩H；占比=人数÷去重A∪H | 统一账号、事件发生端、同一统计窗口 |
| H5用户中的APP覆盖率 | 去重A∩H÷去重H；反向覆盖率以A作分母 | 描述交集，不能命名为下载转化率 |
| H5→APP顺序流转人数 | 源H5有效会话后，在指定观察窗内出现APP有效会话的去重账号数 | 账号、会话、可靠时间；并发／次序不明单列 |
| 跳转到达成功率 | 有目标端有效到达的去重transfer_id÷观察时间已结束的有效跳转尝试数 | 源点击、目标到达及同一关联标识；人数率另外去重账号 |
| 流入后游戏／付费率 | 观察窗内在目标端开局／成功付费的流入账号数÷已满足相应观察时长的流入账号数 | 到达时冻结流入人群；请求端与服务端结果关联、机器人分离 |
| 目标端回访与原端回流 | 从首次符合本次定义的流入日开始，统计目标端回访及返回原端的账号交集 | 分别定义次日与后续观察天数；未达到观察期为N/A |

建议首次核验近7个完整Lagos业务日（2026年9月3日—9日），这里只是待执行窗口；源端活动接近窗口末尾的样本需补足后续观察时间。历史覆盖不足时命名为“窗口内首次观测到APP”，不能写成“首次安装／首次使用APP”。

同一用户APP→H5→APP可以发生两次方向切换，窗口内跨端用户仍只有一人。顺序流转可分析1小时、24小时等窗口敏感性；下载后首次打开应另设观察窗。上述时间是候选分析参数，未作为已确认业务标准。

## 五、最小补充方案：先补关联，再补新事件

| 优先事项 | 复用现有设计 | 需要明确或补齐的内容 |
| --- | --- | --- |
| P0 统一身份 | LOGIN、REGISTER、BINDACCOUNT及user_key／user_id | account_namespace、canonical_account_key、identity_state；匿名绑定生效时间、退出账号与换账号边界；映射仅在受控层处理 |
| P0 明确使用端 | client_type、surface_type、包和版本 | product_surface与runtime_surface分列；app_native／app_webview／h5_browser／pwa_standalone；事件时点上下文 |
| P0 关联同次跳转 | 现有MC、页面到达、会话启动、登录 | transfer_id、from_surface、to_surface、source_session_id、target_session_id、entry_point_id、event_uid、event_time；到达后登录绑定同一旅程 |
| P1 记录跳转阶段 | 能复用现有事件则扩字段 | 逻辑阶段prompt_view、intent、target_arrived、login_success、failed；意图、实际到达和失败分别记录；无回执为未观测到达，不自动认定客户端失败 |
| P1 补业务连接 | GAMESTART、GAMEEND和交易结果 | entry_context_id、request_id、game_round_id关联当次使用端；支付回调继承支付请求端；同币种有效终态去重 |
| P1 安装与唤起拆开 | 下载页、应用首次打开与深链回执 | 已装APP唤起与新安装激活分别统计；安装来源需可验证归因机制，不能从下载点击推出安装完成 |

transfer_id应是短期、受控、无账户或凭据内容的旅程关联值；不能携带登录令牌。同一跳转传输重试复用标识，新一次用户跳转产生新标识。匿名流转可统计尝试数，只有确定绑定到业务账号后才能统计确定性跨端账号人数。

Whot若还要分析“同一局从APP转到H5接着玩”，应在已有重连和牌局事件上补旧／新会话、旧／新使用端、同一参与者、牌局版本及接续结果；多人共享同一牌局ID本身不能证明这个行为。是否允许跨端接续及双端同时操作，需要玩法服务端确认。

## 六、上报验收与汇总结论

**现阶段适合先建设登录账号跨端分析的验证版。** 先核验账号映射与端归属，再输出APP独占、H5独占、两端重叠及流转方向。待跳转关联和到达回执核验后，再提供引导转化与后续价值分析。

上报验收至少包括：同一测试账号在APP/H5使用后的身份一致；匿名登录、换账号与退出不会串人；APP内嵌H5不会计作外部H5流入；两端同时在线、后台心跳及重试不制造切换；源端尝试与目标到达可关联；游戏和支付结果继承当次请求端。仅输出分日、端、包与事件的聚合覆盖和缺失分布，不导出用户明细。

每项检验保留有效分母、未关联、身份未知、端未知、超时及迟到状态。数仓聚合以账号、事件、旅程或业务结果各自的唯一键去重；人数和次数分开，跨端金额同币种分别核对。少于10名用户的报表分组合并或隐藏。

本次结论为“设计与历史证据评估完成，当前线上上报验证受认证阻断”。未修改现有Whot一期／二期方案或飞书文档，未部署新增事件。跨端前后付费或留存差异属于观察关联；若要证明导流带来增量，应另设计有共同分组和完整观察期的实验。
