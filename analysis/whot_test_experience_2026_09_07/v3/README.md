# WHOT 双版本测试 V3

目标：6001旧版、9006新版各100个正式合格局，策略配额34/33/33。历史局、校准局、托管局与机制专项分别统计。

## 当前实现与实际限制

- SQLite事件追加、双版本固定种子排期、历史只读导入、原子结算和失败补槽已实现。
- 规则函数检查版本、帧新鲜度、操作主体、截止时间、合法牌组与实际计分；未认证规则拒绝动作。
- Swift常驻进程提供可见Chrome窗口探测、屏幕区域OCR/模板特征和前台限定点击；已在真实6001房间验证一次关闭操作、一次最低档入局。
- 2026-09-08 新增校准执行改进：可在大厅帧自动点击已验证的DAU-1、对相同Chrome窗口的轻微视口变化重锚定、用牌面小图标投票隔离重叠牌，并对每次点击等待两帧稳定变化后才允许下一次动作；WHOT 20的五牌型选择点已从可见画面记录为校准证据。
- 自动出牌提示现在只在没有完整可行动作时判定为托管；若 `ZAMU YAKO`、手牌和桌牌均清晰，则先执行一次合法动作，避免开局提示遮蔽人工回合。
- `calibration_audit.md/json` 汇总了 14 次 6001 校准观察（8 次已导入数据库），所有记录仍为 provisional，正式合格局为0。
- `vision_profile_6001_calibration.json` 保存当前 6001 画布区域与 WHOT 五牌型候选点，仅作校准资料，未提升 `profiles.json` 的正式认证状态。
- 浏览器 MCP 指向的 Chrome 与通用 AppleScript 默认 Chrome 可能是不同进程。必须用绑定PID的可访问性界面回读当前页面，再匹配窗口，不能读取通用默认实例。
- 视觉配置尚未完成校准，200张/版标注回放、3+10局校准和200个正式对局尚未完成。原生点击耗时不等于回合响应耗时。
- 第一次6001校准为混合托管负局：下注1，开局余额950、扣后949、结算后949，剩余44点。该局不计正式样本。
- 9006路由仍待从实际卡片进入后回读。不得猜测路径或复用6001规则。

## 命令

在本目录运行：

```sh
swiftc -O native.swift -o /tmp/whot-native-v3
python3 lab.py init
python3 lab.py import-v2 ../v2/whot_samples_v2.sqlite3
python3 lab.py status
python3 -m unittest discover -s . -p 'test_*.py' -v
python3 controller.py probe --game 6001
```

`probe`只读。`controller.py run --game 6001 --match <已建立的校准局UUID> --seconds 30`仅在规则和视觉配置通过后执行当前局面；当前配置会拒绝运行。不得用改写status字符串绕过实际回放/校准。这个命令目前尚不含房间自动选择、结算字段自动解析和连续200局调度，不能称为完整无人值守执行器。

## 操作规范

启动前：只绑定普通Chrome、固定测试域和明确game-id。确认950等筹码余额是实际可用字段；赠送计作测试准备资金，不进入游戏返还。

比赛中：不做HTML重建、文档分析、外部检索。只读玩家可见画面，普通回合与特殊动作窗口分别确认。一个动作等待确认时禁止叠加提交。

出现托管、未识别牌、窗口变化或超时：记录当前局失效，保存可见结算；停止自动续局排查，不用托管局填满配额。

恢复：先读`status`的open_matches，再处理原局。未知结果保持未知，不重新开始并覆盖原局。

结算：保存下注、返还显示、前/扣后/结算后余额、牌数、点数和结束原因。点击“再玩”前先校验按钮是否改成更高档房间推荐；首次校准中结算按钮推荐200档，未点击。

## 对比分析与漏洞验证

同人数、同档位、同执行器版本下比较两版策略胜率和Wilson区间、点击时延、局长、托管/错误率与回报。四人局单列，不与两人局合计。

只有确认gross_return的语义并完成逐局余额守恒后计算SUM(gross_return)/SUM(stake)。偶然高回报不代表长期套利；报告所有试验而非挑选胜局。对每个疑似问题记录版本、前置状态、单次UI操作、预期/实际结果、独立复现次数及余额证据。未确认的重复结算、余额创造和策略优势分开列为待核查。

完整对手手牌不可见时，仅评价公开出牌合规与特殊状态结果；无法判断其是否选择了最优牌。当前没有证据证明任何一版存在可利用套利。
