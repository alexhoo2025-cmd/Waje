## 起源分析平台当前基线

2026-08-03 已完成 Waje Game 起源分析平台的页面级盘点，详见 [[起源分析平台盘点-2026-08-03]]。当前账号可读数据统计、用户分析、报表集市和数据管理；首页提示无权限，业务看板暂无可用内容。

核心入口覆盖：新增/活跃、基础留存、LTV、ROI、付费、虚拟资产、页面、模块、启动、设备终端，以及运营周报、TC 详情、游戏概况、场次分析、收益留存等报表。

报表集市中的 `BQ-` 版本使用 BigQuery 新引擎；同名非 BQ 版本属于旧引擎，后续会逐步废弃。新分析优先使用 BQ 版本，并在迁移期间记录数据源、刷新时间和口径差异。

| [Lifecycle Pool V2](https://prod-ac.waje-special.com:8443/sys/dynamic/lifecyclev2/pool) | 生命周期池和 RTP 查询 | 按日期、生命周期、游戏类型/游戏查看基础真实回报比等结果 | 截图显示支持实时数据监控和查询历史记录 |

### Lifecycle Pool V2 三个表的使用区别

根据当前 GM 页面截图与沟通口径，生命周期模块包含：

1. `Lifecycle Pool`：旧版生命周期池，表示历史口径/旧表，常规新分析可不优先使用。
2. `Lifecycle Pool v2`：自研游戏使用的新版生命周期池，优先用于自研游戏 RTP 和生命周期查询。
3. `Lifecycle Pool v2 (Joint)`：自研游戏 + 联运游戏的联合口径，适合同时查看自研和联运范围；使用前要确认游戏范围和汇总规则。

### RTP 查询口径

截图中的表格展示“平均值项：基础真实回报比”，按日期展开，并按游戏类型/生命周期层级和具体游戏展示，另有“总计”列。当前可观察到的查询维度包括：

- 日期。
- 游戏类型/生命周期层级。
- 具体游戏。
- 总计汇总。
- 实时数据与历史查询。

使用时必须同时记录：表名、查询日期、是否完整日、游戏范围、自研/联运范围、RTP 字段名称、汇总方式和查询时间。截图中的 `BaccaWhot` 与 2025-05-06 至 2025-05-20 数值仅作为界面示例，不作为当前 RTP 结论。

### 与新包生命周期分析的衔接

新包分析中的“终身、TC 比、TX 率”和 GM 生命周期池中的“基础真实回报比”不是同一指标。建议：

- 新包 cohort 分析使用新包表中的新增人数、留存、付费、终身、TC 比和 TX 率。
- 游戏 RTP 正常性使用 GM Lifecycle Pool V2 的基础真实回报比，并按游戏、日期、生命周期和自研/联运拆分。
- 需要把 GM RTP 结果与新包的版本、分包渠道、归因媒体和生命周期 cohort 对齐后再做异常解释。
- 不完整天、未成熟 cohort 和 0 值在看板中应显式标记，不能直接与成熟日或成熟生命周期比较。

### 后续整合规划

GM 平台当前作为 RTP 数据的独立查询源，后期计划整合到起源数据平台。目标是让起源平台统一承载埋点、生命周期、游戏 RTP、版本和渠道分析，减少业务在多个后台之间切换。

> 涉及TC异常、提现增长、Bonus或资产异常时，统一按 [[Waje-TC异常、RTP与资产流水诊断框架-2026-08-28]] 执行：RTP用于解释游戏结算回报，TC用于观察现金流出，两者相关但不线性；必须最终落到资产流水守恒与受限用户级关联核查。

由于 GM 基于 AdminLTE，后续整合可以复用现有后台的页面组件和交互经验，但不能把 AdminLTE 本身视为数据查询或 BI 能力。真正需要迁移/复用的是 GM 的后端接口、BigQuery 数据模型、指标口径、权限和导出逻辑。

建议采用渐进式整合：

1. **数据层整合**：将 GM 生命周期池的游戏、日期、生命周期、基础真实回报比、游戏类型、自研/联运标识等结果同步到 BigQuery 统一分析层。
2. **口径层整合**：在起源平台指标字典中明确基础真实回报比、理论 RTP、实际 RTP、终身、TC 比和 TX 率的定义及分母。
3. **展示层整合**：在起源平台报表集市/业务看板增加游戏 RTP 查询，支持日期、游戏、生命周期、版本、分包渠道、归因媒体和自研/联运筛选。
4. **迁移期并行**：GM 原页面与起源平台看板并行核对至少 7–14 天，确认总计、分游戏、分生命周期和完整日结果一致后再作为统一入口。

整合验收至少包括：GM 与起源同日同游戏 RTP 差异、数据更新时间、完整日标记、游戏映射、生命周期映射、权限范围和历史数据回补情况。

## GM 报表系统重整需求

### 当前问题

GM RTP/生命周期报表缺少日期范围、游戏项目、生命周期天数等核心筛选项，使用者只能查看固定或不完整范围，导致：

- 无法快速定位某个游戏或玩法的 RTP。
- 无法按生命周期天数比较玩家回报差异。
- 无法进行日期区间趋势分析和版本/活动前后对比。
- 基础口径、完全口径、实际值和预期值之间难以按同一筛选条件核对。

### P0：必须增加的筛选项

| 筛选项 | 类型 | 默认值 | 说明 |
|---|---|---|---|
| 日期范围 | 起止日期 | 最近 7 个完整日 | 支持单日、连续区间、快捷选项；排除不完整日 |
| 游戏项目 | 多选下拉 | 全部 | 支持游戏名称、游戏 ID、游戏类型搜索 |
| 生命周期天数 | 单选/多选 | 全部 | 支持 1、2、3、4…N 天和生命周期汇总 |
| 游戏类型 | 多选 | 全部 | 自研、联运、外接游戏或平台已有类型 |
| 数据口径 | 单选 | 基础/完全明确默认 | 基础、完全、实际、预期口径不可混淆 |

### P1：建议增加的筛选项

- 自研/联运标识。
- 版本、包名、分包渠道、归因媒体。
- 区服/国家/地区。
- 下注档位或玩法。
- 数据状态：完整日、实时、历史、补数据。
- 异常状态：RTP 超阈值、下注额差异超阈值、数据延迟。

### 看板交互要求

1. 筛选条件应在页面顶部固定展示，并显示当前已选条件。
2. 游戏项目支持搜索、多选、全选和清空。
3. 日期支持快捷选项：昨日、近 7 日、近 30 日、自定义。
4. 修改筛选项后，所有指标卡、趋势图和明细表同步刷新。
5. 支持“基础 vs 完全”“实际 vs 预期”并列对比。
6. 支持导出当前筛选结果，并在导出文件中写入筛选条件、查询时间和数据更新时间。
7. 空结果时展示明确原因：无数据、未成熟、权限不足、日期未完成或筛选条件冲突。

### 核心指标展示

建议同时展示：

- 总基础下注额、总完全下注额及差额/差异率。
- 总基础真实回报比、总完全真实回报比。
- 总基础预期回报比、总完全预期回报比。
- 总人数、有效局数/下注次数。
- 今日完全实际盈利调整幅度。
- 当前完全实际盈利扣除幅度。
- 数据更新时间、是否完整日和当前口径版本。

### 研发实现拆分

**研发/数据开发负责：**

- 补充后端查询接口的日期、游戏、生命周期等参数。
- 统一基础/完全/实际/预期字段定义和计算逻辑。
- 增加游戏、生命周期和版本字典映射。
- 对日期字段做分区查询，控制大范围查询性能。
- 增加权限校验、导出审计和查询日志。

**业务/分析人员负责：**

- 提供常用筛选组合和默认视图。
- 确认游戏分类、生命周期展示方式和异常阈值。
- 验收指标数值、筛选联动、导出结果和空数据提示。

### 验收标准

- 日期范围、游戏项目、生命周期天数均可独立和组合筛选。
- 筛选后总人数、下注额和四类回报比与原始查询结果一致。
- 基础下注额与完全下注额的差额可展示，并支持按游戏/生命周期下钻。
- 支持基础/完全、实际/预期并列比较，不发生字段错位。
- 默认不纳入不完整天；实时查询明确标注“实时”。
- 大范围查询有加载状态、超时提示和最大日期范围限制。
- 导出结果包含筛选条件、口径、数据更新时间和查询时间。
- GM 原报表与重整报表至少并行核对 7–14 天。

### 整合优先级调整

由于 GM 平台当前数据处理效率低、筛选能力不足，RTP 查询和生命周期分析成本较高，建议将“GM RTP 数据整合到起源平台”提升为高优先级数据平台项目，而不是作为长期规划事项等待。

建议采用“先数据、后页面”的加速路径：

1. **P0：锁定数据范围**：优先接入 Lifecycle Pool V2 和 V2 (Joint) 的 RTP、下注额、回报额、人数、游戏、生命周期、日期和自研/联运字段。
2. **P0：建立 BQ 统一事实层**：将 GM 查询结果同步到 BigQuery，按日期、游戏、生命周期分区，生成基础/完全口径和实际/预期回报比汇总表。
3. **P0：起源平台先提供查询能力**：优先上线日期范围、游戏项目、生命周期天数和自研/联运筛选，不等待完整大看板一次性交付。
4. **P1：迁移核心看板**：上线游戏 RTP、生命周期 RTP、基础/完全下注额差异和盈利调整监控。
5. **P1：并行校验与切换**：GM 与起源平台按同日、同游戏、同生命周期并行核对 7–14 天，确认后将起源平台作为业务统一入口。
6. **P2：收敛旧入口**：保留 GM 作为排障和回溯入口，日常分析逐步迁移到起源平台，后续评估是否下线重复查询页面。

### 加速项目的最小交付范围

第一期不要求一次性迁移 GM 全部功能，只交付：

- 游戏 RTP 日查询。
- 生命周期天数筛选。
- 日期范围筛选。
- 游戏/游戏类型筛选。
- 自研/联运筛选。
- 基础下注额与完全下注额差异。
- 基础/完全真实回报比和预期回报比。
- 总人数、数据更新时间、完整日标识。
- 当前筛选结果导出。

这样可以优先解决 GM “查得慢、筛不了、比不了、导不出”的核心问题，再逐步扩展版本、渠道、玩法和异常告警。

## 生命周期详细奖池看板需求初稿

### 需求背景

当前 GM 的“生命周期详细奖池”按天导出：每天约 252 行，每行约 18 个数据指标，单日约 4,536 个数据点；且一次只能导出一天的数据。现有生命周期相关数据分散在 4 张表中，如需分析连续 7 天，需要人工完成约 28 次单日导出，再进行拼接、筛选和对比，处理效率较低，也容易出现日期、游戏和指标遗漏。

群名称已调整为“数据报表”，本需求用于提交研发评估和后续看板设计。

### 目标

- 支持一次查询和导出连续日期范围，至少覆盖 7 天。
- 支持按游戏、生命周期、数据指标和日期筛选。
- 仅展示核心观测指标，减少 252 行 × 18 指标的人工处理成本。
- 支持趋势、异常和游戏间对比，减少离线表格拼接。
- 保留明细下钻能力，必要时仍可追溯到原始四张表。

### P0 功能需求

| 功能 | 要求 |
|---|---|
| 日期范围 | 支持起止日期、单日、近 7 日、近 30 日；一次查询多日数据 |
| 游戏筛选 | 支持游戏名称/ID多选、游戏类型、自研/联运筛选 |
| 生命周期筛选 | 支持生命周期 1、2、3、4…N 天及生命周期汇总 |
| 指标筛选 | 支持选择需要展示的指标，默认只展示核心指标 |
| 四表统一 | 将四张生命周期表统一为一个查询入口，标记来源表和数据粒度 |
| 汇总方式 | 支持按日期、游戏、生命周期汇总；明确求和、平均、加权平均的区别 |
| 导出 | 支持导出当前筛选后的多日结果，文件写入筛选条件、查询时间和数据更新时间 |
| 数据状态 | 标记完整日、实时数据、补数、缺失和未结算数据 |

### 默认核心指标

第一期建议默认展示：

- 基础下注额。
- 完全下注额。
- 基础下注额与完全下注额差额及差异率。
- 基础真实回报比。
- 完全真实回报比。
- 基础预期回报比。
- 完全预期回报比。
- 总人数。
- 今日完全实际盈利调整幅度。
- 当前完全实际盈利扣除幅度。
- 有效局数/下注次数（如源表具备）。

其余指标放入“更多指标”或明细下钻，避免首页一次性展示全部 18 个字段。

### 建议看板布局

1. **顶部筛选区**：日期范围、游戏、游戏类型、自研/联运、生命周期、数据口径。
2. **核心指标卡**：下注额、人数、基础/完全真实回报比、基础/完全预期回报比、差额。
3. **趋势区**：按日期展示下注额、完全真实回报比和基础/完全差异率。
4. **游戏对比区**：按游戏展示人数、下注额、真实回报比和异常状态。
5. **生命周期区**：按生命周期天数展示回报比、下注额和人数。
6. **异常区**：RTP 超阈值、基础/完全差异过大、数据缺失、负盈利或未结算日期。
7. **明细区**：支持下钻到四张来源表的原始记录。

### 研发实现建议

- 将四张来源表通过统一字段模型汇总到 BigQuery 看板层，避免 Ares 页面每次直接扫四张明细表。
- 为日期和游戏建立分区/聚簇，支持至少 30 天范围查询。
- 保留 `source_table`、`stat_date`、`game_id`、`game_name`、`lifecycle_day`、`metric_version` 和 `updated_at`。
- 基础/完全、实际/预期指标必须在数据层统一计算，前端不重复计算。
- 支持 Ares 起源平台查询；Metabase 可作为研发/分析人员的验证入口。
- 对 7 天查询设置默认范围，对超大范围查询增加限制、加载提示和导出任务状态。

### 验收标准

- 一次查询可返回连续 7 天数据，不再要求按天重复导出。
- 四张来源表的数据可按日期、游戏和生命周期正确合并，行数和总额可对账。
- 默认首页只展示核心指标，其他指标可按需展开。
- 基础/完全下注额、四类回报比和差异率与 GM 原报表逐日核对一致。
- 支持按游戏和生命周期下钻，能定位异常数据来源表。
- 导出文件包含日期范围、游戏、生命周期、指标选择、数据更新时间和口径版本。
- 查询结果明确区分完整日、未结算日、补数和缺失数据。
- GM 原始单日导出与新看板至少并行核对 7–14 天。

### 需求优先级

- **P0**：多日查询、四表统一、日期/游戏/生命周期筛选、核心指标展示、导出。
- **P1**：趋势图、游戏对比、异常识别、明细下钻、指标自定义。
- **P2**：订阅推送、自动告警、版本/渠道联动、历史回补和权限细分。

当前优先质量问题：

- 数据质量总错误率 3.30164%；GAMEEND 事件有 130,874 条异常属性。
- ROI 明细中汇总 CAC 为 0，导致汇总 ROI 显示 NaN。
- 当前日数据未完整结算，运营周报和 TC 详情出现负利润/极端 TC 比。
- 用户分群和部分元数据停留在 2023–2024 年，需重算和确认规则有效性。

## 建议建立的指标卡

- 用户：DAU、注册转化、首局率、D1/D7 留存、生命周期分层
- 玩法：参与人数、局数、投注额、派奖额、RTP/毛利、异常率
- 商业化：首充率、充值金额、提现成功率、净收入、复购率
- 体验：加载失败、断线、扣款失败、奖励未到账、客服投诉

指标卡正式使用前，必须补充“定义、时间范围、过滤条件、数据源、负责人、更新时间”。
