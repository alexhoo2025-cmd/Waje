# GAMEEND 埋点异常修复清单（研发提交版）

> 目标：将起源平台已观察到的 GAMEEND 异常属性拆成可执行的字段、类型/枚举、版本和来源排查路径，并给出事件级监控、验收 SQL/伪代码、优先级和回归门槛。
>
> 证据边界：本清单基于 [[起源分析平台盘点-2026-08-03]] 与 [[埋点与数据上报地图]]。当前已掌握页面级质量快照，但尚未读取底层数仓表、SDK/服务端上报代码、ETL SQL 和完整字段字典；文中带“候选”的字段名需要研发/数据负责人按实际 schema 替换确认。

## 1. 技术摘要

2026-07-27 至 2026-08-02 的数据质量快照显示：GAMEEND 接收 418,338 条、入库 287,464 条、异常属性 130,874 条，异常属性占接收量 **31.28%**；接收量减入库量也为 130,874 条。同期全事件错误率为 3.30164%，抛弃条数显示为 0。该问题应作为 **P0 埋点质量阻断项**，在修复前不要把 GAMEEND 直接用于局数、完局率、玩法留存、资金循环或利润归因。

当前最短排查路径：

1. 先保留原始 payload、接收 ID、事件 ID、错误字段和错误类型，按字段统计异常，不要先用默认值填平或静默丢弃。
2. 按“必填缺失 → 类型/枚举不合法 → 版本组合 → 上报来源”四个维度切分，定位异常集中在哪一条链路。
3. 对修复版本做回放和端到端验收，再以 24 小时灰度 + 7 天回归确认生产质量。

## 3. GAMEEND 字段契约（候选版，先确认再固化）

字段名以实际埋点参数字典为准。下表先按字段语义划分为“建议必填”“条件必填”“观测字段”，避免在未完成字段盘点前一次性把不适用字段设成硬必填。

### 3.1 可能的必填字段

| 级别 | 字段语义 | 候选字段名 | 校验规则 | 异常时处理 |
|---|---|---|---|---|
| 建议必填 | 事件标识 | `event_code` / `event_name` | 非空且值为 `GAMEEND` | 拒绝进入标准化表，保留原始记录 |
| 建议必填 | 事件追踪键 | `event_id` / `request_id` / `ingest_id` | 非空、格式合法、重试可复用同一业务事件键 | 缺失时进入隔离表，不能用随机补值掩盖 |
| 建议必填 | 事件时间 | `event_time`；服务端补 `received_at` | 可解析；记录客户端时间与服务端接收时间；超出时钟偏差阈值需标记 | 不因客户端时间异常丢失原始事件 |
| 建议必填 | 用户/设备身份 | `user_id`、`xl_id`、`uuid`、`account_type` | 按登录态定义“至少一个身份键”；登录用户优先 `user_id`，匿名用户至少保留 `uuid`；`xl_id` 用于起源口径关联 | 身份缺失进入隔离；禁止把所有匿名事件归到同一用户 |
| 建议必填 | 游戏上下文 | `game_type`、`game_id`、`session_id` / `round_id` | 非空；能唯一定位到玩法、房间/局或一局上下文 | 缺失时不能进入局级事实表 |
| 条件必填 | 玩法/模式 | `mode_id`、`play_id` | 对存在模式/玩法的 `game_type` 必填；无模式玩法需登记例外 | 未知或缺失按 `game_type` 分支隔离 |
| 建议必填 | 结束结果 | `result`、`end_reason` | GAMEEND 必须表达完成、退出、失败、断线/超时等结束状态；不能用空字符串代替 | 未知枚举进入隔离，并告警 |
| 条件必填 | 局内计数 | `bet_count`、`bet_times`、`goal_times` | 适用玩法中为非负整数；无该概念的玩法必须有字典例外 | 类型不符或负数进入隔离 |
| 条件必填 | 金额/资产 | `bet_amount`、`win_amount` / `reward_amount`、`currency` / `asset_type` | 只要上报金额，就必须同时有金额单位/币种/资产类型；金额精度和正负方向先按业务字典确认 | 不做无依据的币种或单位补换算 |
| 建议必填 | 客户端环境 | `client_type`、`app_id`、`package_name`、`product_version`、`hot_update_version` | 非空且能映射到版本/包字典；版本缺失不能定位回归范围 | 进入 `unknown_version` 分支并告警 |
| 建议必填 | 上报来源/契约版本 | `source` / `report_source`、`sdk_version` / `schema_version` | 来源至少可区分客户端、服务端、转发/桥接、重试；契约版本可追溯 | 缺失时保留原始数据并标记来源未知 |

建议把字段分成三类实现：

- **硬必填**：事件标识、事件追踪键、事件时间、身份键、游戏上下文、结束结果、版本和来源。
- **条件必填**：`mode_id`、`play_id`、计数、金额/资产字段，按 `game_type` 和是否存在该业务概念决定。
- **观测/兼容字段**：客户端与服务端时间、SDK 版本、热更新版本、原始 payload、验证错误列表、接收/入库时间；这些字段即使业务字段不完整也应尽量保留。

### 3.2 类型与枚举校验

| 类别 | 字段示例 | 预期类型/规则 | 常见异常 |
|---|---|---|---|
| 标识类 | `event_id`、`user_id`、`xl_id`、`uuid`、`game_id`、`session_id`、`round_id` | 字符串；不做数值化；允许业务定义的长度和字符集 | 数字被序列化成字符串/反之、空串、截断、重复 |
| 版本/环境类 | `product_version`、`hot_update_version`、`sdk_version`、`package_name`、`client_type` | 字符串；版本按字典或 SemVer/现有规则校验 | 老版本字段名、热更新覆盖、版本为空、包名大小写不一致 |
| 时间类 | `event_time`、`received_at` | ISO/平台约定时间；时区可还原；客户端时间与服务端接收时间分开保存 | 毫秒/秒混用、时区错位、未来时间、延迟过大 |
| 计数类 | `bet_count`、`bet_times`、`goal_times` | 非负整数；不接受 `1.0`、空字符串或负数 | 字符串数字、浮点、负数、`null` |
| 金额类 | `bet_amount`、`win_amount`、`reward_amount` | 数值；精度、正负方向、币种/资产类型由字典定义 | 分/元或最小单位混用、NGN 与其他币种混用、负号方向不一致 |
| 结束结果 | `result`、`end_reason` | 字符串枚举；未知值不得静默映射为“其他” | 客户端新枚举未同步、大小写/空格不一致、`quit` 与 `exit` 多套命名 |
| 业务维度 | `game_type`、`mode_id`、`play_id`、`account_type` | 字符串枚举或字典 ID；必须可关联字典 | ID 不存在、旧 ID 仍上报、同义值多套编码 |
| 来源 | `source` / `report_source` | 枚举：至少区分 client/server/bridge/retry/unknown，最终以链路字典为准 | 来源字段缺失、转发层覆盖原始来源、重试被当成新事件 |

类型校验优先使用“原始 JSON 类型 + 规范化值”双列保存；只做明确允许的兼容转换（例如去除首尾空格），不能把未知枚举、负数或金额单位错误转换后当成正常数据。

## 4. 分维度排查路径

### 4.0 先建立可追溯基线（P0）

在修复任何字段前，先确认每条原始 GAMEEND 至少能关联以下元数据：`ingest_id`、`event_id/request_id`、`received_at`、原始 payload、`source`、`product_version`、`hot_update_version`、`package_name`、错误类型和错误字段。若当前链路没有这些字段，先补链路字段，再做异常归因；否则无法区分“客户端坏数据”“转发层改写”和“入库校验失败”。

首轮建议抽取：全量错误计数 + 每类错误 100 条原始样本 + 每个版本/来源/包名的分层样本。样本中禁止保存账号凭据或完整敏感身份信息，保留脱敏后的关联键和 payload hash 即可。

### 4.1 必填字段路径（P0）

| 排查顺序 | 重点检查 | 最小判断 | 可能根因 | 修复动作 |
|---|---|---|---|---|
| 1 | 事件标识、追踪键、接收时间 | 非空率、唯一率、重试复用率 | 老 SDK 未生成 `event_id`；网关改写字段；批量上报丢元数据 | 在 SDK/网关统一生成并透传追踪键，原始层保留 `ingest_id` |
| 2 | 用户/设备身份 | 登录/匿名分支分别统计缺失率 | 登录前事件只传 `user_id`；匿名事件未传 `uuid`；起源 ID 未绑定 | 固化身份优先级和关联规则；缺失进入隔离表 |
| 3 | 游戏上下文 | `game_type`、`game_id`、`session_id/round_id` 缺失率 | 退出/断线/失败路径未走统一上下文；客户端内存清理后无法取值 | 结束事件从服务端事实或持久化局上下文补齐，不能只补默认值 |
| 4 | 结束结果 | `result`、`end_reason` 缺失/空串/不一致 | 正常结束、退出、失败多个代码路径各自组包 | 统一 GAMEEND 构造器；所有结束路径先归一化再上报 |
| 5 | 条件字段 | 按 `game_type/mode_id/play_id` 看 `bet_*`、`goal_times` 缺失 | 不同玩法复用同一 schema，但条件字段未做玩法分支 | 建立“玩法 × 字段必填矩阵”，不适用字段显式为 `not_applicable` 或不入列 |

处理原则：缺失字段先标记 `missing:<field>` 并进入隔离/错误明细，原始事件不删除；只有在字段契约确认后，才把该字段纳入硬校验。

### 4.2 类型与枚举路径（P0）

1. 先按 `error_type` 或解析器报错信息区分 `type_error`、`enum_error`、`parse_error`，再按字段排名。
2. 对计数类检查字符串数字、浮点、负数和科学计数法；对金额类同时检查精度、单位和币种/资产类型。
3. 对 `result/end_reason/game_type/mode_id/play_id/source/client_type/account_type` 拉取当前字典，比较“字典生效时间”和“首次出现时间”。
4. 未知枚举进入隔离表，保留 `raw_value`；不能统一改成 `other` 后继续入库，否则下游无法发现新状态。
5. 类型修复必须覆盖序列化层、网关解析层和标准化表三处；只改下游 CAST 不能消除上游坏数据。

### 4.3 版本路径（P0）

按以下组合切片，找出异常率首次跃升的版本、热更新版本和包：

`product_version × hot_update_version × sdk_version/schema_version × package_name × event_date/hour`

重点核对：

- 新版本是否新增了字段、改了字段名、把数值改成字符串，或增加了未登记枚举。
- 热更新是否替换了事件构造逻辑，但客户端展示版本未变化。
- 老版本是否继续发送旧 schema；服务端是否保留向后兼容解析。
- `unknown_version` 是否与异常率同步上升；如果版本缺失，应先修版本透传。
- 服务端部署版本/网关版本是否与客户端版本同时切换，避免把服务端解析回归误判为客户端问题。

版本修复要求：新旧 schema 至少在一个兼容窗口内都可解析；迁移完成后才下线旧字段；新 schema 必须带 `schema_version` 或等价可追踪字段。

### 4.4 来源路径（P0/P1）

至少按 `source/report_source` 区分客户端、服务端、桥接/转发和重试队列；若平台暂时没有来源字段，应从 SDK、网关路由、队列 topic 或服务端事件日志补出来源维度。

| 来源切片 | 重点判断 | 验证方式 | 修复方向 |
|---|---|---|---|
| 客户端 | 是否只在退出/失败/断线路径缺字段 | 版本 × `end_reason` × `client_type` 对比 | 统一事件构造器，发送前做本地 schema 校验 |
| 服务端 | 是否因客户端事件转服务端事实时丢字段 | 原始事件与标准化事件按 `event_id/round_id` 对账 | 解析器兼容旧/新字段，保存原始值和错误原因 |
| 桥接/转发 | 是否改名、截断、类型转换或覆盖来源 | 逐跳比较 payload hash、字段类型和字段数 | 禁止无记录的字段改写；转发层增加 schema 版本和 trace |
| 重试/补发 | 是否造成重复或错误状态被重复放大 | `event_id`、`round_id`、`received_at` 排序检查 | 幂等键 + 重试次数 + 原始首次接收时间；异常事件可重放但不可重复计数 |
| 多来源并发 | 同一局是否同时有客户端和服务端 GAMEEND | 同一 `round_id/game_id` 的来源数量与时间差 | 明确权威来源；分析层只选一条事实，另一条作为覆盖/对账信号 |

### 4.5 次级控制：重复、延迟和时序（P1）

埋点地图明确要求核对重试、重复上报、延迟上报和时区。GAMEEND 异常修复后应继续检查：同一局是否多条结束事件、结束事件是否早于开始事件、客户端时间与服务端接收时间差是否异常、补发是否跨日。若没有稳定的 `round_id/session_id`，先补业务幂等键，不能只用整包 hash 去重。

## 6. 事件级监控指标与建议门槛

以下门槛是当前缺少历史稳定基线时的**建议初始值**，上线前由数据/研发负责人确认并固化；一旦取得 7 天稳定基线，可再按基线的 P95/P99 调整。

| 指标 | 计算口径 | 必须切分 | 建议门槛/动作 |
|---|---|---|---|
| `received_count` | 原始层收到的 GAMEEND 条数 | 日期/小时、来源、版本、包、玩法 | 监控突降/突增；与启动/开始局量联动检查 |
| `persisted_count` | 标准化事实表成功入库条数 | 同上 | 与接收量对账；不可解释差异触发 P0 |
| `invalid_count` | 任一字段校验失败的事件数 | `error_type/error_field` + 版本/来源 | 必须可追溯到原始事件 |
| `invalid_rate` | `invalid_count / received_count` | 事件、日期/小时、版本、来源、包、`game_type` | 整体目标 `<0.5%` 连续 24 小时；任一主要切片不得 `>1%` |
| `missing_required_rate` | 缺失硬必填字段的事件数 / 接收量 | 字段、玩法、结束原因、版本 | 生产 `<0.1%`；确定性回放必须为 0 |
| `type_error_rate` | 类型/解析失败事件数 / 接收量 | 字段、版本、来源 | 生产 `<0.1%`；新版本上线即超阈值阻断 |
| `enum_error_rate` | 未知/不在字典的枚举事件数 / 接收量 | 字段、枚举值、版本、玩法 | 生产 `<0.1%`；未知值必须保留原值并告警 |
| `persist_rate` | `persisted_count / received_count` | 来源、版本、包 | 目标 `≥99.5%`；不满足则阻断下游使用 |
| `discard_rate` | 抛弃条数 / 接收量 | 错误类型、来源、版本 | 目标为 0；如非 0 必须有隔离数据和补偿方案 |
| `unknown_version_rate` | 版本缺失/无法映射事件数 / 接收量 | 包、来源、版本组合 | `<0.1%`；否则无法定位回归，按 P0 处理 |
| `source_error_rate` | 各来源异常数 / 各来源接收数 | `source/report_source` | 任一来源显著高于整体时按来源负责人处理 |
| `duplicate_rate` | 同一幂等键重复事件数 / 接收量 | `round_id/event_id`、来源、重试次数 | 目标按业务基线确认；不得导致局数重复计数 |
| `late_arrival_rate` | 超过约定延迟窗口到达事件数 / 接收量 | `event_time`、`received_at`、来源、版本 | 先定义窗口；跨日补发需可识别，不得误归属 |
| `end_coverage`（可选） | 有效 GAMEEND 局数 / 有效 START 或进入局数 | 玩法、版本、来源 | 仅在存在可信 START/开始局事件时启用，先做趋势监控 |

监控面板最小维度：`event_code`、`dt/hour`、`source`、`product_version`、`hot_update_version`、`sdk_version/schema_version`、`package_name`、`client_type`、`game_type`、`mode_id`、`play_id`、`error_type`、`error_field`。所有指标同时展示分子、分母和数据更新时间，避免只看百分比。

## 7. 验收 SQL / 伪代码

以下 SQL 使用 BigQuery 风格函数作为模板；请将 `<project>.<dataset>.<table>` 和 JSON 路径替换为实际表名/字段名。验收前必须保证 `ingest_id` 或等价追踪键存在，否则接收量与入库量不能可靠对账。

### 7.1 事件级质量总览

```sql
-- 伪 SQL：原始事件表需保留原始 payload 与链路元数据
WITH raw AS (
  SELECT
    DATE(received_at) AS dt,
    ingest_id,
    event_id,
    event_code,
    source,
    product_version,
    hot_update_version,
    package_name,
    JSON_VALUE(payload, '$.user_id') AS user_id,
    JSON_VALUE(payload, '$.xl_id') AS xl_id,
    JSON_VALUE(payload, '$.uuid') AS uuid,
    JSON_VALUE(payload, '$.game_type') AS game_type,
    JSON_VALUE(payload, '$.game_id') AS game_id,
    JSON_VALUE(payload, '$.session_id') AS session_id,
    JSON_VALUE(payload, '$.round_id') AS round_id,
    JSON_VALUE(payload, '$.result') AS result,
    JSON_VALUE(payload, '$.end_reason') AS end_reason,
    JSON_VALUE(payload, '$.mode_id') AS mode_id,
    JSON_VALUE(payload, '$.play_id') AS play_id,
    JSON_VALUE(payload, '$.bet_count') AS bet_count_raw,
    JSON_VALUE(payload, '$.bet_times') AS bet_times_raw,
    JSON_VALUE(payload, '$.goal_times') AS goal_times_raw,
    received_at
  FROM `<project>.<dataset>.<raw_event_table>`
  WHERE event_code = 'GAMEEND'
    AND received_at >= @start_ts
    AND received_at < @end_ts
), checks AS (
  SELECT
    *,
    (
      NULLIF(TRIM(COALESCE(event_id, '')), '') IS NULL
      OR NULLIF(TRIM(COALESCE(game_type, '')), '') IS NULL
      OR NULLIF(TRIM(COALESCE(game_id, '')), '') IS NULL
      OR (NULLIF(TRIM(COALESCE(user_id, '')), '') IS NULL
          AND NULLIF(TRIM(COALESCE(xl_id, '')), '') IS NULL
          AND NULLIF(TRIM(COALESCE(uuid, '')), '') IS NULL)
      OR NULLIF(TRIM(COALESCE(result, '')), '') IS NULL
      OR NULLIF(TRIM(COALESCE(end_reason, '')), '') IS NULL
      OR (NULLIF(TRIM(COALESCE(bet_count_raw, '')), '') IS NOT NULL
          AND SAFE_CAST(bet_count_raw AS INT64) IS NULL)
      OR SAFE_CAST(bet_count_raw AS INT64) < 0
      OR (NULLIF(TRIM(COALESCE(bet_times_raw, '')), '') IS NOT NULL
          AND SAFE_CAST(bet_times_raw AS INT64) IS NULL)
      OR SAFE_CAST(bet_times_raw AS INT64) < 0
      OR (NULLIF(TRIM(COALESCE(goal_times_raw, '')), '') IS NOT NULL
          AND SAFE_CAST(goal_times_raw AS INT64) IS NULL)
      OR SAFE_CAST(goal_times_raw AS INT64) < 0
    ) AS has_validation_error
  FROM raw
)
SELECT
  dt,
  COUNT(*) AS received_count,
  COUNTIF(has_validation_error) AS invalid_count,
  COUNTIF(NOT has_validation_error) AS candidate_valid_count,
  SAFE_DIVIDE(COUNTIF(has_validation_error), COUNT(*)) AS invalid_rate
FROM checks
GROUP BY dt
ORDER BY dt;
```

说明：上例中的条件必填字段不能直接对所有玩法一刀切；正式 SQL 应加入“玩法 × 字段必填矩阵”。类型检查要同时读取原始 JSON 类型，不能只靠 `SAFE_CAST`，否则字符串数字会被误判为合法类型。

### 7.2 按版本、来源和包定位异常集中点

```sql
SELECT
  DATE(received_at) AS dt,
  COALESCE(source, 'unknown') AS source,
  COALESCE(product_version, 'unknown') AS product_version,
  COALESCE(hot_update_version, 'unknown') AS hot_update_version,
  COALESCE(sdk_version, 'unknown') AS sdk_version,
  COALESCE(package_name, 'unknown') AS package_name,
  COUNT(*) AS received_count,
  COUNTIF(error_type IS NOT NULL) AS invalid_count,
  SAFE_DIVIDE(COUNTIF(error_type IS NOT NULL), COUNT(*)) AS invalid_rate,
  COUNTIF(error_type = 'missing_required') AS missing_required_count,
  COUNTIF(error_type = 'type_error') AS type_error_count,
  COUNTIF(error_type = 'enum_error') AS enum_error_count
FROM `<project>.<dataset>.<gameend_quality_table>`
WHERE event_code = 'GAMEEND'
  AND received_at >= @start_ts
  AND received_at < @end_ts
GROUP BY 1, 2, 3, 4, 5, 6
HAVING COUNT(*) >= 50
ORDER BY invalid_rate DESC, received_count DESC;
```

验收判定：能识别异常率最高的版本/来源/包，并能回溯到具体 `error_field`；如果所有事件都落在 `unknown_version` 或 `unknown` 来源，先判定链路元数据不完整，不得以“异常已下降”结案。

### 7.4 接收、入库与隔离对账

```sql
WITH received AS (
  SELECT ingest_id, event_id
  FROM `<project>.<dataset>.<raw_event_table>`
  WHERE event_code = 'GAMEEND'
    AND received_at >= @start_ts
    AND received_at < @end_ts
), persisted AS (
  SELECT DISTINCT ingest_id, event_id
  FROM `<project>.<dataset>.<normalized_gameend_table>`
  WHERE event_code = 'GAMEEND'
    AND normalized_at >= @start_ts
    AND normalized_at < @end_ts
), quarantined AS (
  SELECT DISTINCT ingest_id, event_id
  FROM `<project>.<dataset>.<gameend_error_table>`
  WHERE event_code = 'GAMEEND'
    AND received_at >= @start_ts
    AND received_at < @end_ts
)
SELECT
  COUNT(*) AS received_count,
  COUNTIF(p.event_id IS NOT NULL) AS persisted_count,
  COUNTIF(q.event_id IS NOT NULL) AS quarantined_count,
  COUNTIF(p.event_id IS NULL AND q.event_id IS NULL) AS unexplained_count
FROM received r
LEFT JOIN persisted p USING (ingest_id)
LEFT JOIN quarantined q USING (ingest_id);
```

验收要求：`unexplained_count = 0`；若异常仍未入库，必须在隔离表中可查，且可按错误字段、版本和来源解释。不要用 `event_id` 单独连接重试事件，优先使用接收层 `ingest_id` 对账、业务幂等键去重。

## 8. 回归标准与测试矩阵

### 8.1 测试矩阵

| 场景 | 输入 | 预期结果 | 门槛 |
|---|---|---|---|
| 正常完局 | 新版本、合法字段、合法枚举 | 标准化入库 1 条，错误 0 条 | 必过 |
| 正常退出/失败/断线/超时 | 各结束原因各 1 组 | 均走统一构造器；结果和结束原因可还原 | 必过 |
| 身份分支 | 登录用户、匿名用户、起源 ID 绑定用户 | 按身份规则入库；不把匿名事件合并到同一用户 | 必过 |
| 每个硬必填缺失 | 逐字段置空/删字段 | 进入隔离，错误字段准确 | 必过；错误不可静默放行 |
| 条件字段缺失 | 按 `game_type/mode_id/play_id` 逐组测试 | 适用玩法隔离；不适用玩法按字典例外通过 | 必过 |
| 类型错误 | 计数传字符串/浮点/负数；时间传错误格式 | `type_error/parse_error` 可定位；原始值保留 | 必过 |
| 枚举错误 | 新增或未知 `result/end_reason/source` | `enum_error`；不映射为 `other` | 必过 |
| 版本兼容 | 旧客户端、热更新、服务端新旧解析器组合 | 兼容窗口内均可处理；schema 版本可追踪 | 必过 |
| 来源分支 | client、server、bridge、retry | 来源可识别；转发不丢字段；同一业务事件可幂等 | 必过 |
| 重试/重复 | 相同 `event_id` 或业务幂等键重复发送 | 只计 1 条标准事实，重复有日志 | 必过 |
| 延迟/乱序 | 结束事件晚到、跨日、先到 END 后到 START | 原始时间和接收时间均保留；按规则归属 | 必过 |
| 金额/资产 | 零值、小数、币种/资产类型合法组合 | 单位和正负方向符合字典；无隐式换算 | 必过 |

### 8.2 发布前与生产回归门槛

- **确定性验收**：上述测试 100% 通过；必填、类型和枚举错误不得进入标准化 GAMEEND 事实表；每条错误都能回到原始 payload 和错误字段。
- **回放验收**：使用脱敏历史样本覆盖主要版本、包、来源、玩法和结束原因；接收量 = 入库量 + 隔离量 + 明确重复量，未解释量为 0。
- **灰度 24 小时**：整体 `invalid_rate <0.5%`，主要切片不超过 1%；`missing_required_rate/type_error_rate/enum_error_rate <0.1%`；`persist_rate ≥99.5%`；`discard_rate = 0`；`unknown_version_rate <0.1%`。
- **稳定 7 天**：以上指标连续 7 天满足门槛；版本、来源、包和玩法没有新的异常集中点；重复/延迟事件不导致局数、完局率或资金类指标重复计数。
- **下游回归**：GAMEEND 修复后，抽样核对开始局→结束局、玩法/场次、收益留存和相关经营报表；当前日数据未完整结算时，不用当日快照判断回归成功。
- **阻断条件**：出现未解释接收-入库差、异常率在任一主要版本/来源突增、未知枚举被静默转码、原始数据不可回溯、或客户端/服务端同一局重复计数，均不得关闭 P0。

## 9. 研发提交时需要补齐的确认项
