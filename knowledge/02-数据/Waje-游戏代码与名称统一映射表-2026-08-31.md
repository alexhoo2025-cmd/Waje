# Waje 游戏代码与名称统一映射表

## 1. 使用结论

- 本表作为项目内 game_id → 游戏名称 → 游戏来源 → 游戏提供商 的统一参考入口。
- **PP和Tada均为联运厂商缩写**，不是游戏类型：
  - PP：联运厂商缩写；
  - Tada：联运厂商缩写。
- 游戏分析、RTP、埋点、GA4路径、Metabase和起源报表应优先使用 game_id 关联，游戏名称只用于展示。
- 同名游戏可能对应多个代码，禁止仅按游戏名称连接事实表。
- 自研游戏代码以技术部《自研游戏GameId》为最高优先级；产品游戏总表用于补充名称、厂商和属性。

## 7. Limbo/Keno映射冲突结论

产品游戏表显示：

    Limbo = 9010
    Keno  = 9008

技术部对照表确认：

    Limbo = 9008
    Keno  = 9010

两套映射相反。该冲突会直接影响：

- GA4游戏页面触达和回访；
- Metabase局数、下注和用户数；
- 起源GAMESTART/GAMEEND关联；
- 游戏上线前后留存归因；
- RTP与单游戏故障分析。

本知识库采用技术部映射作为自研游戏正式代码：Limbo=9008、Keno=9010。此前按相反映射生成的GA4、Metabase和单游戏报告必须重算；产品游戏表需要更正。

## 8. 同名不同代码

| 游戏名称 | 游戏代码 |
|---|---|
| Gold Rush | 40055、50491 |
| Limbo | 40087、9010 |
| Keno | 40093、9008 |

同名游戏可能来自不同厂商或产品形态。分析时必须同时携带：

    game_id
    game_name
    game_source
    provider
    client_type / package
    release_id / config_version

## 9. 数据建模建议

建议建立统一维表 dim_game：

    game_id              主键
    game_name            展示名称
    game_source          自研/三方
    provider             自研/PP/Tada/其他
    provider_game_id     厂商侧代码
    game_type            游戏类型
    link_type            长链接/短链接
    game_size_mb         游戏体量
    free_player_allowed  免费玩家是否可玩
    in_package           是否包内游戏
    valid_from/to        映射生效时间
    mapping_version      映射版本

事实表关联统一使用 game_id + mapping_version；名称、厂商和类型从维表获取，避免在不同报表中维护互相冲突的硬编码。

## 10. 更新规则

1. 飞书控制表修订号变化时重新读取五张工作表；
2. 检查代码缺失、同一代码多名称、同名多代码和轻量化跨表一致性；
3. 生成新的CSV/JSON快照，不覆盖历史快照；
4. 对影响现有报告的映射变化建立待重算清单；
5. 技术表与产品表冲突时，先按技术表冻结分析代码，再由产品/数据开发修正产品维表。
