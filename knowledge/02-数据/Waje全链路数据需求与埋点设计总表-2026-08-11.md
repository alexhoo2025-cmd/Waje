# Waje 全链路数据需求与埋点设计总表

> 目的：把产品需求、起源埋点、BigQuery 事实、MySQL 配置、GM 运营数据和报表看板统一到同一套数据契约中，作为后续埋点开发、数仓建模、报表建设、数据质量和版本回归的共同基线。
>
> 证据边界：本文基于项目知识库、起源平台 Waje Special 只读盘点、Lark 需求目录及其中已读取的数据/埋点相关文档整理。页面列表、模块列表、用户属性、事件属性和汇率转换在本次平台访问中部分返回“暂无数据”，该状态只记录为“待补证”，不推断为没有配置。底层 BigQuery/MySQL 表名和部分正式公式尚未提供，本文使用字段级契约和 SQL 模板，不冒充最终物理 schema。

## 1. 结论与使用方式

Waje 当前需要建立一条从“需求 → 事件 → 原始数据 → 标准事实 → 认证指标 → 看板”的可追溯链路。

```text
产品/运营需求
  → 数据问题与指标目标
  → 页面/模块/元事件/虚拟事件
  → 原始事件与服务端事实
  → 标准化事实层
  → 指标语义层与质量门槛
  → 起源 / BI / ARES / GM / Metabase 看板
  → 版本回归与经营动作
```

使用规则：

- 产品提数据需求时，先引用本文的业务模块、指标和事件链路，再补充页面/玩法特有字段。
- 研发新增事件时，必须同步 [[Waje埋点事件与属性字典-2026-08-11]]，不得只在代码中新增字段。
- 数据开发建表或改 SQL 时，必须同步 [[Waje数据指标看板映射与研发验收清单-2026-08-11]]，记录来源、口径、成熟窗口和质量状态。
- 任何指标在 `N/A`、未成熟、数据质量不通过或成本未入库时，不得用 0 代替并下业务结论。
- 不修改起源平台配置，不在知识库、日志或原始快照中保存账号、密码、Cookie、Token 或个人明细。

## 2. 已确认的平台与数据现状

### 2.1 起源数据管理模块

当前 Waje Special 可见的埋点相关入口：

| 模块 | 平台职责 | 已观察到的字段/能力 | 当前状态 |
|---|---|---|---|
| 埋点手册 | 上报模型与使用说明 | 页面、模块、通用/自定义参数 | 页面入口可用，细则需与研发文档对齐 |
| 数据质量 | 接收、入库、异常、抛弃 | 日期、事件筛选、上报源、导出异常 | 可用；应增加版本、包、玩法切片 |
| 埋点测试 | 用户轨迹和事件回放 | 账号 ID、日期、上报源、事件、功能埋点 ID、错误码 | 可用于 QA 与线上定位 |
| 元事件管理 | 原子事件字典 | 事件名、展示名、平台、昨日入库量、描述、分类、状态、操作人 | 当前可见 34 个元事件 |
| 虚拟事件 | 元事件组合或条件事件 | 事件分组、事件标识、SQL、层级、修改时间 | 已用于新增、活跃、首充、TX 失败等口径 |
| 用户属性 | 用户维度定义 | 属性名、显示名、类型、计算逻辑、状态、维度表 | 本次页面部分返回暂无数据，需补导出 |
| 事件属性 | 事件维度定义 | 属性名、显示名、类型、状态、维度表 | 本次页面部分返回暂无数据；关键事件详情已读到 |
| 汇率转换 | 基础货币与目标货币 | 目标货币、汇率、更新时间、产品、同步规则 | 本次页面部分返回暂无数据，需确认当前配置 |
| 页面列表 | 功能页面 | 页面图、名称、ID、系统类型、模块数/事件数、owner、更新时间 | 当前页面部分返回暂无数据；以历史截图和需求文档补证 |
| 模块列表 | 页面内功能模块 | 模块名、事件类型、模块标识、系统类型、所属页面、owner、更新时间 | 当前页面部分返回暂无数据 |
| 埋点参数 | 功能埋点参数 | 属性名、显示名、说明、数据类型、状态、属性类型、维度表 | 当前可见自定义参数列表暂无数据 |

### 2.3 数据基础架构边界

| 层/系统 | 正式职责 | 本文设计要求 |
|---|---|---|
| BigQuery | 统计事实、明细和聚合：用户、订单、游戏、下注、派奖、生命周期、RTP、质量 | 认证指标和看板事实优先落在 BQ；记录数据截止、完整日、成熟度和质量状态 |
| MySQL | 系统权限、事件定义、指标/游戏/版本/渠道配置、字典和权限 | 作为配置与元数据源；禁止把权限和配置硬编码在报表 SQL |
| Impala | 旧统计引擎 | 迁移并行期只做对账；通过验收后逐步下线 |
| 起源/Ares | 产品与行为分析、投放分析、数据管理和可视化 | 按主题拆分入口；统一指标语义和筛选字典 |
| BI | 经营、财务、结算和管理分发 | 只消费认证指标，不自行复制一套付费/留存口径 |
| GM | 用户维护、配置、实时查询和排障 | 保留操作能力；生命周期/RTP 趋势分析迁移至起源/认证指标层 |
| Metabase | 受控数据访问、风险隔离、临时验证和专题看板 | 只连接授权数据集；所有导出和敏感字段访问留审计 |

## 3. 需求覆盖矩阵

### 3.1 Lark 需求树覆盖

| 文档分支/主题 | 已确认的相关内容 | 数据/埋点产出 |
|---|---|---|
| Web 需求 | web 1.0/2.0、国家适配、多语言、设备监控与性能优化 | H5 页面、性能、弱网、版本和国家维度 |
| App 需求 | Coin 金币场、充值 TX 通知、OTP、签到、商城、Push、风险用户、KYC/BVN、动态页签 | 注册、支付、资产、任务、风险、通知和功能埋点 |
| 联运需求 | BetC 游戏清单、流量分配、Tada 新游戏、H5 Palmpay 落地页 | 外接游戏、供应商、渠道、玩法和流量分配字段 |
| 技术需求 | 页面采集、模块采集、TX 优化、金币场 AB、金币场玩家身份打点 | 页面/模块模型、AB、身份和交易链路 |
| 版本/发版/数据分析 | 新包、老包、版本报告、生命周期和 RTP | 版本对照、完整日、生命周期 cohort、RTP 事实 |
| 风控与合规 | 风险用户、KYC、BVN、银行校验、OTP 限制 | 风险状态枚举、校验结果、失败原因和审计，不采集生物信息 |
| 数据平台优化整合 | Ares、BI、GM、BigQuery、Metabase、权限 | 语义层、系统边界、血缘、权限和迁移验收 |

### 3.2 数据需求到事件域

| 业务问题 | 必要事实 | 主要事件/表 | 结果指标 |
|---|---|---|---|
| 新用户是否完成新手路径 | 用户、版本、注册、入口、首局、首充、任务 | `REGISTER`、`LOGIN`、`PV`、`MC`、`GAMESTART`、`ORDER`、`FINISHTASK` | 注册到首局、首充率、D1/D7 留存、任务完成率 |
| 新包是否影响质量 | 版本、包、设备、页面、错误、游戏链路 | `INSTALL`、`AL`、`PV`、`PAGELOAD`、`CRASH`、`GAMESTART`、`GAMEEND` | 启动成功率、首屏耗时、崩溃率、进局成功率 |
| 游戏玩法是否健康 | 局、下注、返奖、资产、模式、机器人 | `GAMESTART`、`GAMEEND`、`BETREWARD`、`ASSET` | 有效局数、完局率、下注额、返奖、RTP、TC、收益留存 |
| 充值和提现是否顺畅 | 订单、支付状态、账务、TX、风控、通知 | `ORDER`、`ASSET`、`WITHDRAW`、`AUDIT`、`LOGIN` | 支付成功率、到账时延、TX 成功率、失败原因、资金对账 |
| Coin 金币场是否有效 | Coin 资产、页签、下注、返还、奖励、机器人/真人 | `MC`、`GAMESTART`、`GAMEEND`、`ASSET`、`GETITEM`、`USEITEM` | Coin 使用率、游戏深度、奖励成本、回流和转化 |
| 运营活动是否增量 | 场景、人群、分组、触达、奖励、结果 | 新增运营事件 + 订单/游戏/留存事实 | 对照/实验增量、成本、净收益、护栏 |

## 4. 统一事件模型

### 4.1 事件最小身份

```text
event_name
event_version
event_uid
event_time_client
event_time_server
received_at
source
platform
app_version / web_version
package_name
channel
user_id
uuid
session_id
trace_id
```

`event_name + event_version + event_uid` 是事件治理最小单元。`event_uid` 必须支持重试幂等和原始记录回溯，不得每次重试随机生成新业务事件 ID。

### 4.2 业务公共参数

```text
country
currency
asset_type
game_id
game_type
play_id
mode_id
room_id
round_id
package_name
channel
attribution_media
campaign_id
creative_id
user_type
lifecycle_day
is_robot
experiment_id
config_version
```

### 4.3 数据治理字段

```text
is_retry
retry_count
is_duplicate
ingest_id
ingest_time
schema_version
source_version
error_type
error_field
error_code
error_message
raw_payload_hash
```

必须区分用户 ID、起源 ID和设备 ID；客户端时间、服务端时间和入库时间；事件次数、事件人数、用户 UV 和设备 UV；真金、金币和奖励资产；基础/完全下注额和基础/完全真实回报比；BQ 与旧引擎来源。

## 5. 业务模块与事件链路

### 5.1 用户、新手和生命周期

```text
INSTALL/AL
  → REGISTER
  → LOGIN/绑定账号
  → 首次大厅 PV
  → 首次游戏 MC/MV
  → GAMESTART
  → GAMEEND/BETREWARD
  → 首次 ORDER 成功
  → 任务完成/奖励领取
  → D1/D7 留存
```

必须补充或确认：OTP 发送/成功/失败/限流、注册失败、首登、首个有效局、首充入口、首充成功、每日登录、任务曝光/领取/完成/奖励到账。

### 5.2 页面、模块和功能

```text
页面 page_id
  → 模块 module_id
    → 功能埋点 event_id
      → 元事件 + 事件属性 + 用户属性
```

`PV/PD` 必须可配对并统一停留时长单位；`MV` 明确曝光阈值、去重和可见时长；`MC` 固定 `element_id`、元素类型、业务动作和内容。`element_type` 与 `elements` 当前均显示为元素类型，必须完成字段合并或职责拆分。

### 5.3 游戏、下注和结算

```text
大厅/玩法入口
  → GAMESTART
  → 匹配/组局
  → 下注尝试/成功/失败
  → 回合/托管/取消托管
  → GAMEEND
  → BETREWARD
  → ASSET
```

`GAMEEND` 是 P0。必须覆盖正常结束、主动退出、失败、断线、超时、托管结束等路径，并明确 `round_id`、`status`、`end_reason`、金额/币种、玩法/模式、版本/来源和机器人标记。

### 5.4 资产、任务和 Coin

Coin 需求明确：充值赠送、Coin 下注和返还、金币页签、特殊场、额外奖励、破产处理、真人匹配限制。必须区分：资产获得、消耗、返还、过期、奖励发放、奖励领取和账本落账。

### 5.5 充值、提现和风控

```text
充值页 PV
  → 支付方式 MC
  → ORDER 创建
  → 支付发起
  → 支付成功/失败
  → ASSET 入账

TX 页 PV
  → TX 提交
  → 风险识别/OTP/KYC/BVN
  → WITHDRAW
  → AUDIT
  → 成功/失败/到账
```

金融事实以服务端订单、账务和 TX 状态为准；客户端事件只用于页面漏斗和失败体验诊断。KYC 只记录合规批准的状态枚举，不采集人脸或证件原文。

### 5.6 版本、渠道、性能和稳定性

核心事件必须支持 H5、Android、iOS、老包/新包、版本、热更新、渠道、分包、归因媒体、国家、设备和网络维度。性能域至少包括首屏、白屏、接口、进局、下注、充值、TX、崩溃、ANR、网络重试和错误码。

## 6. 事件新增与治理优先级

| 优先级 | 范围 | 目标 |
|---|---|---|
| P0 | `GAMEEND`、下注结算、`ASSET`、支付成功、提现结果、风险拦截、金额对账 | 确保局数、资金和利润事实可用 |
| P1 | 注册登录、新手任务、首充、Coin、游戏开始、页面/模块主链路、版本质量 | 支撑新手、版本和产品优化 |
| P2 | Push、分享、客服、活动、Web 自动采集、非核心性能 | 支撑运营和体验细分 |
| P3 | 历史事件清理、低使用率字段合并、旧引擎兼容收尾 | 降低长期维护成本 |

## 7. 责任与评审门槛

| 角色 | 必须负责 |
|---|---|
| 产品 | 明确业务目标、触发时机、主指标、护栏、适用端和优先级 |
| 数据产品 | 维护事件/属性/指标字典、血缘、质量门槛和变更记录 |
| 客户端研发 | 统一事件构造器、版本兼容、发送前校验、设备/版本字段 |
| 服务端研发 | 金融/游戏事实、幂等、状态机、账务和审计 |
| 数据开发 | 原始层、标准事实层、语义层、回填、对账和质量监控 |
| QA | 正常/异常/弱网/重试/升级/降级和跨端回归 |
| BI/报表 | 只消费认证指标，显示完整日、成熟窗口、质量状态和截止时间 |
| 运营/客服 | 验证场景、奖励、通知、TX 和用户可见结果 |

上线前必须完成：字段契约评审、样例 payload、事件测试、数据质量查询、下游报表映射、权限/脱敏审查和回滚方案。
