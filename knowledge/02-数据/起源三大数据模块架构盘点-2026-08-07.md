# 起源三大数据模块架构盘点

## 1. 盘点范围

本次核验了起源平台首页和三个系统入口：

| 模块 | 地址 | 当前定位 |
|---|---|---|
| 业务报表和看板 / 起源分析平台 | <https://datagrowth.wajegame.com/tracking-web/iframe> | 行为、用户、留存、事件、报表集市和数据治理 |
| ARES 投放数据平台 | <https://datagrowth.wajegame.com/ares-web/homePage> | 投放数据、媒体行为、智能投放和渠道发行 |
| BI 系统 / 商业智能平台 | <https://datagrowth.wajegame.com/datart-web/organizations/5bace6dcaef542ea9d7cc42d57cc165d/vizs/c7aad7acf3ed40b38594229ffeb246e9> | 数据源、模型、仪表板、数据图表和协作分发 |

核验时间：2026-08-07。仅做页面读取，未修改报表、权限、数据源或投放配置。

## 2. 首页整体结构

平台首页把三个系统并列呈现：

```text
Waje 数据平台门户
├── 起源分析平台：用户/行为/留存/事件/报表
├── ARES 投放平台：媒体/渠道/投放/智能策略
└── 商业智能平台：数据源/模型/仪表板/分享推送
```

首页的产品描述分别强调：

- 起源：降低数据分析门槛，提供多维度交叉分析，辅助业务决策。
- ARES：打通自有行为和媒体行为，支持 ROI 决策、智能止损、预算自动调整和回传控制。
- BI：提供从数据接入、模型分析到可视化呈现的完整 BI 能力，支持报表分享和推送。

这说明三端的设计意图是互补的，但当前入口仍是并列跳转，尚未形成统一的“发现问题—归因—分析—执行”工作流。

## 3. 起源分析平台：业务分析层

### 3.1 当前模块结构

| 一级模块 | 主要能力 | 适合回答的问题 |
|---|---|---|
| 首页 | 产品入口和平台导航 | 从哪里进入分析 |
| 业务看板 | 公共看板、我的看板 | 固定经营视图是什么 |
| 敏捷分析 | 书签、留存、事件、漏斗、分布、属性 | 用户和行为如何变化 |
| 数据统计 | 用户、玩家价值、埋点、终端 | 核心用户指标是多少 |
| 用户分析 | 预警、分群、用户轨迹 | 哪些用户异常、用户做了什么 |
| 报表集市 | 经营、玩法数值、游戏、增长、经济体系 | 已沉淀哪些主题报表 |
| 数据管理 | 埋点手册、数据质量、元事件、属性、字典 | 数据是否正确、事件如何定义 |
| AB 测试 | 实验入口 | 版本/策略是否有效 |

### 3.2 产品判断

起源是当前最接近“产品数据分析工作台”的系统，但仍存在三个结构性问题：

1. 报表入口按历史功能堆叠，首屏没有统一核心指标和异常优先级。
2. 报表、用户轨迹、埋点明细之间的下钻关系不够显式。
3. 起源自身能看行为和用户结果，但投放成本、媒体归因、BI模型和GM生命周期数据没有完全聚合。

因此起源适合作为统一分析入口，但不应继续单纯扩充报表数量。

## 4. ARES 投放平台：增长归因与投放执行层

### 4.1 当前可见结构

ARES 页面显示以下一级模块：

| 一级模块 | 推断职责 |
|---|---|
| 数据中心 | 投放数据、媒体行为、成本和效果分析 |
| 智投助手 | 自动化策略、止损、预算调整和投放辅助 |
| 渠道发行 | 渠道、媒体、包和发行关系管理 |
| 基础设置 | 投放系统基础字典、账户和策略参数 |
| 脚本管理 | 投放脚本或自动化任务 |

### 4.2 当前可用性问题

本次访问 ARES 首页时，页面顶部出现“区服获取失败”，主内容区为空。这个现象至少说明：

- ARES 页面依赖区服/区域上下文，区服接口异常会影响首页加载。
- 当前不能把“空白页面”判断为没有投放数据。
- 需要将区服获取、权限、接口响应和页面加载拆成平台级健康监控。

### 4.3 产品定位判断

ARES 不应承担完整的产品行为分析，也不应成为产品经理查询留存、用户路径和故障明细的主入口。它的核心职责应是：

```text
媒体/渠道成本
  → 归因用户
    → 新增/活跃/付费/留存结果
      → ROI 判断
        → 投放策略执行
```

ARES 最需要的不是更多业务报表，而是与起源统一用户、渠道、媒体、版本和付费结果口径。

## 5. BI 系统：统一模型和可视化交付层

### 5.1 当前页面结构

BI 当前打开的是“经营大盘”仪表板，页面可见：

- 仪表板、视图、数据源、调度、成员、权限、变量等管理入口。
- 项目目录：`WAJE项目`、`WAJE项目_BQ`、`手心玩`、`下线待删除`。
- 当前仪表板标签：`经营大盘`。
- 看板操作：嵌入、编辑、更多。
- 趋势区域：新增日活。
- 结果表：按日期、游戏展示基础数据、充值数据和 TX 数据。

### 5.2 当前经营大盘指标

页面字段覆盖面很宽，能看到以下指标组：

| 指标组 | 当前字段示例 |
|---|---|
| 用户规模 | 日活、付费日活、非付费日活、新增、注册人数、登录账户数、游戏人数 |
| 游戏参与 | 0局用户占比、游戏局数、APP在线人均时长、有效用户APP在线人均时长 |
| 收入与付费 | 营收、首充金额、新增付费金额、付费人数、付费金额、平均首充金额、首充率、新增付费率 |
| 成本与利润 | 投放成本、利润、日活人均营收 |
| 充值 | 历史付费登录用户数、登录用户人均充值、充值渠道手续费 |
| 提现/TX | 申请TX金额、TX到账人数、TX到账金额、申请TX人数、TX手续费、TX用户手续费、TC比 |
| 筛选 | 开始日期、结束日期、归因媒体、分包渠道、归因渠道、H5/APP、生命周期 |

当前页面抓取到部分组件处于加载状态，且明细区域出现 `No Data`。因此字段结构可以作为平台能力证据，但当前数值不应作为经营结论，需核验数据源、刷新状态和筛选条件。

### 5.3 产品定位判断

BI 最适合作为统一模型的可视化和分发层：

- 负责跨主题汇总、仪表板、数据图表、调度、分享和推送。
- 不应在每个仪表板内部重复定义 DAU、付费、留存、TX、TC 等指标。
- `WAJE项目_BQ` 目录表明 BigQuery/统一数仓可能已经是重要数据组织方向，但需要确认数据源 owner、刷新频率和口径版本。

## 6. 三端关系与职责边界

### 6.1 推荐目标架构

```text
统一事实层 / BigQuery
├── 用户事实：注册、登录、活跃、留存、轨迹
├── 行为事实：PV、MV、MC、GAMESTART、GAMEEND
├── 付费事实：订单、支付成功、退款、提现、资产流水
├── 投放事实：媒体、渠道、成本、归因
├── 生命周期事实：游戏、生命周期、下注、RTP、控制调整
└── 质量事实：延迟、缺失、异常、完整日、口径版本
          ↓
统一指标层 / 指标字典 / 维度字典
          ↓
起源：分析工作台  |  ARES：投放执行  |  BI：经营看板与分发
```

### 6.2 目标分工

| 工作流 | 主入口 | 辅助入口 | 最终产出 |
|---|---|---|---|
| 新手生命周期 | 起源 | BI、埋点明细 | 漏斗、留存、首付费、用户路径 |
| 游戏/RTP/奖池 | 起源 | GM、BI | 游戏与生命周期异常、数值调整 |
| 投放 ROI | ARES | 起源、BI | 媒体/渠道成本、回收、预算策略 |
| 经营日报/周报 | BI | 起源、ARES | 管理看板、趋势、推送 |
| 用户故障定位 | 起源 | BI、原始事件、客服 | 用户轨迹、事件、版本和终端定位 |
| 数据治理 | 起源数据管理 | BI数据源/调度 | 事件字典、质量监控、指标口径 |

## 7. 当前主要问题

### P0：平台入口与数据工作流断裂

- 三端并列存在，但没有统一任务入口。
- 用户从起源发现异常后，通常需要手动跳转 ARES、BI 或其他明细平台。
- 起源、ARES、BI 之间的筛选条件不能保证自动继承。

### P0：指标重复定义

- DAU、新增、付费、首充、营收、TX、TC 等指标在多个系统出现。
- 同名指标可能使用不同时间口径、用户口径和数据源。
- `TC` 等缩写在 BI 中出现，但正式公式、单位和分母仍需进入指标字典。

### P1：数据状态不可见

- ARES 出现区服获取失败，但没有在门户或平台健康页统一呈现。
- BI 出现加载中和 `No Data`，用户难以区分无数据、筛选冲突、权限不足和接口失败。
- 起源已有数据质量入口，但质量状态未统一回显到看板卡片。

### P1：下钻链路不完整

建议所有汇总结果都支持携带以下上下文：

`date`、`game_id`、`play_id`、`lifecycle`、`media`、`channel`、`version`、`platform`、`user_id`、`uuid`、`order_id`、`event_id`。

## 8. 优化优先级

### 第一阶段：统一入口和口径

1. 在门户增加“经营总览、新手生命周期、投放ROI、游戏/RTP、故障定位、数据质量”六个任务入口。
2. 建立统一指标字典，优先覆盖 DAU、新增、有效游戏用户、留存、付费金额、付费率、首充率、RTP、RTP偏差、数据可用率。
3. 统一日期、游戏、生命周期、版本、渠道、媒体、H5/APP 和数据状态筛选。

### 第二阶段：统一下钻和数据状态

1. 起源、ARES、BI 的汇总卡片使用统一下钻上下文。
2. 所有 No Data、加载失败、未成熟、补数和权限不足都显示明确状态。
3. BI 的经营大盘与 ARES 的投放结果按日期、媒体、渠道、产品和用户口径对账。

### 第三阶段：职责收敛

- 起源成为产品和用户分析入口。
- ARES 成为投放归因和执行入口。
- BI 成为统一经营看板、分享和推送入口。
- GM 作为生命周期奖池配置和运营排障后台，结果进入统一指标层。
- 归档重复报表，避免同一指标在三个系统分别维护。

## 9. 验收标准

- 用户可以从一个门户入口进入目标任务，而不是先记住三个系统地址。
- 同一日期、游戏、渠道、媒体和用户范围下，起源、ARES、BI 的核心指标可对账。
- 所有指标页面显示数据源、更新时间、口径版本和数据状态。
- 起源异常可以下钻到用户/事件；ARES异常可以下钻到媒体/渠道/成本；BI异常可以下钻到数据源/调度/模型。
- 统一筛选条件至少支持日期、产品、游戏、生命周期、版本、渠道、媒体、H5/APP、用户范围和数据状态。
- 旧报表归档前，完成至少 7–14 个完整日的并行核对。

## 10. 待确认事项

1. ARES 的“区服”是权限上下文、业务区服还是投放区域，以及失败时是否影响全量数据。
2. BI `WAJE项目` 与 `WAJE项目_BQ` 的数据源和 owner 是否分别对应旧库与 BigQuery。
3. BI 经营大盘当前 `No Data` 是数据为空、加载异常还是筛选/权限问题。
4. 起源与 ARES 的媒体、渠道、分包渠道字段映射。
5. DAU、新增、付费、营收、TX、TC 的统一事实源和正式指标定义。
