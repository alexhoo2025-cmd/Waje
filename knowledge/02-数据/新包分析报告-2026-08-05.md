# 新包分析报告

## 1. 执行摘要

本次更新文件包含 8 个新包/渠道工作表、2,370 条日期记录，新增人数合计约 548.5 万。整体看，App 渠道的留存、付费、LTV、TC 比和 TX 率明显高于 H5；H5 Facebook 是当前最弱渠道，H5 Google 相对较好但仍低于 App。

主要结论：

- **留存**：App Store、App Store iOS、Google Ads 的成熟 cohort 表现较好；H5 Facebook 的次留约 27.5%、7 日留存约 6.9%，明显偏低。
- **付费/LTV**：iOS App Store 新增付费率约 31.5%、终身值约 2,948；H5 Facebook 新增付费率约 7.9%、终身值约 123，端差异非常大。
- **TC 比/TX 率**：App 的 TC 比约 0.76–0.81、TX 率约 49%–61%；H5 Facebook 约 0.63 和 34%，H5 Google 约 0.76 和 44%，需要结合活动、KYC、提现限制和用户结构解释。
- **异常**：存在负的首日/终身值、部分 pww 的 7/15/30/60 日留存为 0、若干渠道近期 LTV 明显下降。负值可能是净收益/回报口径的真实结果，也可能是回滚、退款、活动奖励或日期未成熟造成，不能直接判定为程序错误。
- **数据使用边界**：2026-07-29 至 2026-08-05 的 cohort 尚未成熟，不应直接比较 30 日/60 日留存或终身 LTV；当前日和不完整日应从正式趋势中剔除。

### 3.1 留存差异

- iOS App Store 与 Google Ads 的次留分别约 57.8% 和 56.4%，7 日留存约 24.4% 和 23.6%，属于当前较强的 App/渠道组合。
- H5 Facebook 次留比 iOS App Store 低约 30.3 个百分点，7 日留存低约 17.5 个百分点；这是最需要优先排查的端/渠道差异。
- PAWAJEBETH5 的付费率不低，但留存显著低于 App，说明“付费转化”不能替代“持续留存”，应继续看首充用户留存和破产/提现行为。

### 3.2 付费与 LTV 差异

- iOS App Store 新增付费率约为 H5 Facebook 的 4 倍，终身值约为 H5 Facebook 的 24 倍，差异已不能仅用样本量解释。
- H5 Facebook 的低 LTV 与低留存、低付费率、低 TC 比和低 TX 率同时出现，优先怀疑端链路、渠道质量、游戏可用性或登录/支付/提现体验，而不是单一指标波动。
- Google 商店终身值高于 Google Ads，但两者留存和付费率接近，可能由付费金额、游戏结构、用户生命周期成熟度或 cohort 组成差异驱动，需要拆首充金额、付费档位和游戏类型。

### 3.3 TC 比与 TX 率

- Google Ads 的 TC 比最高，约 83.8%；iOS App Store 的 TX 率最高，约 60.9%，说明“回报/资金循环”和“提现行为”不是同一维度，不能用一个指标替代另一个。
- pww、H5 Facebook 的 TC 比和 TX 率均偏低，应检查其游戏参与、首充、提现门槛、KYC 拦截和用户生命周期结构。
- 需要确认 TC 比、TX 率的精确定义：是金额比、人数比、用户占比还是累计生命周期指标；当前仅按工作表列名和已有资料使用。

## 5. 异常情况与排查优先级

### P0：先确认是否影响经营判断

1. **H5 Facebook 全链路偏低**：次留、7 日留存、付费率、终身、TC 比和 TX 率同时偏低。排查登录、首启、支付、游戏入口、外接游戏权限、提现/KYC、渠道归因和服务器可用性。
2. **PAWAJEBETH5 近期付费率/TC 比上升但留存走弱**：需拆首充用户留存、首充金额、充值后下注/提现、破产率，防止将短期付费增长误判为新包质量改善。
3. **近期 cohort 的 LTV 不能直接比较**：新近日期的 15/30/60 日字段可能是空值、0 或未成熟值，应从日报趋势和排名中剔除。

### P1：数据口径与计算异常

1. **负值**：多个工作表存在负首日或负终身值，尤其 iOS、PAWAJEBETH5、pww 和 H5 Google。需核对是否为净收入/利润字段，以及退款、提现、奖励、回滚或跨日结算是否允许为负。
2. **pww 留存为 0**：pww 的 7 日留存有 5 条 0、15 日留存有 9 条 0、30 日留存有 13 条 0、60 日留存有 6 条 0。应核对是小样本真实为 0、未成熟填 0，还是回填缺失。
3. **首日/生命周期波动**：部分日期出现负首日、负终身或远高于相邻日期的 LTV；建议与版本发布、活动、服务器事故、奖励策略和渠道质量变更做事件对齐。

### P2：业务解释与长期优化

- 统一基础回报比、真实回报比、TC 比、TX 率的分子、分母、用户去重键和时间窗口。
- 按 App/H5、渠道、版本、游戏、生命周期和首充档位建立分层看板。
- 对小样本日期设置最小新增人数门槛和置信区间，避免单日极端值误导判断。

## 6. 建议的数据校验 SQL/伪代码

```sql
-- 1. 完整日和成熟 cohort
WHERE stat_date < CURRENT_DATE()
  AND is_complete_day = TRUE
  AND cohort_age_days >= retention_day

-- 2. 留存字段不应把未成熟值当真实 0
CASE
  WHEN cohort_age_days < retention_day THEN NULL
  WHEN retention_value IS NULL THEN NULL
  ELSE retention_value
END AS retention_value_valid

-- 3. 负值审计
SELECT source_sheet, stat_date, new_users, day_1, lifetime, note
FROM new_user_cohort
WHERE day_1 < 0 OR lifetime < 0;

-- 4. 业务指标重算
SELECT
  SUM(first_pay_users) / NULLIF(SUM(new_users), 0) AS paid_rate,
  SUM(tx_users) / NULLIF(SUM(eligible_users), 0) AS tx_rate,
  SUM(reward_amount) / NULLIF(SUM(bet_amount), 0) AS return_ratio
FROM cohort_fact
WHERE is_complete_day = TRUE;
```

## 7. 回归标准

- 新增 cohort 报表必须有数据截止时间和完整日标记。
- 未成熟的 15/30/60 日留存、LTV 不进入正式趋势或排名。
- 0 值必须能区分真实 0、缺失、默认值和未成熟。
- 负 LTV/首日值必须能追溯到订单、提现、奖励、回滚或净收益构成。
- 渠道、端、版本、分包渠道和归因媒体筛选后，新增人数、付费人数、TX 用户数可与明细汇总对账。
- 关键指标按新增人数加权与按 cohort 简单平均的差异需要可解释。
- 新包版本发布后至少观察 7 日留存、付费率、TC 比、TX 率和数据延迟；成熟 LTV 在 D30/D60 再复核。
