# GM Lifecycle Pool v2 (Joint) 迁移至起源平台实施方案（V2.0）

> 在起源报表集市建立5张独立只读报表。默认按查询时间范围汇总，用户点击查询后执行；GM修改能力不迁移。

## 一页结论

| 项目 | 确定方案 |
|---|---|
| 报表数量 | 5张独立报表 |
| 默认统计 | 查询期汇总；可切换按日明细 |
| 必备筛选 | 日期范围、软件版本、包体、分包渠道、归因媒体、归因渠道 |
| 口径 | 沿用GM原指标算法；比例与人均从累计分子/分母重算 |
| 权限 | 起源只读；GM修改能力不迁移 |
| 触发 | 仅按需手动触发；收到日期范围与更新要求后由用户点击查询，不创建定时任务 |

## 查询期汇总原则

| 类型 | 规则 |
|---|---|
| 求和 | 下注额、金额、盈利、次数在查询范围内直接求和。 |
| 查询期去重 | 人数按原始指标去重键在查询范围内去重，不把每日人数直接相加。 |
| 累计分子/累计分母 | RTP、TC比、流充比、折损系数等按原指标的累计分子和累计分母重新计算，不平均每日百分比。 |
| 原权重重算 | 预期RTP等配置型比率按原指标权重重算，通常以对应下注额加权。 |
| 派生重算 | 人均、占比和差距使用查询期累计值按原公式重新计算。 |
| 分组维度 | 查询期汇总模式隐藏日期；按日明细模式增加日期分组。 |

## 实施规则

- 5张报表是5个独立入口和独立权限对象，但共用同一套筛选字典、指标语义层和查询服务。
- 默认统计方式为查询期汇总；按日明细只用于趋势、追溯和兼容在线结果文档导出。
- 比例、人均、占比和RTP必须从累计分子/分母重算，不得平均每日或行级结果。
- 软件版本、包体和渠道必须来自事件发生时维度；无法还原的历史数据标记为不可筛选或推断，禁止伪造。
- 旧GM聚合接口缺少新增维度，实施必须从更细粒度事实重算；P0口径版本固定为gm_joint_v1。
- 起源首期只读；GM的修改、盈利调整和扣除能力保留在GM，并继续执行权限与审计。
- 仅允许用户按需手动触发：用户给出日期范围和更新要求、设置条件并点击查询后才执行；不因筛选变化自动触发长查询，不创建任何Codex定时任务或后台自动调度。

## 验收清单

- 起源报表集市准确出现5张独立报表，名称与本合同完全一致。
- 任一报表可一次查询起止日期，并按版本、包体、分包渠道、归因媒体和归因渠道筛选。
- 查询期汇总模式不按日期拆行；明细维度分别为无、生命周期×游戏、游戏、生命周期、生命周期。
- 5张报表的显示字段、顺序、数值格式与最终在线结果文档对应。
- SUM、DISTINCT、RATIO_OF_SUMS、WEIGHTED、DERIVED五类聚合均通过单元和对账测试。
- 2026-07-27至2026-08-10金标区间逐表通过金额、人数、RTP及跨表勾稽校验。
- 零分母显示为空值或N/A，不出现Infinity%、NaN或将缺失日期填0。
- 查询结果回显筛选条件、查询时间、数据更新时间、口径版本、查询ID和数据状态。
- Lark兼容导出保留5个同名Sheet，并支持按日明细；页面与导出数值一致。
- GM写操作未迁入起源，只读权限、导出权限和日志审计通过测试。
