# 风控数值与机器人机制拆解

> 本文基于飞书知识库“04_风控数值与机器人”目录及其当前可读取的子页面整理。**唯一包含明确数值的页面自带“历史参考，当前有效性待核”声明；机器人相关页面当前仅能确认主题目录，尚无可验证正文。**因此本文用于沉淀资料、提出数据验证与研发补证要求，不能直接作为线上风控、奖池或机器人策略执行依据。

## 1. 结论摘要

| 结论 | 证据状态 | 处理原则 |
|---|---|---|
| 存在“个人盈利关联生命周期奖池”的历史数值资料 | 已验证，历史参考 | 保留数值和原文出处；不得默认视为现网配置 |
| 历史资料以万分比维护生命周期系数 | 已验证，公式未提供 | 可表达相对系数，不推断其参与结算、赔率或风控阈值的具体方式 |
| 机器人与匹配包含匹配策略、多人匹配、结算换牌、展示优化等主题 | 仅目录已验证 | 必须取得正文、版本和实际配置后才能分析机制或公平性影响 |
| 当前生产规则、命中条件、适用游戏、配置版本和责任人 | 待补证 | P0：由风控/游戏服务端导出带生效状态的配置快照并留存版本 |

当前最大风险不是“没有数值”，而是**历史资料、策略说明和当前生产配置尚未建立可追溯映射**。在此状态下，把历史系数或机器人主题直接用于 RTP、用户盈亏、留存或合规结论，会产生错误归因。

## 3. 已验证的历史数值：生命周期系数

### 3.1 原始资料元信息

来源页面显示：

- 原始路径：`产品文档 / 安卓新包 / 1.0.9`
- 创建日期：2024-01-13
- 迁移日期：2026-08-04
- 资料状态：历史参考，当前有效性待核
- 描述：个人盈利控制中添加“生命周期系数”（万分比）

### 3.2 历史配置表

| 生命周期天 | 系数（万分比） | 仅作数学换算的相对系数 |
|---:|---:|---:|
| 1 | 10,000 | 1.00 |
| 2 | 12,000 | 1.20 |
| 3 | 11,000 | 1.10 |
| 4 | 10,000 | 1.00 |
| 5 | 10,000 | 1.00 |
| 6 | 10,000 | 1.00 |
| 7 | 10,500 | 1.05 |
| 8 | 11,000 | 1.10 |

若该字段在某个公式中以 `生命周期系数 / 10,000` 直接作为乘数，则第 2 天相对基准为 `+20%`，第 3/8 天为 `+10%`，第 7 天为 `+5%`。**这是万分比的数学换算，不是对实际控制力度、用户收益、RTP、胜率或奖池概率的结论。**来源未说明：

- 该系数作用于哪一个目标值或阈值；
- 是否仅适用于个人盈利控制，还是会影响奖池、匹配、返奖或其他配置；
- 适用的游戏、玩法、用户分层、地区、包和版本；
- 命中时机、优先级、兜底规则和实验分流；
- 是否已上线、何时生效、是否已经废弃。

因此，任何“生命周期系数导致 RTP / 用户盈亏变化”的判断，均须先完成配置快照与事实数据关联验证。

## 4. 奖池与 RTP：应如何还原为可审计规则

`01_奖池水位_RTP` 下可见的主题包括：个人盈利关联生命周期奖池、多维度细分奖池-游戏盈利控制奖池、奖池后台优化、奖池后台分周期展示新增用户数据、奖池根据状态和用户类型执行分类控制、新生命周期奖池后台、游戏基础数据、游戏盈利奖池、羊毛党不计生命周期奖池、老包生命周期奖池等。

这些标题显示设计至少涉及“生命周期、用户类型、游戏维度、奖池状态、新老包和疑似羊毛党排除”等分层方向；但标题不等于规则。建议将每条生效规则统一成可审计配置，而非散落在后台页面或历史文档中。

| 配置字段 | 要求 | 用途 |
|---|---|---|
| `rule_id`、`rule_name`、`config_version` | 必填且不可覆盖历史版本 | 规则唯一识别与回溯 |
| `status`、`effective_from`、`effective_to` | 必填 | 区分草稿、灰度、生效、下线和历史参考 |
| `game_id`、`game_type`、`play_id`、`mode_id` | 按适用范围必填 | 防止跨游戏错误套用 |
| `user_segment`、`lifecycle_day_from/to` | 明确定义与版本 | 校验用户分层和生命周期命中 |
| `coefficient_permyriad`、`formula_name`、`target_metric` | 必填 | 说明数值、公式及其作用对象 |
| `priority`、`fallback_rule_id`、`experiment_id` | 条件必填 | 处理多规则叠加、兜底和 AB 实验 |
| `config_source`、`owner`、`approval_ticket`、`updated_at` | 必填 | 建立配置来源、责任与审批链路 |

### 4.1 需要建立的事实—配置对账

以下为目标查询结构；表名和字段须由 BigQuery / 游戏服务端实际映射，不能直接执行。

```sql
-- 验证生命周期规则是否存在可观察的业务差异：
-- 事实数据必须按服务端结算时间和实际生效的 config_version 取数。
SELECT
  DATE(server_settled_at) AS target_day,
  lifecycle_day,
  game_id,
  applied_config_version,
  COUNT(DISTINCT user_id) AS users,
  COUNT(DISTINCT round_id) AS rounds,
  SUM(bet_amount) AS bet_amount,
  SUM(reward_amount) AS reward_amount,
  SAFE_DIVIDE(SUM(reward_amount), SUM(bet_amount)) AS actual_rtp
FROM fact_game_round
WHERE server_settled_at >= :start_at
  AND server_settled_at < :end_at
  AND is_test_account = FALSE
GROUP BY 1, 2, 3, 4;
```

验算时还必须同时输出：配置命中率、未命中率、规则切换时刻、完整日标识、机器人占比、异常/退款局占比及样本量。不能只比较两个 RTP 均值后归因于某个系数。

## 5. 机器人与匹配：已确认主题与缺口

`02_机器人与匹配` 当前可见的子主题为：

| 子主题 | 当前正文证据 | 不能据此得出的结论 |
|---|---|---|
| 匹配发展史 | 未获取到正文 | 不能判断历史匹配算法或当前逻辑 |
| 匹配策略调整 | 未获取到正文 | 不能判断排队阈值、优先级或人机比例 |
| 多人游戏匹配逻辑 | 未获取到正文 | 不能判断组局条件或匹配公平性 |
| 机器人相关 | 未获取到正文 | 不能判断机器人投放、等级、行为或标识策略 |
| 翻倍场机器人结算换牌逻辑 | 未获取到正文 | 不能判断是否存在、如何触发或是否仍生效 |
| 规则引导匹配机器人显示优化 | 未获取到正文 | 不能判断展示规则或用户可见性 |

在正文与当前配置缺失时，不应把“机器人”视为单一二元字段。至少需要区分：

- `is_robot`：对局参与者是否是机器人；
- `robot_policy_id` / `match_policy_id`：命中的机器人或匹配策略；
- `match_trace_id`：一次组局的可追溯链路；
- `intervention_reason`：触发人机补位、排队保护或新手保护的原因；
- `bot_skill_tier`：机器人能力档位或策略版本；
- `settlement_policy_version`：结算相关策略的版本；
- `display_flag`：前台是否展示机器人身份或差异化标识。

这些是**建议补齐的观测字段**，并非已确认的现有字段。现有起源 `GAMEEND` 文档仅确认存在 `is_robot` 用户属性；其纳入哪些经营报表、机器人是否影响任何数值或结算，仍需专题确认。

### 5.1 机器人与匹配的最低监控集

```sql
-- 目标口径：按游戏、玩法、版本和策略版本监控人机匹配。
SELECT
  DATE(matched_at) AS target_day,
  game_id,
  mode_id,
  match_policy_id,
  app_version,
  COUNT(*) AS match_count,
  AVG(wait_seconds) AS avg_wait_seconds,
  APPROX_QUANTILES(wait_seconds, 100)[OFFSET(95)] AS p95_wait_seconds,
  SAFE_DIVIDE(COUNTIF(is_robot), COUNT(*)) AS robot_seat_rate,
  COUNT(DISTINCT CASE WHEN is_robot THEN bot_id END) AS active_bot_count
FROM fact_match_participant
WHERE matched_at >= :start_at
  AND matched_at < :end_at
GROUP BY 1, 2, 3, 4, 5;
```

同一监控面板还应显示真人首局/新手/付费/高风险用户分层、人机对局的下注额与真实回报比、取消匹配率、异常断线率和投诉率。所有指标须标注是否剔除测试账号、异常局、退款局与未完整日。

## 7. 回归标准与待确认项

上线、调整或回溯任一数值/机器人策略前，至少满足：

- [ ] 历史资料与当前生产规则有明确状态标识，不以历史网页替代线上配置；
- [ ] 规则值、公式、优先级和生效时间可由版本化配置导出；
- [ ] 实际命中事件可关联到对局、结算和资产流水；
- [ ] RTP、用户盈亏、下注和奖励均以服务端事实数据对账，并剔除未完整日；
- [ ] 人机匹配可按游戏、玩法、版本、策略版本和用户层下钻；
- [ ] 机器人策略调整具备灰度范围、对照组、回滚版本和 7 个完整日观察；
- [ ] 所有用于报表的 `is_robot` 口径说明“是否包含机器人”，禁止静默混算。

当前待确认事项：

1. 2024-01-13 生命周期系数是否仍在生产使用；若在使用，当前版本和完整公式是什么。
2. 生命周期系数究竟作用于个人盈利控制、奖池目标、发奖、匹配还是其他对象。
3. `01_奖池水位_RTP` 中各子主题对应的现网后台、配置表、游戏范围和负责人。
4. 机器人主题正文、现网机器人匹配策略、结算策略及前台展示策略的版本化来源。
5. 起源 `GAMEEND.is_robot` 与游戏服务端机器人标识的字段映射、延迟及报表纳入规则。
