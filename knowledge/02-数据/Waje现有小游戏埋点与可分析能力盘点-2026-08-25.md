# Waje 现有小游戏埋点与可分析能力盘点

> 结论：现有埋点已经可以做“跨小游戏”的入口、参与、局级结果、下注/结算、资产、留存和部分人机/场次分析；但多数小游戏只接入了通用游戏生命周期，**不能直接分析骰点、棋子移动、鱼种命中、转盘格、Slot 滚轴/免费局等玩法机制细节**。对 RTP、结算金额和人机结论必须先通过 `GAMESTART → GAMEEND → BETREWARD → ASSET` 完整性与金额口径校验。

## 1. 使用边界与能力状态

| 状态 | 含义 | 本报告中的使用方式 |
|---|---|---|
| 已验证 | 已在起源平台快照、页面/模块样本或报表目录中确认 | 可作为现有能力描述；业务结论仍需使用完整日和质量门禁 |
| 条件可用 | 事件/字段已存在，但字段完整性、枚举、版本或金额单位尚未审计 | 可设计分析口径与核验 SQL；不能直接作为经营结论 |
| 设计待落地 | 仅在专项设计、需求或配置资料中出现，未完成 Ares/BQ 实测 | 不能写成现网已支持能力 |

本报告使用“新包优先”原则：新包/当前上线产品是业务分析主范围；老包日志只可用于理解历史机制，不能进入新包 KPI、RTP、留存、LTV、支付或风控统计。

## 2. 当前已确认的游戏数据链

```text
页面/模块：PV / PD / MV / MC
        ↓
游戏局：GAMESTART → GAMEEND → BETREWARD → ASSET
        ↓
报表：游戏概况、玩法详情、场次分析、局数分布及留存、收益留存、人机组局详情、TC 比-玩法
```

| 数据层 | 已确认事件/对象 | 可代表的事实 | 关键限制 |
|---|---|---|---|
| 入口与浏览 | `PV`、`PD`、`MV`、`MC`、页面/模块列表 | 页面访问、模块曝光、入口点击、页面停留 | `MC` 的 `page_id/module_id/event_id/action_type` 并非全部已完成强约束 |
| 开局 | `GAMESTART` | 用户进入有效局、开局时间、玩法/场次上下文 | `round_id`、版本、来源和机器人字段仍需实际 schema 核验 |
| 结束 | `GAMEEND` | 局结果、局时长、下注、结算、场次、人数、超时、机器人 | 当前 P0 质量对象；不同统计窗口曾出现约 6.24% 与 31.28% 异常率，不能直接对比趋势 |
| 结算 | `BETREWARD` | 奖励/返奖结果、局级结算关联 | 奖励状态、金额方向、币种和局关联需对账 |
| 资产 | `ASSET` | 资产增加/消耗、账本、奖励、任务或局来源 | 需确认 `ledger_id` 幂等、余额前后、资产类型与单位 |
| 聚合报表 | BQ 游戏分析、玩法数值、经营/经济体系报表 | 渗透、局数、场次、人机、打码、收益留存、TC/付费关联 | 同名非 BQ 报表为旧引擎，逐步废弃；默认筛选的 `No Data` 不能视为无数据 |

## 3. 已有埋点覆盖到哪些具体小游戏

### 3.1 已经有“直接可见证据”的小游戏

| 小游戏/类别 | 已确认的页面或埋点证据 | 可直接做的分析 | 不能直接做的分析 | 状态 |
|---|---|---|---|---|
| Whot / CrazyWhot | `whot 游戏页面`、`whot 结算界面`的页面分析快照；“仅 whot crazywhot”用户分群；通用游戏局链 | 进入/结算页转化、局数、局时长、留存、场次、人机、通用下注/结算 | 出牌牌型、手牌、逐回合策略、规则命中、单张牌效果 | 已验证入口；局级分析条件可用 |
| 捕鱼 | 捕鱼游戏页面、`捕鱼界面-使用道具` 的 `MC`、fish 插件下载 `MV`；通用游戏局链 | 捕鱼入口、道具点击、下载/加载入口、局数、时长、破产/结算及资产关联 | 鱼种、炮台、子弹、命中率、击杀、鱼群/房间水位、逐发收益 | 已验证入口/道具；机制层缺失 |
| 牌桌/组局类小游戏 | `room_id`、`desk_id`、`player_num`、`play_position`、`outtime_count`、`is_robot`、`end_action_state` | 场次参与、2/4 人等人数分布（若玩法上报）、真人/机器人、托管/退出、局时长、胜负/分数 | 匹配排队开始时刻、每个座位身份、真实/机器人座位数、逐步操作 | 条件可用 |
| 倍数/目标类小游戏 | `goal_times`、`bet_times`、`bet_count`、`times_settlement`、`refund_num`、`cash_settlement` | 倍数选择、目标倍数分布、下注次数、退款、结算倍数、收益分布 | 每次 Cash Out、逐笔下注尝试/拒绝、概率档位或风控命中 | 条件可用 |

### 3.2 当前游戏供给可纳入通用分析，但尚未逐游戏验收

新包资料中反复出现 TaDa、Aviator、Keno、Limbo、Color Dice、CoinFlip、五张牌、21 点、体彩、金币场和外接 Slots。它们可以在建立稳定游戏维表后复用通用局链分析，但“游戏名称出现于配置/变更日志”不等于每一个游戏已完成埋点字段验收。

| 游戏/玩法族 | 可复用的通用能力 | 需要补证的最小字段 |
|---|---|---|
| Aviator、Limbo、Color Dice、CoinFlip 等概率/倍率玩法 | 参与、有效局、下注、结算、局时长、留存、版本/包对比 | `game_id`、`play_id`、下注/返奖金额、`round_id`、规则/配置版本 |
| Keno、体彩等选号/开奖玩法 | 进入、有效局、下注与最终结算、留存 | `bet_id`、选项/号码、下注状态、开奖/撤单/退款、最终结算状态 |
| TaDa、外接 Slots | 入口、进局、有效局、资产流转、游戏间迁移 | 供应商、`game_id`、游戏加载/ready、Spin/Bonus/Free Game 等机制事件 |
| 五张牌、21 点等牌类 | 场次、人数、局时长、回合数、分数/结算、托管 | 牌局阶段、操作、手牌/牌型、决策、座位级身份 |

### 3.3 专项设计不应误认为现网能力

| 专项 | 已有设计能力 | 当前证据状态 |
|---|---|---|
| 内嵌 Coin Ludo | 匹配、房间、局、2/4 人、真人/机器人、托管、重连、Coin RTP、Extra Chip、Coin→真金回流 | `implementation-design`；Ares 页面/模块 ID 与服务端/BQ schema 仍待实测 |
| 体彩小游戏 | 投注 ID、选项、有效投注、结算、退款、RTP 与看板口径 | 数据统计与口径方案；非现网字段审计结果 |
| H5 页面性能 | `H5_SESSION_START`、`H5_NAVIGATION_PERF`、游戏 ready、错误、网络恢复等 | 需求/字段已设计；10 个专属元事件尚未创建，自动 Web 事件当前接近 0 |

## 4. 目前支持的分析层面

| 分析层面 | 可以回答的问题 | 核心事件/对象 | 成熟度 |
|---|---|---|---|
| 游戏供给与入口 | 哪些游戏被看到、被点击、从哪个页面/模块进入 | `PV/PD/MV/MC`、`page_id/module_id/element_id/play_id` | 已验证，但需统一元素语义 |
| 游戏参与漏斗 | 入口点击后是否开局、是否完局、在哪一步流失 | `MC → GAMESTART → GAMEEND` | 条件可用；需补 session/round 链路完整率 |
| 局级体验 | 局数、局时长、正常结束/退出/超时、托管、破产 | `GAMEEND` 的 `game_time/status/end_action_state/outtime_count/broke_num` | 条件可用；GAMEEND 质量 P0 |
| 场次与人机 | 不同玩法/模式/房间的玩家数、机器人参与、真人对战率、胜率 | `room_id/mode_id/player_num/is_robot/score`，场次分析报表 | 条件可用；座位级/匹配阶段字段不足 |
| 下注与结算 | 下注额、倍数、退款、结算、服务费、局级收益 | `bet_num/bet_times/goal_times/refund_num/cash_settlement/service_charge/BETREWARD` | 条件可用；币种、最小单位、正负方向待统一 |
| 资产与经济 | 破产、赠送、资产获得/消耗、奖励成本、局到账本对账 | `ASSET/GETITEM/USEITEM/RECEIVETASK/FINISHTASK` | 条件可用；账本幂等和资产字典待审计 |
| RTP 与概率健康 | 实际回报、玩法/房间/版本/规则的回报异常 | `GAMESTART → GAMEEND → BETREWARD → ASSET` | 未认证；必须完成金额口径、退款规则与链路对账后才可发布 |
| 留存与价值 | 局数分布、玩法留存、收益留存、首充/TC 后续表现 | 游戏概况、局数分布及留存、收益留存、TC 生命周期报表 | 已有报表；需完整日、成熟 cohort 与新包筛选 |
| 风险与异常 | 设备重复、玩法重合、羊毛/破产/退款/异常局 | BQ 设备重复率、玩法重合度、经济体系报表、资产/订单事件 | 条件可用；不能把风险推断当规则命中事实 |

## 5. 可拆分的分析维度

### 5.1 游戏与规则维度

`game_type`、`game_id`（待统一游戏字典）、`play_id`、`mode_id`、`room_id`、`desk_id`、`battle_id`、`cur_circle`、`play_position`、游戏供应商、自研/外接、规则/配置版本、上线/下线/恢复窗口。

### 5.2 用户、对局与人机维度

`user_id`、`uuid`、账号/注册方式、生命周期、首局/首充状态、`unique_id`、`unique_id_bar`、`player_num`、`is_robot`、`end_action_state`、托管/取消托管、破产次数。

### 5.3 经济与结算维度

`bet_num`、`bet_count`、`goal_times`、`bet_times`、`times_settlement`、`cash_settlement`、`refund_num`、`service_charge`、`score`、`asset_type`、资产流向、订单/账本/奖励来源。

### 5.4 流量与运营维度

页面、模块、元素 ID/名称/内容、曝光/点击、入口来源、活动、任务、分包、渠道、归因媒体、国家、平台、APP/H5 版本和热更新版本。

### 5.5 时间与质量维度

业务日期、完整日标记、客户端/服务端/入库时间、`event_uid`、重试/去重、来源、schema 版本、接收量、入库量、异常率、延迟。

## 6. 当前不能可靠回答的问题

1. 单款小游戏的细粒度机制：逐骰子、逐棋子、每张牌、鱼种/炮台/子弹、Slot 滚轴/Bonus、转盘格与概率命中。
2. 单款游戏的认证 RTP：没有完成局→结算→账本链路、金额单位和退款规则校验前，`现金结算 ÷ 下注` 不能直接视为真实 RTP。
3. 匹配体验的根因：现有字段可描述部分局后结果，但缺 `match_id`、匹配开始/结束、座位级真人/机器人和取消原因的通用现网验证。
4. H5 的加载/卡顿/白屏导致的进局损失：`PAGELOAD/AUTOPV/AUTOPD/AUTOMC` 当前量接近 0，H5 性能专属事件尚未落地。
5. 新旧包、配置版本或供应商的严格因果比较：缺稳定游戏字典、版本生效时间、配置命中记录和完整观察窗口时，只能做描述性对比。

## 7. 最小补齐优先级

| 优先级 | 补齐项 | 直接解锁的分析 |
|---|---|---|
| P0 | 修复 `GAMEEND` 必填、类型、枚举、版本/来源；建立 `GAMESTART → GAMEEND → BETREWARD → ASSET` 对账 | 有效局、局级收益、RTP、资产和结算可信度 |
| P0 | 建立游戏维表：`game_id → 名称/类型/玩法/模式/房间/供应商/资产/包/上线窗口` | 每款小游戏的独立看板、跨游戏比较与版本分析 |
| P1 | 为具体玩法增加机制事件：选号、Cash Out、鱼种/炮台、牌局阶段、Spin/Bonus 等 | 玩法机制、难度、概率体验与异常机制排查 |
| P1 | 对多人小游戏补 `match_id`、座位身份、匹配等待、取消、重连与托管原因 | 2/4 人模式、机器人补位、匹配体验与人机策略 |
| P1 | 落地 H5 性能与游戏 ready 事件 | H5 入口→进局→可下注损失、弱网和低端机体验 |
| P2 | 统一金额单位、资产字典与配置命中版本 | 真实 RTP、奖励成本、风控/数值变更效果审计 |
