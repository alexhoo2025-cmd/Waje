# Waje 数据指标、看板映射与研发验收清单

> 本文配套 [[Waje全链路数据需求与埋点设计总表-2026-08-11]] 和 [[Waje埋点事件与属性字典-2026-08-11]] 使用。目标是让产品、数据、研发、运营和 QA 对“看什么、从哪里来、何时可用、如何验收”使用同一套标准。

## 1. 指标认证规则

每个认证指标必须同时登记：

```text
metric_id
metric_name
definition_version
numerator
denominator
grain
dedup_key
timezone
currency/asset_type
source_table/source_event
data_cutoff_at
complete_day_rule
maturity_rule
quality_status
owner
```

指标状态统一使用：

| 状态 | 含义 | 看板行为 |
|---|---|---|
| `certified` | 口径、来源、质量和对账均通过 | 可进入正式经营/产品结论 |
| `provisional` | 口径基本稳定但仍在并行对账 | 可展示，必须带“试运行”标识 |
| `immature` | cohort、生命周期或完整日未成熟 | 显示 `N/A`，禁止显示 0 |
| `blocked` | 数据质量、权限或成本源不满足 | 显示阻断原因，不参与排序和结论 |
| `deprecated` | 旧口径或旧引擎待下线 | 只读历史，不得新增依赖 |

默认时区为 Asia/Hong_Kong，但订单、游戏、生命周期和投放成本的业务日必须由数据负责人确认；同一指标不能在不同报表隐式切换时区。

## 2. 核心指标口径

### 2.1 用户、留存和新手

| metric_id | 指标 | 定义 | 分子 | 分母 | 主要维度 | 认证条件 |
|---|---|---|---|---|---|---|
| `user_dau` | DAU | 选定用户口径下有效活跃用户数 | 日内有效用户去重数 | — | 日期、端、版本、包、渠道 | 明确 `user_id`/设备口径；测试账号排除 |
| `user_new` | 新增用户 | 首次满足注册/首登定义的用户 | 新增用户数 | — | 注册日、端、包、媒体 | 注册和安装分开；来源可追溯 |
| `game_user` | 有效游戏用户 | 发生质量合格有效局的用户 | 有效 `GAMESTART` 用户 | — | 游戏、玩法、版本 | GAMEEND 质量不通过时降级/阻断 |
| `newbie_first_game_rate` | 新手首局率 | 新增用户在窗口完成首个有效局 | 完成首局的新增用户 | 新增用户 | cohort、端、包 | 首局定义和窗口固定 |
| `retention_d1/d7` | D1/D7 留存 | cohort 用户在 N 日再次有效活跃 | 第 N 日活跃 cohort 用户 | cohort 起始用户 | cohort、端、渠道 | cohort 达到 N 日后才认证 |
| `task_complete_rate` | 新手任务完成率 | 目标任务完成用户/进入任务用户 | 完成任务用户 | 任务曝光/领取用户 | 任务、版本、场景 | 任务 ID、版本、奖励可关联 |
| `first_pay_rate` | 首充率 | cohort 用户在窗口完成首个成功支付 | 首充成功用户 | cohort 用户 | cohort、包、媒体 | 服务端支付成功且扣除冲正 |

### 2.2 付费、资产与提现

| metric_id | 指标 | 定义 | 关键事实源 | 注意事项 |
|---|---|---|---|---|
| `pay_amount` | 支付金额 | 成功支付金额扣除退款/冲正 | 支付订单 + 账务 | 币种和业务日固定 |
| `pay_rate` | 付费率 | 成功付费用户/认证活跃用户 | 订单 + 用户事实 | 分母不能隐式替换为登录用户 |
| `arpu` | ARPU | 认证收入/活跃用户 | 收入/用户 | 收入定义必须写明是否含赠送 |
| `arppu` | ARPPU | 认证收入/付费用户 | 收入/付费用户 | 付费用户为成功支付去重用户 |
| `repay_rate` | 复充率 | 首充后窗口内再次成功支付用户/首充用户 | 订单 | D1/D7 cohort 成熟后比较 |
| `withdraw_success_rate` | 提现成功率 | 成功 TX 笔数或用户数/提交笔数或用户数 | TX 状态机 | 必须同时展示笔数和用户数 |
| `reward_cost` | 奖励成本 | 运营奖励/资产账本实际发放额 | 奖励账本 + ASSET | 发放、领取、使用分开 |
| `asset_reconciliation_diff` | 资产对账差异 | 支付/奖励/下注/返奖与资产流水差额 | 订单、游戏、资产 | 超阈值阻断经营结论 |

### 2.3 游戏、RTP 和生命周期

| metric_id | 指标 | 定义 | 关键事实源 | 质量门槛 |
|---|---|---|---|---|
| `round_start` | 开局数 | 质量合格 `GAMESTART` 局数 | 服务端/游戏事件 | `round_id` 唯一 |
| `round_end` | 完局数 | 质量合格 `GAMEEND` 局数 | 服务端结算 | GAMEEND 异常率达标 |
| `round_completion_rate` | 完局率 | 完局数/开局数 | GAMESTART + GAMEEND | 同一玩法/窗口/来源 |
| `bet_amount_base` | 基础下注额 | 基础口径下注金额 | 游戏/账务事实 | 与完全下注额区分 |
| `bet_amount_full` | 完全下注额 | 完全口径下注金额 | 游戏/账务事实 | 公式由数值/财务确认 |
| `real_rtp_base` | 基础真实回报比 | 基础实际回收/基础下注 | 结算事实 | 资金口径和币种固定 |
| `real_rtp_full` | 完全真实回报比 | 完全实际回收/完全下注 | 结算事实 | 与 GM 报表对账 |
| `expected_rtp_base/full` | 预期回报比 | 数值配置/理论概率对应回报 | MySQL 配置 + 游戏模型 | 不可与实测 RTP 混用 |
| `game_lifecycle_profit` | 生命周期收益 | cohort 在生命周期内累计净收益/收入 | 生命周期事实 | 日期成熟、成本和 TX 完整 |
| `tc_ratio` | TC 比 | 平台正式公式 | TC 认证指标层 | 公式未确认前显示试运行 |
| `win_loss_rate` | 胜负率 | 按玩法定义的用户/局胜负比例 | GAMEEND/结算 | 需区分用户胜负和局胜负 |

> 基础下注额与完全下注额不能按“数值更大/更小”直接解释。两者必须在指标字典中声明是否包含追加下注、全额下注、特殊模式、返还或其他金额项，再与 GM 和起源同口径对账。

## 4. 全局筛选器

所有正式看板应提供或明确说明以下筛选器：

| 筛选 | 规则 |
|---|---|
| 日期范围 | 支持单日/多日；显示数据截止时间和是否完整日 |
| 游戏/玩法/模式 | `game_id`、`play_id`、`mode_id`、`room_id` 从 MySQL 维表取展示名 |
| 生命周期天数 | `lifecycle_day`；D1/D7/D30 未成熟显示 `N/A` |
| 用户 cohort | 注册日、首充日、首局日等必须显式选择 |
| 端与版本 | H5、Android、iOS、APP/Web 版本、热更新版本 |
| 包与渠道 | 包名、一级渠道、分包渠道、归因媒体、活动/创意 |
| 用户类型 | 新/老、付费/未付费、机器人/真人、风险状态 |
| 资产/币种 | 真金、Coin、奖励、NGN 等；禁止隐式混合 |
| 引擎来源 | BQ/旧引擎；迁移对账时必须可切换或并列 |
| 数据状态 | `certified`、`provisional`、`immature`、`blocked` |

## 5. 事件级数据质量监控

### 5.1 通用监控指标

| 指标 | 公式 | 必须切分 |
|---|---|---|
| `received_count` | 原始接收事件数 | 日期/小时、事件、来源 |
| `ingested_count` | 标准化成功入库事件数 | 事件、来源、版本、包 |
| `abnormal_count` | 校验异常事件数 | 错误类型、字段、事件 |
| `discarded_count` | 被抛弃事件数 | 事件、来源、错误 |
| `ingest_rate` | 入库/接收 | 事件、版本、包、玩法 |
| `abnormal_rate` | 异常/接收 | 事件、错误字段、来源 |
| `duplicate_rate` | 重复/接收 | 事件、幂等键、重试 |
| `null_required_rate` | 必填缺失/接收 | 字段、版本、玩法 |
| `enum_invalid_rate` | 未知枚举/接收 | 字段、值、版本 |
| `type_invalid_rate` | 类型错误/接收 | 字段、来源、版本 |
| `late_arrival_rate` | 迟到/接收 | 业务日、来源、版本 |
| `p50/p95/p99_ingest_delay` | `received_at - event_time_server` 分位数 | 事件、来源、小时 |

### 5.2 初始告警门槛

门槛为缺少历史稳定基线时的初始建议，运行 7 个完整日后按 P95/P99 调整。

| 事件/指标 | 预警 | P1/P0 | 处理 |
|---|---:|---:|---|
| `GAMEEND` 异常率 | >1% | >3% 为 P1；结算事实不可用为 P0 | 阻断 RTP/局数结论，按字段/版本/来源排查 |
| 核心事件入库率 | <99.5% | <99% 为 P1 | 核对原始/标准化/隔离三层 |
| 必填缺失率 | >0.1% | 回放非 0 即不通过 | 进入隔离并修复构造器/解析器 |
| 未知枚举率 | >0.1% | 新版本首次出现即阻断 | 保留原值，补字典和兼容逻辑 |
| 金融对账差异 | >0.1% | 任意不可解释差异为 P0 | 支付、资产、TX 联合对账 |
| 新版本核心事件量 | 较基线下降 >20% | >30% 为 P1 | 结合发布窗口和流量变化判断 |
| 迟到事件率 | 超过历史 P95 | 影响业务日则 P1 | 检查时区、重试、补发和分区 |

## 6. 验收 SQL / 伪代码

以下为 BigQuery 风格模板，表名和字段需由数据开发替换为实际 schema。SQL 不保存或输出账号密码、Cookie、Token 或完整个人敏感信息。

### 6.1 `GAMEEND` 字段质量

```sql
WITH raw AS (
  SELECT
    DATE(received_at) AS dt,
    ingest_id,
    event_uid,
    source,
    app_version,
    package_name,
    game_type,
    game_id,
    play_id,
    mode_id,
    room_id,
    unique_id,
    status,
    end_action_state,
    bet_num,
    cash_settlement,
    received_at,
    event_time_server
  FROM `<project>.<dataset>.<normalized_gameend>`
  WHERE event_name = 'GAMEEND'
    AND received_at >= @start_ts
    AND received_at < @end_ts
), checks AS (
  SELECT
    *,
    (
      event_uid IS NULL
      OR unique_id IS NULL
      OR game_type IS NULL
      OR play_id IS NULL
      OR status IS NULL
      OR end_action_state IS NULL
      OR bet_num < 0
      OR cash_settlement < 0
    ) AS invalid_basic
  FROM raw
)
SELECT
  dt,
  COUNT(*) AS received_count,
  COUNTIF(invalid_basic) AS abnormal_count,
  SAFE_DIVIDE(COUNTIF(invalid_basic), COUNT(*)) AS abnormal_rate,
  COUNT(DISTINCT unique_id) AS unique_round_count,
  COUNTIF(event_time_server > received_at) AS future_event_time_count
FROM checks
GROUP BY dt
ORDER BY dt;
```

正式实现必须用“玩法 × 字段必填矩阵”替换统一硬编码，不能把不适用字段强行要求为 0。

### 6.2 按版本、来源和包定位

```sql
SELECT
  DATE(received_at) AS dt,
  COALESCE(source, 'unknown') AS source,
  COALESCE(app_version, 'unknown') AS app_version,
  COALESCE(package_name, 'unknown') AS package_name,
  game_type,
  COUNT(*) AS received_count,
  COUNTIF(error_type IS NOT NULL) AS abnormal_count,
  SAFE_DIVIDE(COUNTIF(error_type IS NOT NULL), COUNT(*)) AS abnormal_rate,
  COUNTIF(error_type = 'missing_required') AS missing_required_count,
  COUNTIF(error_type = 'type_error') AS type_error_count,
  COUNTIF(error_type = 'enum_error') AS enum_error_count
FROM `<project>.<dataset>.<gameend_quality>`
WHERE event_name = 'GAMEEND'
  AND received_at >= @start_ts
  AND received_at < @end_ts
GROUP BY 1, 2, 3, 4, 5
HAVING COUNT(*) >= 50
ORDER BY abnormal_rate DESC, received_count DESC;
```

### 6.3 接收、入库和隔离对账

```sql
WITH received AS (
  SELECT DISTINCT ingest_id
  FROM `<project>.<dataset>.<raw_event>`
  WHERE event_name = 'GAMEEND'
    AND received_at >= @start_ts AND received_at < @end_ts
), persisted AS (
  SELECT DISTINCT ingest_id
  FROM `<project>.<dataset>.<normalized_gameend>`
  WHERE event_name = 'GAMEEND'
    AND normalized_at >= @start_ts AND normalized_at < @end_ts
), quarantined AS (
  SELECT DISTINCT ingest_id
  FROM `<project>.<dataset>.<event_quarantine>`
  WHERE event_name = 'GAMEEND'
    AND received_at >= @start_ts AND received_at < @end_ts
)
SELECT
  (SELECT COUNT(*) FROM received) AS received_count,
  (SELECT COUNT(*) FROM persisted) AS persisted_count,
  (SELECT COUNT(*) FROM quarantined) AS quarantined_count,
  SAFE_DIVIDE((SELECT COUNT(*) FROM persisted), (SELECT COUNT(*) FROM received)) AS persist_rate,
  SAFE_DIVIDE((SELECT COUNT(*) FROM quarantined), (SELECT COUNT(*) FROM received)) AS quarantine_rate;
```

验收要求：`received = persisted + quarantined + 明确可解释的丢弃`。页面显示“抛弃 0”不能替代三层对账。

### 6.4 游戏链路完整性

```sql
WITH starts AS (
  SELECT DISTINCT unique_id
  FROM `<project>.<dataset>.<game_start>`
  WHERE event_date BETWEEN @start_date AND @end_date
), ends AS (
  SELECT DISTINCT unique_id
  FROM `<project>.<dataset>.<game_end>`
  WHERE event_date BETWEEN @start_date AND @end_date
), rewards AS (
  SELECT DISTINCT unique_id
  FROM `<project>.<dataset>.<bet_reward>`
  WHERE event_date BETWEEN @start_date AND @end_date
)
SELECT
  COUNT(*) AS started_rounds,
  COUNTIF(e.unique_id IS NOT NULL) AS ended_rounds,
  COUNTIF(r.unique_id IS NOT NULL) AS rewarded_rounds,
  SAFE_DIVIDE(COUNTIF(e.unique_id IS NOT NULL), COUNT(*)) AS end_coverage,
  SAFE_DIVIDE(COUNTIF(r.unique_id IS NOT NULL), COUNT(*)) AS reward_coverage
FROM starts s
LEFT JOIN ends e USING (unique_id)
LEFT JOIN rewards r USING (unique_id);
```

### 6.5 支付、奖励和资产对账

```sql
SELECT
  order_id,
  payment_success_amount,
  asset_increase_amount,
  payment_success_amount - asset_increase_amount AS diff,
  currency,
  asset_type
FROM `<project>.<dataset>.<payment_success>` p
JOIN `<project>.<dataset>.<asset_ledger>` a USING (order_id)
WHERE ABS(payment_success_amount - asset_increase_amount) > @tolerance;
```

### 6.6 留存成熟窗口

```sql
SELECT
  cohort_date,
  lifecycle_day,
  COUNT(DISTINCT CASE WHEN is_active = 1 THEN user_id END) AS retained_users,
  COUNT(DISTINCT user_id) AS cohort_users,
  SAFE_DIVIDE(
    COUNT(DISTINCT CASE WHEN is_active = 1 THEN user_id END),
    COUNT(DISTINCT user_id)
  ) AS retention_rate,
  CASE
    WHEN DATE_DIFF(CURRENT_DATE(@timezone), cohort_date, DAY) >= lifecycle_day
    THEN 'mature'
    ELSE 'immature'
  END AS maturity_status
FROM `<project>.<dataset>.<user_lifecycle_daily>`
GROUP BY cohort_date, lifecycle_day;
```

未成熟 cohort 的 `retention_rate` 在语义层输出 `NULL/N/A`，不输出 0。

## 7. BigQuery/MySQL/Ares 映射

| 内容 | MySQL 配置/元数据 | BigQuery 事实/指标 | 起源/Ares 展示 |
|---|---|---|---|
| 事件定义 | 事件名、版本、属性、状态、owner | 原始事件、标准化事件、质量结果 | 元事件/事件属性/质量 |
| 游戏维度 | 游戏、玩法、模式、场次字典 | 局、下注、返奖、RTP事实 | 游戏与 RTP |
| 版本/渠道 | 包、版本、渠道、媒体字典 | 用户、事件、订单按维度落地 | 版本/新包/投放 |
| 权限 | 角色、数据范围、字段脱敏、报表权限 | 行/列权限所需标签 | 各看板权限 |
| 指标公式 | 公式版本、显示名、过滤默认值 | 认证计算结果 | 语义层/看板 |
| 汇率/币种 | 目标货币、汇率、生效时间 | 统一金额与原币金额 | 收入、RTP、TC、TX |

BQ 迁移期间必须保留 `engine_source`、`data_cutoff_at`、`definition_version`，不允许把 BQ 与旧引擎结果直接 UNION 后当成同一口径。

## 8. 研发验收清单

### 8.1 埋点契约

- [ ] 每个新增事件有编码、展示名、版本、触发时机、来源、平台、owner。
- [ ] 每个属性有类型、必填性、空值策略、枚举/维表、示例值和生效版本。
- [ ] 事件唯一键、重试、去重、延迟和跨日规则已实现。
- [ ] 用户 ID、设备 ID、起源 ID 的优先级和映射已确认。
- [ ] 金额字段同时包含金额、币种、资产类型、最小单位和正负方向。
- [ ] `GAMEEND` 的玩法矩阵覆盖所有目标游戏和退出/失败路径。
- [ ] `ORDER` 已拆分订单创建、支付成功、失败、退款和冲正。
- [ ] 金融事实由服务端产生，客户端事件只做行为和体验诊断。

### 8.2 数据质量

- [ ] 原始、标准化、隔离三层可按 `ingest_id/event_uid` 对账。
- [ ] 事件质量可按日期、小时、版本、热更新、包、渠道、玩法、来源和错误字段切分。
- [ ] `GAMEEND` 异常率连续 24 小时低于 0.5%，且主要切片不高于 1%。
- [ ] 核心事件入库率达到 99.5% 以上；异常不静默丢弃。
- [ ] 未知枚举、类型错误、必填缺失均可导出错误字段和原始值样本。
- [ ] `duplicate_rate`、`late_arrival_rate`、P95 入库延迟有监控和负责人。

### 8.3 报表和指标

- [ ] 每个卡片显示数据截止时间、完整日、成熟状态、质量状态和口径版本。
- [ ] 日期、游戏、玩法、生命周期天数、版本、包、渠道、归因媒体、资产和引擎来源筛选可用。
- [ ] 筛选上下文在下钻、导出和分享时保持一致，并写入导出元信息。
- [ ] BQ 与旧引擎至少并行对账 7–14 个完整日，核心指标差异有解释。
- [ ] 留存、LTV、ROI、TC、RTP 和支付指标均能回到事实源和字段字典。
- [ ] 页面、模块和事件的名称变化不会破坏历史 ID 关联。

### 8.4 安全与权限

- [ ] 账号、密码、Cookie、Token 不进入代码、SQL、日志、快照和 Markdown。
- [ ] 用户明细、KYC、银行和风险字段按角色最小化授权并脱敏。
- [ ] 受限数据只通过授权数据集/Metabase 连接访问；导出、分享和下载留审计。
- [ ] 研发、产品、运营、财务、客服、投放的行列权限和导出权限已验收。

## 9. 回归标准

### 发布前

1. 客户端/服务端 schema fixture 通过必填、类型、枚举和版本兼容测试。
2. 正常结束、退出、失败、断线、超时、重试、补发和跨日场景全部产生可追踪事件。
3. 支付成功/失败、退款/冲正、TX 审核、风险拦截、奖励发放和资产流水可对账。
4. 页面/模块/事件链路可从 `PV/MV/MC` 下钻到业务结果。
5. 通过埋点测试查询到事件，并能在数据质量页看到接收/入库/异常状态。

### 灰度 24 小时

- 核心事件异常率、入库率、重复率和延迟没有超过门槛；
- 新版本与旧版本分布可解释；
- `GAMESTART → GAMEEND → BETREWARD → ASSET` 链路可对账；
- 订单/资产、TX 和奖励没有不可解释差异；
- 关键看板无 `NaN`、异常 0 或时间窗错位。

### 稳定 7 日

- 7 个完整业务日质量达标；
- D1/D7 及生命周期指标只在成熟 cohort 展示；
- BQ 与旧引擎并行结果完成签字；
- 旧字段/旧引擎仍有明确下线时间和回滚方案；
- 产品、数据、研发、QA、运营共同确认数据可用于决策。
