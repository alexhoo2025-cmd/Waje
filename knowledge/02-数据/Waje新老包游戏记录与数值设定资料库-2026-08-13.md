### 4.4 新包数值与风控的分析原则

新包日志显示，游戏回报、KYC、反刷、首充、TX 审核与支付体验常在相近时间段共同调整。任何“某数值改变导致 RTP、留存或收入变化”的结论都必须先排除同日发布、游戏上下架、运营活动、支付故障和埋点变化。

建议按下列顺序验证：

1. 从服务端配置导出 `rule_id`、`config_version`、生效区间、游戏/用户/包适用范围与旧新值。
2. 用完整日数据按 `package_name × platform × game_id × play_id × config_version` 拆分下注、奖励、真实 RTP、人数和局数。
3. 将 KYC/反刷规则命中与注册、首充、支付成功、TX 审核、投诉和异常账户分开观察。
4. 将同日游戏上下架、版本发布、支付渠道故障、活动触达标为混杂因素；不能只做简单前后均值比较。

```sql
-- 目标结构：验证新包游戏数值变更；表名和字段需由 BQ 实际映射。
SELECT
  DATE(server_settled_at) AS target_day,
  package_name,
  platform,
  app_version,
  game_id,
  play_id,
  config_version,
  COUNT(DISTINCT user_id) AS users,
  COUNT(DISTINCT round_id) AS rounds,
  SUM(bet_amount) AS bet_amount,
  SUM(reward_amount) AS reward_amount,
  SAFE_DIVIDE(SUM(reward_amount), SUM(bet_amount)) AS actual_rtp
FROM fact_game_round
WHERE package_scope = 'new_current_primary'
  AND is_complete_day = TRUE
GROUP BY 1, 2, 3, 4, 5, 6, 7;
```

## 8. 数据质量、待确认项与回归要求

### 8.1 当前资料限制

- 源表是变更日志，不是配置中心、发布系统或事实数据表；其中“线上数值”不能证明当前仍然生效。
- 新包日期中有两条、老包日期中有一条未带年份，未进入标准化趋势。
- 一行可能混合多个动作，主题标签可重叠，不能按行数替代变更次数、事件量或影响规模。
- 新包 `2023-11-07` 至 `2026-08-12` 的历史记录仍属于新包工作表；不应因日期早而自动转为老包。

### 8.2 P0 补证项

| 优先级 | 需要补齐的事实 | 验收标准 |
|---|---|---|
| P0 | 新包现网数值/风控配置快照 | 有 `rule_id`、`config_version`、旧新值、生效区间、优先级、适用游戏/用户/包和负责人 |
| P0 | 游戏维表 | 所有运营游戏名可映射 `game_id`、供应商、自研/外接、玩法、资产类型与上下线时间 |
| P0 | 配置命中链路 | 对局、支付、TX/KYC 可追溯到规则版本或明确未命中 |
| P0 | 资产与订单对账 | `ORDER/WITHDRAW/AUDIT → ASSET`、`GAMESTART → GAMEEND → BETREWARD → ASSET` 可按业务键关联 |
| P1 | 版本/分包/归因质量 | 新旧版本、H5/Android/iOS、传音/Opera 等包可按统一字段拆分 |
| P1 | 变更日干扰标记 | 发布、游戏上下架、活动、支付故障、数据修复均进入分析日历 |

### 8.3 分析与发布回归标准

- [ ] 新包每个分析数据集明确 `package_scope = new_current_primary`，老包数据集不能参与聚合。
- [ ] 老包只出现在“历史参考/机制演进”章节，图表和指标卡不得混入老包事实。
