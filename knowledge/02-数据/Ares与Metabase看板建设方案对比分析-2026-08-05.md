# Ares 与 Metabase 看板建设方案对比分析

## 技术结论

基于当前数据基础架构，Ares（起源平台）和 Metabase 都可以承载 BigQuery 可视化，但定位不同：

- **Ares 适合作为业务统一入口**：承接现有埋点管理、数据统计、报表集市、权限和业务看板。
- **云主机 Metabase 同时是受控访问与风险隔离层**：除快速制作专题看板、验证指标外，部分业务数据只允许通过此入口访问；它承载最小授权、导出控制和访问审计。
- **推荐采用“双层方案”**：Ares 承担正式业务入口；Metabase 承担受限业务数据访问、风险隔离和敏捷分析。稳定的指标口径必须沉淀到 BigQuery 认证层，不能在两个前台各自维护。

不建议让两个平台分别维护同一指标的 SQL 和口径。统计事实应统一由 BigQuery 提供，MySQL 负责配置与元数据，两个展示平台复用同一套 BigQuery 汇总表或 View。

## 1. 现有数据基础架构与约束

### 1.1 数据职责

| 层级 | 当前职责 | 看板建设要求 |
|---|---|---|
| BigQuery | 新引擎；统计相关数据，包括用户、订单、游戏、下注、派奖、生命周期、RTP 和埋点质量结果 | 作为生产看板主数据源，承载明细事实和汇总 View |
| MySQL | 基础配置、事件定义、指标配置、游戏/版本/渠道字典、权限等系统类信息 | 作为元数据和配置源，不承担大规模统计查询 |
| Impala/非 BQ 旧引擎 | 历史或过渡链路 | 不建议新看板继续依赖，逐步迁移和下线 |
| Ares | 现有数据平台入口、数据统计、用户分析、报表集市、数据管理和业务看板 | 面向业务用户统一访问、权限和发布 |
| Metabase | 云主机上的受控 BI 查询和可视化入口 | 受限业务数据访问、权限控制、风险隔离、专题分析和自助看板 |

### 1.2 已知现状

- Ares 当前已有 `BQ-` 报表，说明平台已经存在 BigQuery 报表接入或嵌入链路。
- Ares 已有“业务看板、公共看板、我的看板、共享分组”等入口，但当前账号看到的业务看板内容为空，可能是未配置或权限不足，不能直接判断为功能不支持。
- 报表集市中 BQ 与非 BQ 版本并列；BQ 使用 BigQuery 新引擎，非 BQ 旧版本后续逐步废弃。
- 目前数据口径仍需治理：完整日、0 值处理、用户去重键、版本/分包渠道/归因媒体、RTP 和生命周期指标定义都不能只依赖页面名称。

## 2. 两种平台的实现方式

### 2.1 Ares 原生看板

```text
MySQL 配置/字典
        ↓ 同步
BigQuery 明细事实 → BigQuery 汇总 View/表 → Ares 业务看板
```

实现步骤：

1. 在 BigQuery 建立统一明细事实层和看板汇总层。
2. 将 MySQL 的事件、指标、游戏、版本、渠道字典同步到 BigQuery 字典表。
3. 在 Ares 中配置数据集、指标、筛选器、图表和看板目录。
4. 通过 Ares 的业务看板或报表集市发布给业务用户。
5. 由 Ares 统一管理菜单、角色、共享分组和访问权限。

适合沉淀经营总览、新包生命周期、游戏 RTP、GAMEEND 数据质量等正式看板。

### 2.2 Metabase 独立看板

```text
MySQL ───────────────┐
                     ├→ Metabase → 图表/问题/仪表盘/订阅
BigQuery 汇总 View ──┘
```

实现步骤：

1. Metabase 连接 BigQuery 和 MySQL。
2. BigQuery 作为主要查询源；MySQL 仅用于配置或辅助字典查询。
3. 在 Metabase 中同步字段、设置字段类型和中文名称。
4. 由业务/分析人员创建问题、图表、筛选器和仪表盘。
5. 通过 Metabase 权限、集合和订阅功能分发。

不建议在 Metabase 中直接跨 MySQL 和 BigQuery 临时关联生产数据。应先把配置同步到 BigQuery，再由 BigQuery 完成关联和统计。

### 2.3 Ares 嵌入 Metabase

```text
BigQuery → Metabase 看板 → Ares iframe/嵌入入口
```

适合 Ares 当前原生看板开发排期较长，但又需要统一从起源平台进入的阶段。缺点是会产生两套平台的用户、权限、看板生命周期和故障排查链路。

## 3. 方案对比

| 维度 | Ares 原生看板 | Metabase 独立看板 | Ares 嵌入 Metabase |
|---|---|---|---|
| 上线速度 | 中，取决于 Ares 是否已有可复用模板 | 快 | 中快 |
| 业务自助配置 | 取决于现有看板编辑器，可能需要研发开放能力 | 较强，业务/分析人员可自行配置 | Metabase 内可配置，但 Ares 侧仍需研发接入 |
| BigQuery 支持 | 已有 BQ 报表，需确认新增数据集/图表能力 | 官方支持，连接直接 | Metabase 直接连接 |
| 权限统一 | 最好，沿用 Ares 账号、角色和菜单 | 云主机入口本身承担部分权限控制与风险隔离，仍需与 Ares/BQ 角色模型对齐 | 两套权限，复杂度最高 |
| 指标治理 | 容易与 Ares 元事件、数据管理统一 | 需要额外维护指标字典 | 两边都要对齐 |
| 自助分析能力 | 取决于 Ares 原生能力 | 强，适合快速探索 | 强，但体验跨平台 |
| 大规模查询 | 由 BigQuery 承担，平台差异小 | 由 BigQuery 承担 | 由 BigQuery 承担 |
| 维护成本 | 初始开发较高，长期统一 | 初始低，但需维护独立平台 | 最高，涉及两套系统 |
| 适合场景 | 正式经营看板、统一入口、权限敏感数据 | 专题分析、指标验证、快速试错 | 过渡期或 Ares 原生能力不足 |
| 主要风险 | Ares 看板能力、权限和开发排期未知 | 口径分散、权限与 Ares 不一致 | 双平台重复配置和故障定位困难 |

## 4. 哪些工作需要研发，哪些业务可以做

### 4.1 必须由研发/数据开发完成

- BigQuery 数据分层、分区、聚合表和生产 View。
- MySQL 配置/字典同步到 BigQuery 的任务或接口。
- 用户、事件、游戏局、订单、下注和派奖事实的统一关联。
- 指标口径实现：下注额、基础回报比、真实回报比、RTP、LTV、留存等。
- 完整日、时区、迟到数据、重复数据和 0 值处理规则。
- GAMEEND 等关键事件的质量监控和回归 SQL。
- BigQuery 成本控制、查询限额、缓存、分区过滤和数据权限。
- Ares 新数据集、新图表类型、跨页筛选器或嵌入能力的开发（如果现有平台不支持）。
- 生产数据发布、版本管理、回滚和指标变更审计。

### 4.2 业务/分析人员可以自行配置

在数据层已经准备好且权限开放后，业务人员可以负责：

- 选择已有数据集和指标。
- 配置日期、游戏、版本、H5/App、分包渠道、归因媒体和生命周期筛选。
- 拖拽图表、调整看板布局和展示顺序。
- 配置业务看板标题、说明和默认筛选条件。
- 创建临时专题分析和游戏对比。
- 配置订阅、导出和固定刷新频率（需平台权限允许）。

业务人员不应自行修改生产 SQL、核心指标公式或权限隔离规则。

## 5. 推荐的落地方案

### 阶段一：建立统一指标底座

研发/数据开发先在 BigQuery 建立：

- `dim_game`：游戏和玩法字典。
- `dim_version_package`：端、版本、包和生效时间。
- `dim_channel_media`：分包渠道和归因媒体。
- `dim_event`：事件、字段、版本和来源定义。
- `ads_business_daily`：经营日汇总。
- `ads_lifecycle_game_daily`：生命周期 × 游戏汇总。
- `ads_game_rtp_daily`：游戏 RTP 日汇总。
- `ads_gameend_quality_daily`：GAMEEND 质量汇总。

所有表都应包含数据截止时间、是否完整日、数据源、更新时间和口径版本。

### 阶段二：Metabase 快速验证

先在 Metabase 连接 BigQuery，快速制作 4 个 MVP 看板：

1. 经营总览。
2. 新包与生命周期。
3. 游戏 RTP。
4. GAMEEND 数据质量。

用 1–2 周验证指标、筛选器、性能、业务使用频率和口径差异。对受限业务数据，业务人员只能经云主机 Metabase 的授权入口访问；仍不建议让 Metabase 直接跨 MySQL 和 BigQuery 临时关联生产明细。

### 阶段三：Ares 正式发布

当 MVP 稳定后，优先将正式看板迁入 Ares：

- 复用 Ares 现有 BQ 报表配置能力。
- 如支持原生业务看板，则直接配置 Ares 看板。
- 如只支持嵌入式报表，则把稳定查询作为报表集市条目接入。
- 将指标说明、负责人、更新时间、数据源和口径版本挂到 Ares 看板中。

Metabase 保留给数据分析、研发排查和临时专题，并持续承担受限业务数据的云主机受控访问与风险隔离；它不应单独定义正式经营口径。

### 阶段四：权限和质量固化

- Ares 管理业务访问和菜单权限。
- BigQuery 管理数据集、View 和行级数据权限。
- Metabase 按角色开放：既服务需要自助分析的用户，也作为部分受限业务数据的唯一授权访问入口；需落实数据集、行/列、导出和审计规则。
- BQ 与旧引擎并行核对 7–14 天，确认后下线非 BQ 依赖。
- 建立看板变更审批、指标版本和数据质量告警。

## 6. 决策建议

| 决策问题 | 建议 |
|---|---|
| 是否需要新建 Metabase | 不作为必选项；若需要快速试错和自助分析，可先部署小范围 Metabase |
| Ares 是否值得继续建设 | 值得，尤其适合统一入口、业务权限和正式经营看板 |
| 是否让业务人员直接搭建生产看板 | 可以配置已有指标和筛选器；核心 SQL、指标和权限仍由研发/数据开发负责 |
| 是否允许两个平台各自定义指标 | 不允许；指标公式和数据口径必须以 BigQuery 统一层为准 |
| 是否继续使用 Impala | 新看板不继续依赖，按迁移计划逐步废弃 |
| 推荐最终形态 | BigQuery 统一统计底座 + Ares 正式业务入口 + Metabase 受控访问/风险隔离与敏捷分析层 |

## 7. 需要研发先确认的能力清单

1. Ares 是否支持直接新增 BigQuery 数据集或只支持现有报表模板。
2. Ares 是否支持业务看板中的图表、指标卡、筛选器和联动配置。
3. Ares 现有 `BQ-` 报表的配置入口、数据集定义和权限模型。
4. Ares 是否支持从 MySQL 读取指标定义、事件字典和游戏字典。
5. Ares 是否支持看板级和行级权限。
6. Ares 报表是否支持定时刷新、导出、订阅和异常告警。
7. 业务看板为空是功能未配置，还是当前账号无权限。

## 8. 结论

从长期治理看，Ares 应作为正式业务看板平台；云主机 Metabase 既是快速分析和验证工具，也是受限业务数据的受控访问与风险隔离层。两者不应各自建设一套事实数据和指标逻辑，而应共享 BigQuery 的统一汇总层。

最小可行路径是：

```text
研发建设 BigQuery 统一指标层
        ↓
Metabase 受控访问、风险隔离与敏捷分析
        ↓
Ares 复用 BQ 报表能力正式发布
        ↓
业务人员基于标准数据集自行调整看板
```

这样既能控制研发投入，也能保留业务自助分析能力，同时避免 Ares、Metabase、旧引擎之间产生多套口径。
