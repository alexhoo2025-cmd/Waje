# Waje 多端设备、性能、事件与会话报表 / 看板详细设计 V2

> 版本：V2 · 2026-08-27  
> 面向：产品、研发、数据、运营值班  
> 交付：本地阅读版 HTML + 指标与数据契约 + Metabase 落地说明

## 0. 先看结论

这份设计把 Android、iOS、H5 拆成独立端侧，在同一套视觉和指标规则下展示，但不把不同产品的事件、会话或性能记录直接相加。首页先回答“数据是否到达、是否成熟、是否能解释”，再进入设备、性能、稳定性和业务链路。

- **Android：**三个生产包均已有 Performance 记录，2026-08-20 至 26 共 7 个性能日；Analytics 目前只有 2026-08-24 一张日表，行为趋势仍未成熟。
- **iOS：**现有来源 `com.wajegame.wajegame` 有 5 个 Analytics 日表、6 个 Performance 日，能试运行性能基线，但不能与 Android 做完整 7 日趋势结论。
- **H5：**2026-08-14 至 21 有 8 个 Analytics 日表，仅有 `page_view`、`session_start`、`first_visit`、`user_engagement` 四类标准行为事件；Web Vitals、白屏、核心请求、前端错误、游戏就绪和可下注都属于**数据缺口**，不得用停留或退出代理性能。
- **V1 的展示门禁：**百分位性能指标至少 500 个合格样本；正式问题排行至少 100 个用户型分母或 200 个计数型分母；少于门槛只显示“样本不足观察”，不触发正式告警。
- **远端落地状态：**目标聚合数据集 `wajenigeria.europe-west4.waje_device_performance_mart` 尚未因 `bigquery.datasets.create` 权限不足而创建；Metabase 远端写入权限也未提供。本文件和本地预览是可交付的设计与实施合同，不冒充已上线看板。

设计依据为需求文档《设备监控及性能优化指标系统开发需求》（2026-08-17）：

[打开需求文档](https://ksg964l11fam.sg.larksuite.com/wiki/QsplwWjnHi0J1PksQJQl3SrDgce?from=from_copylink)

需求文档要求统一监控：设备健康、页面性能、稳定性、网络质量、核心业务链路、游戏体验、版本质量和告警闭环。全局分析维度包括国家、手机运营商、终端、分包渠道、设备档位、手机内存、手机品牌、应用版本、H5 版本、浏览器、机器温度和时间。

本方案的安全边界：

- 只向聚合层和看板暴露日期、端侧、包体、版本、国家、品牌/型号桶、系统、网络、事件类别和性能统计；不暴露用户标识、会话原值、广告标识、Cookie、完整 URL、请求/响应正文、订单明细或错误堆栈。
- Android Sessions 的唯一会话数仅在 Sessions 表内部使用；Analytics 的 `session_start` 统一称为“会话开始事件数”，不与唯一会话数混算。
- Crashlytics 导出行数不是崩溃数、受影响用户数或崩溃率；在字段、去重键、会话分母完成认证前只展示事件量和问题数。
- H5 Analytics 日表位于 `waje-analytics-readonly` 的 US 区域，V1 聚合层只使用 `wajenigeria` 的 `europe-west4` 数据。跨区域纳入必须先复制、对账并获批准。

## 3. 统一信息架构：8 个页面，而不是一张大杂烩

### 01｜全端健康总览

**问题：**今天哪些端有完整数据？哪个端的性能、行为或稳定性结论可以使用？

**首屏样式：**顶部为“数据截止时间 / 完整日覆盖 / 数据状态”状态带；下方是 5 个有明确决策含义的卡片；中部左侧放端侧覆盖趋势，右侧放质量告警；底部放三端状态矩阵。

**首屏卡片：**

1. 完整数据日覆盖率：已到达完整日 ÷ 请求日；显示百分比和“当前完整日 / 请求日”。
2. 会话开始事件数：当前窗口 `session_start` 事件次数；卡片必须显示端侧和窗口。
3. 原生性能记录量：仅 Firebase Performance 记录；用于判断样本是否存在，不表示性能好坏。
4. 性能数据状态：`已核验 / 试运行 / 未成熟 / 延迟 / 数据缺口 / 阻断`。
5. 严重质量告警数：只统计已达到门槛且需行动的告警；数据缺口单独计数。

**主图与表：**

- 端侧 × 日期覆盖热条：完整日为实心色块，延迟为橙色，缺失为灰色；当天不作为完整日。
- 端侧状态矩阵：行是 Android / iOS / H5，列是 Analytics、Performance、Sessions、Crashlytics、业务漏斗、H5 Web 性能，单元格显示状态和最新时间。
- 质量告警清单：数据源、影响端、异常现象、首次发现、最新状态、责任动作。

**当前呈现：**Android Performance 7 日可试运行；iOS 5～6 日未成熟；H5 行为可用但 Web 性能为数据缺口。

### 02｜核心业务成功率与漏斗

**问题：**注册、登录、充值、进局、下注到底是“提交了”还是“服务端成功了”？

**首屏样式：**一条横向漏斗，上方放每阶段成功数和成功率，下方左右分为“客户端尝试信号”和“服务端认证结果”。未有服务端分母的阶段使用灰底 `blocked`，不能用点击、iframe 创建或客户端回调替代。

**阶段：**启动首页 → 注册 → 登录 → 充值 → 提现 → 进局 → 游戏就绪 → 可下注 → 首局。

**图表与明细：**

- 漏斗阶段表：阶段、有效尝试数、服务端成功数、成功率、样本量、状态、缺口说明。
- 按端 / 包体 / 版本 / 国家 / 设备档位的单维度对比条形图。
- 失败原因堆叠条：业务拒绝、鉴权失败、参数校验、系统错误、超时、重复提交分开。
- 问题对象排行：一次只选择一个主维度（版本、国家、运营商、设备档位等），不画高基数联合热力图。

**当前呈现：**Analytics 中的注册、充值、提现只作为客户端行为信号；最终成功率需由 Origin 服务端聚合补齐。H5 尚无 `game_ready` / `bet_ready`；Android/iOS 同样不把普通事件直接解释为成功。

### 03｜页面与原生性能分析

**问题：**用户在哪个页面、版本或设备上变慢？慢在启动、渲染还是接口？

**页面布局：**

- 顶部 4 卡：页面访问量 / 启动或首页加载 P95 / 页面白屏率 / 核心请求失败率。
- 中部全宽折线：按日期或版本显示 P50 / P95 / P99；只画合格且去重的 `page_visit_id` 或启动链路样本。
- 下方两列：左为页面排行，右为网络请求类别排行；每行可展开到单一设备维度。
- 右上角显示样本量、数据截止时间、质量状态；样本不足时显示 `N/A`，不补 0。

**页面排行字段：**页面、集中维度、访问量、P50、P95、P99、资源传输大小 P50/P95、API 失败率、白屏率、受影响会话数、状态。

**原生性能字段：**轨迹类别、版本、设备/系统、持续时长 P50/P95/P99、慢帧比例、冻结帧比例、网络响应 P95、响应码成功率、请求量、样本量。

**当前呈现：**Android Performance 已有轨迹、网络、慢帧/冻结帧字段；iOS Performance 可试运行；H5 当前没有 Web Vitals、路由 ready、核心请求和白屏事件，因此性能卡全部显示 `data_gap`，不显示伪造数值。

### 04｜稳定性分析

**问题：**哪个版本或设备的 Fatal、ANR、Non-fatal 正在增加？影响面是否经过可靠去重？

**首屏样式：**Fatal、ANR、Non-fatal、问题数四张独立卡；每张卡同时显示事件量、去重键、可用分母和状态。下方为问题排行和版本回归表。

**明细字段：**问题类型、主问题对象、异常现象、事件量、去重事件量、受影响用户/会话（完成认证后才显示）、集中端点、版本、设备、系统、页面、状态。

**规则：**

- 记录数按 `event_id` 去重；问题数按 `issue_id` 去重；Fatal、Non-fatal、ANR 分开统计。
- 原始事件可能同时有多个标签，排行和告警只选一个主异常维度，避免重复归因。
- 跨问题、跨包的受影响用户使用并集，不相加；分组小于 10 个去标识化会话时合并或隐藏。

**当前呈现：**Android Crashlytics 先展示去重事件量和问题数，崩溃率、ANR 率和受影响用户数保持 `provisional`；iOS 当前未看到 Crashlytics 导出表，显示 `data_gap`。

### 05｜网络质量分析

**问题：**网络慢或失败集中在哪个国家、运营商、网络类型、请求类别或页面？

**首屏样式：**顶部卡片为网络 P95、超时率、重试率、HTTP 成功率；下方左侧是国家/运营商排行，右侧是请求类别散点（横轴 P95、纵轴失败率、气泡为请求量）。

**明细字段：**国家、运营商桶、网络类型、请求类别、请求量、HTTP 200～399 成功率、系统失败率、超时率、重试率、P50/P95 响应耗时、受影响会话、集中页面。

**算法规则：**网络 P95 按请求类别分开；有效请求必须有请求开始和完成时间；`4xx` 拆为业务拒绝、鉴权失败和系统异常；跨请求类型不能平均。重复请求使用 `request_id` 去重。

**当前呈现：**Android/iOS Performance 已有响应码和耗时字段，需先完成安全的请求类别映射；H5 网络质量需补 `H5_CORE_REQUEST` 和 `H5_NETWORK_CHANGE`。

### 06｜设备、版本与渠道分析

**问题：**低端机、特定品牌、老系统或某个包体是否集中出现体验问题？

**首屏样式：**左侧为设备档位分布，右侧为版本质量矩阵；底部是设备/系统/网络单维度排行。颜色只表示状态或异常偏离，不把事件行占比写成用户占比。

**统一维度：**端侧、分包渠道、包体、应用版本、发布批次、国家、品牌、型号桶、操作系统与版本、内存档位、网络类型、运营商桶、机器温度桶、日期。

**设备档位：**极低端 `<1GB`；低端 `1GB≤RAM<2GB`；中端 `2GB≤RAM<4GB`；高端 `≥4GB`。未知内存不归入任何档位，并在数据质量页显示未知率。

**当前呈现：**Android Performance 有品牌/型号、系统、国家、运营商、网络类型；RAM、机器温度、设备档位及稳定的 `release_id` 仍需补齐或确认。iOS 当前同样缺少统一内存/温度维度；H5 的设备档位和网络维度尚未采集。

### 07｜游戏体验分析

**问题：**用户能否从启动进入可玩的游戏状态，并完成第一局？

**页面布局：**上方为“启动首页 / 进入游戏 / 游戏就绪 / 可下注 / 首局”阶段卡；中部为阶段耗时分布和退出点；下方为按端、包、版本、设备档位、网络的异常排行。

**必须区分：**`GAMESTART` 是 Origin 的服务端事件候选，不自动等同“游戏就绪”；`BETREWARD` 也不自动等同“可下注”。只有服务端成功枚举和客户端链路键对上后，才生成阶段成功率。

**当前呈现：**现有 Firebase Analytics 仅能提供部分行为尝试信号；H5、Android、iOS 的 `game_ready` / `bet_ready` / 首局服务端事实尚未完整认证，阶段卡显示 `blocked` 或 `data_gap`。

### 08｜告警与数据质量

**问题：**哪些指标可以告警，哪些只是数据本身坏了？

**页面布局：**左侧为数据质量状态卡，右侧为告警队列；底部是指标血缘、样本量、去重、字段覆盖和延迟检查。

**状态枚举：**

| 状态 | 含义 | 展示行为 |
|---|---|---|
| `certified` | 字段、口径、分母、刷新均已核验 | 可用于正式日报和告警 |
| `provisional` | 有数据但仍需字段、去重或来源确认 | 可观察，不用于高风险结论 |
| `immature` | 数据日不足 7 天或版本样本不足 | 只显示单端基线，不做趋势比较 |
| `delayed` | 最新事件时间落后阈值 | 显示数据延迟，不触发产品性能告警 |
| `data_gap` | 该端或该指标没有采集 | 明确显示未接入，不填 0 |
| `blocked` | 需要服务端事实、权限或语义确认 | 显示阻断项和补齐动作 |

## 5. 指标字典：定义、算法、分母、来源与状态

> 任何卡片、图表或导出结果都必须从本表引用定义。显示事件次数时，标签写“事件数”；显示用户或会话时，必须有明确去重键和分母。

| 指标 | 定义与算法 | 分母 / 样本门槛 | 粒度与来源 | 当前状态 |
|---|---|---|---|---|
| 数据覆盖率 | `完整数据日数 ÷ 请求数据日数`；同时展示最新事件时间和延迟分钟数 | 请求日为自然日；当天不算完整日 | 日期 × 端 × 来源 × 包；`mart_endpoint_coverage_daily` | 全端必备 |
| 日活跃用户（DAU） | 以经批准的去标识化用户键在日内去重；不能用事件行数替代 | 用户键有效且满足隐私阈值 | 日期 × 端 × 包；Analytics/服务端 | 当前 `blocked`，需确认用户键口径 |
| 会话开始事件数 | `COUNTIF(event_name='session_start')` | 事件记录数，不是唯一会话数 | 日期 × 端 × 包 × 版本；Analytics | Android/iOS/H5 可用，窗口成熟度不同 |
| Android 去标识化会话数 | `COUNT(DISTINCT session_id)`，只在 Sessions 表内部计算 | Sessions 表有效 `session_id` | 日期 × Android 包 × 版本；Sessions | Android 可用，不能跨端相加 |
| 页面 / 屏幕浏览 | H5 统计 `page_view`，原生统计 `screen_view` 事件数 | 事件数；不解释为用户数 | 日期 × 端 × 页面/屏幕；Analytics | H5/原生行为可用 |
| 启动 / 首页成功率 | `成功显示核心内容的启动链路 ÷ 有效启动链路`；按 `app_launch_id` 或 `session_id` 去重 | 有效启动链路；未知结束状态排除 | 日期 × 端 × 包 × 版本；Performance + 客户端 | `blocked`，需补齐成功枚举 |
| 注册成功率 | `有效注册成功数 ÷ 有效注册提交数`；验证码错误、提交失败、页面故障分开 | 服务端确认的有效提交 | 日期 × 端 × 包 × 版本；Origin + Analytics | 部分 `blocked` |
| 登录成功率 | `进入登录成功状态数 ÷ 有效登录提交数`；风险拒绝与系统错误拆开 | 有效登录提交 | 日期 × 端 × 包 × 版本；Origin + Analytics | 部分 `blocked` |
| 24 小时充值成功率 | `24 小时内最终到账数 ÷ 成熟的有效充值订单数`；未满 24 小时不入分母 | 订单成熟窗口 24 小时 | 日期 × 端 × 包 × 版本；服务端账务 + 客户端尝试 | `blocked`，需服务端事实 |
| 下注成功率 | `服务端确认成功的下注订单数 ÷ 有效下注提交数`；赔率变化、余额不足为正常拒绝单列 | 有效下注提交 | 日期 × 端 × 包 × 版本；Origin | `blocked` |
| 游戏进入成功率 | `进入可操作状态数 ÷ 有效游戏启动数`；`game_start_id`、游戏 ID 必须关联 | 有效游戏启动链路 | 日期 × 端 × 包 × 版本；Origin + 客户端 | `blocked` |
| 首次可玩率 | `首次进入可玩状态的链路数 ÷ 有效游戏启动链路数` | 客户端 `game_ready` + 服务端确认 | 日期 × 端 × 游戏；H5 V2 + Origin | `data_gap` / `blocked` |
| 重复提交率 | 在时间窗口内同一链路的重复提交用户/会话数 ÷ 有效提交用户/会话数；注册/登录 10 秒、提现 10 秒、下注/进局 5 秒 | 合法链路键；不与正常重试混淆 | 日期 × 端 × 阶段；客户端 + Origin | 待补链路键 |
| 低端设备占比 | `RAM 档位为极低端或低端的有效设备/会话数 ÷ 有内存观测的有效设备/会话数` | 未知内存不入分母 | 日期 × 端 × 包 × 档位 | `data_gap`，需内存字段 |
| 高温链路失败率 | `高温/极高温样本中的失败链路数 ÷ 有温度观测的有效链路数` | 未知温度排除；需温度桶 | 日期 × 端 × 链路；客户端 + Origin | `data_gap` |
| 原生轨迹 P50/P95/P99 | 合格 `DURATION_TRACE` 时长的分位数；用 `APPROX_QUANTILES(duration_ms,100)` | 仅成功且非负时长；样本 ≥ 500 | 日期 × 端 × 包 × 版本 × 一个设备维度；Performance | 字段具备，数值待审计 |
| 页面加载 P50/P95/P99 | 合格 `page_ready_at - page_start_at` 的分位数；按 `page_visit_id` 去重 | 页面 ready 成功；缺结束、负时长、超时单列；样本 ≥ 500 | 日期 × 页面 × 版本 × 浏览器/网络；H5 V2 | `data_gap` |
| 资源传输大小 P50/P95 | 实际压缩传输字节数的分位数；缓存命中但无字节不填 0 | 字节可观测；未知单列 | 日期 × 页面/资源类别 | `data_gap`，需资源计时 |
| API 失败率 | `(系统失败 + 超时 + 5xx) ÷ 有效请求数`；4xx 拆为业务拒绝/鉴权/系统 | 请求有安全类别和请求键 | 日期 × 请求类别 × 端；Performance/H5 V2 | Android/iOS 待分类；H5 缺口 |
| 网络 P95 | `response_completed_time_us ÷ 1000` 的第 95 分位 | 有开始、完成、响应码；样本 ≥ 500 | 日期 × 端 × 包 × 请求类别 × 网络 | Android/iOS 字段具备 |
| 超时率 | 超时请求数 ÷ 有效请求数 | 请求类别内计算 | 日期 × 请求类别 × 网络 | 待统一超时枚举 |
| 重试率 | 发生重试的请求链路数 ÷ 有效请求链路数 | `request_id` / 业务链路键去重 | 日期 × 请求类别 × 网络 | 待补重试字段 |
| 慢帧比例 | `SCREEN_TRACE` 中慢帧比例的 trace 加权均值 | 有效屏幕 trace；样本 ≥ 500 | 日期 × 包 × 版本 × 设备/系统 | Android/iOS 可试运行 |
| 冻结帧比例 | `SCREEN_TRACE` 中冻结帧比例的 trace 加权均值 | 同上 | 日期 × 包 × 版本 × 设备/系统 | Android/iOS 可试运行 |
| Fatal / Non-fatal 事件数 | 按 `event_id` 去重后的 `is_fatal=true/false` 事件数 | 去重键有效 | 日期 × 包 × 版本 × 设备/系统；Crashlytics | Android 先展示数量 |
| 问题数 | `COUNT(DISTINCT issue_id)` | `issue_id` 非空 | 日期 × 包 × 版本 × 主维度；Crashlytics | Android 可试运行 |
| 异常排行分数 | `40%×受影响用户归一化 + 30%×偏离度 + 20%×核心业务权重 + 10%×影响范围` | 用户型分母 ≥100 或计数型 ≥200；单一主维度 | 日期 × 单一问题维度；聚合层 | 设计完成，待稳定性分母 |
| H5 Web 性能状态 | Web Vitals、路由 ready、核心请求、前端错误的完整率与延迟 | `measurement_state=complete`；缺指标为缺口 | 日期 × 页面 × 浏览器/网络；H5 V2 | 当前 `data_gap` |

## 7. 报表输出设计

### 7.1 D+1 端侧健康日报

**标题区：**日期、数据截止时间、完整日数、口径版本、总体状态。  
**摘要区：**三端各一段结论，必须包含“可用 / 不可用 / 下一动作”。  
**表格区：**端侧覆盖、设备结构、性能 P95、稳定性事件量、核心漏斗状态。  
**异常区：**只列达到门槛的异常，标注主维度、样本量、影响范围和负责人。  
**结尾：**缺口与次日动作，不写无证据的因果判断。

### 7.2 周度版本回归报告

只有达到 7 个完整日、版本样本量达标、字段和口径未变时发布。每个版本固定包含：版本覆盖、P50/P95/P99、网络成功率、慢帧/冻结帧、Fatal/Non-fatal 事件数、业务阶段状态、与上一版本的偏离及置信说明。H5 在未补齐 Web Vitals 前不生成“页面性能回归”结论。

### 7.3 15 分钟原生诊断页

仅 Android/iOS Performance 与 Crashlytics 使用；显示原生轨迹 P95、网络 P95、HTTP 成功率、慢帧、冻结帧、Fatal/Non-fatal 事件量。最新事件时间落后 45 分钟时，状态改为 `delayed`，不触发产品性能告警；当前源的最大事件时间约落后一天，因而首期只做新鲜度监测。

### 7.4 H5 接入覆盖报告

单独报告 10 个 H5 V2 逻辑事件的事件量、字段完整率、采集成功率、入库延迟、重复率和缺失项；将 Web Vitals、核心请求、白屏、前端错误、游戏就绪、可下注作为独立模块，不与 GA4 四类标准事件混写。

## 9. 埋点与数据缺口路线图

### P0：先让 H5 能回答性能问题

落地 10 个逻辑事件：

`H5_SESSION_START`、`H5_NAVIGATION_PERF`、`H5_CORE_REQUEST`、`H5_GAME_LOAD`、`H5_GAME_READY`、`H5_BET_READY`、`H5_CLIENT_ERROR`、`H5_NETWORK_CHANGE`、`H5_RECOVERY_RESULT`、`H5_SESSION_END`。

公共字段包含 `session_id`、`page_visit_id`、`game_load_id`、`request_id`、`measurement_state`、`web_version`、`release_id`、`device_tier`、`memory_tier`、`browser_name`、`os_name`、`network_type`；性能字段包含 `fcp_ms`、`lcp_ms`、`inp_ms`、`cls`、长任务、资源和核心请求耗时、错误类别与脱敏指纹。

禁止采集 Cookie、令牌、完整 URL、请求/响应正文、广告标识和精确设备指纹。

### P0：统一原生字段与稳定性语义

- 原生 `custom_attributes` 仅允许 `release_id`、`screen_id`、`flow_stage`、`trace_category`、`request_kind`、`game_id`、`game_load_id`、`error_category` 等白名单枚举。
- 完成 Crashlytics `event_id` 去重、`issue_id` 聚合、`is_fatal` 分类、ANR 识别和会话分母认证。
- 确认 iOS 生产来源、包体和版本映射；补齐统一发布批次。
- RAM、机器温度、设备档位缺失时保留“未知”，不回填 0。

### P1：用服务端事实闭环核心业务

由 Origin 提供按日期 × 端 × 包 × 版本 × 阶段的认证聚合，至少覆盖登录成功、进局成功、游戏就绪、可下注、首局和最终支付结果。将 `REGISTER`、`LOGIN`、`GAMESTART`、`GAMEEND` 等候选事件与成功枚举、链路键完成语义确认。

### P1：网络与 CDN 观测

接入安全的请求类别、超时、重试和 CDN/cache 命中字段；不记录完整路径、请求体或响应体。跨域或缓存无法取得资源字节时标记未知，不写 0。

## 10. 告警、排行与验收

### 10.1 告警门槛

- 性能 P95 相对 7 日基线恶化 ≥20%，样本 ≥500，连续两个窗口成立。
- 数据源延迟 >45 分钟直接标记数据故障；不把“无数据”当性能异常。
- 正式用户型排行分母 ≥100；计数型排行分母 ≥200；低于门槛为“小样本观察”。
- 跨类型受影响用户取并集；单一问题排行只允许一个主维度。

### 10.2 验收清单

- 每个页面显示端侧、日期、数据截止时间、完整日数、样本量、质量状态和口径版本。
- 同一筛选上下文下，卡片、图表、表格和导出结果可相互对账。
- Android、iOS、H5 不跨端相加事件、会话、用户或受影响用户；不同来源窗口不做趋势比较。
- H5 未补埋点前，Web Vitals、白屏、网络、核心漏斗均显示 `data_gap` / `blocked`。
- 所有小于 10 个去标识化会话的分组隐藏或合并；不落盘原始事件行。
- 每日刷新分为 06:30 WAT 预刷新、12:30 WAT 最终刷新；延迟日进入质量页。
- 7 个完整日后才启用版本回归；稳定性率指标在去重键与会话分母认证前保持 `provisional`。
