### 早期为什么看起来像没有使用浏览器接口

1. 起源已登录页面最初位于另一个 Chrome Profile；扩展选中的 Profile 没有同一会话。
2. 扩展能够读取部分标签元信息，但接管目标标签会超时；这是 Profile/会话连接问题，不是起源系统拒绝自动化。
3. 在可控 Chrome Profile 登录后，浏览器接口恢复正常，实际完成了后续大部分查询和下载。

## 推荐的高效工作流

```text
Profile 预检
  → 浏览器并发查询池（2–3 页）
  → 7 天窗口原始导出
  → 下载完成轮询与内容归档
  → source-data.json（字段、日期、筛选、哈希）
  → 一次性新副本写入
  → Artifact Tool 读回与公式/历史校验
  → 后置视觉 QA
```

### 执行规范

1. **先选浏览器**：确认 Chrome 插件与已登录起源 Profile 相同；不一致时先在可控 Profile 登录，而不是复制 Cookie。
2. **先小样本、后正式窗口**：用 7/12–7/13 证明筛选；用户明确的别名映射可作为 `mapping_override`，但 7/13 前历史必须保护。
3. **固定 7 天窗口**：例如 7/14–7/20、7/21–7/27、7/28–8/03、8/04–8/10、8/11–8/16。
4. **并发而非并行写入**：浏览器查询可 2–3 页并发；Excel 更新始终单实例。
5. **下载不是完成**：下载列表为 `已完成` 后才取文件；文件表头、日期集合、哈希三项合格才入清单。
6. **拆分 QA**：数据读回、历史哈希、样式克隆、公式扫描为阻断门槛；重型渲染作为可恢复后置任务，不重新发起数据查询。

## 后续优化优先级

1. 在日常使用的 Chrome Profile 安装并启用 Chrome 插件，固定由该 Profile 打开起源/GM 页。
2. 为每个报表保存“筛选别名合同”：Sheet 名、显示名、包渠道、媒体、渠道、样本证据。
3. 使用 `source-data.json` 作为浏览器阶段和 Excel 阶段的唯一交接物，支持断点续跑。
4. 生命周期 Joint 使用 3 页日期队列；起源报表使用 7 天窗口和 2–3 页池。
5. 将视觉渲染移到后台 QA；主交付仅等待数据完整、读回一致、公式与历史保护通过。
