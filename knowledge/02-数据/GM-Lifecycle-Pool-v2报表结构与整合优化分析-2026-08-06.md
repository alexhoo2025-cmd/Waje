# GM Lifecycle Pool v2 报表结构与整合优化分析

## 1. 结论摘要

`Lifecycle Pool v2.html` 是一个基于 AdminLTE 3 的 GM 后台单页报表。页面结构清晰，但数据组织仍偏“后端一次返回多张明细表、前端逐表展示和逐表导出”，适合后台排查，不适合日常多日期、多游戏、多生命周期的分析。

建议将它改造成“统一筛选 + 指标分层 + 汇总看板 + 可下钻明细”的报表，并将 GM RTP 数据逐步接入起源平台的 BigQuery 统一分析层。

核心判断：

- 当前页面只有一个 `queryDate` 日期控件，没有日期范围、游戏、生命周期、游戏类型、自研/联运等业务筛选器。
- 当前页面包含 7 个数据表和 7 个独立导出按钮，数据粒度和用途混在同一页面。
- 报表同时展示基础/完全、实际/预期、盈利调整、破产控制、用户留存和充值提现指标；缺少指标分组和默认核心指标。
- 页面已具备统一 API 查询基础：前端通过 `/sys/dynamic/lifecyclev2/pool/query` 获取数据，再分别填充各表。
- 最适合的整合方式是：BigQuery 统一事实/汇总层，Ares 起源平台作为正式入口，GM 保留为运营排查后台。

## 2. 来源与页面技术结构

| 项目 | 观察结果 |
|---|---|
| 页面标题 | Lifecycle Pool v2 |
| 页面入口 | `/sys/dynamic/lifecyclev2/pool` |
| UI 框架 | AdminLTE 3.0.0-rc.5、Bootstrap、jQuery |
| 表格/导出 | 原生 HTML Table + `exportTableToExcel` |
| 图表依赖 | 引入 Chart.js，但当前页面主体以表格为主 |
| 查询入口 | `queryLifecyclePool(1)` |
| 数据接口 | `/sys/dynamic/lifecyclev2/pool/query?queryDate=...&startDate=...&endDate=...&subKey=...` |
| 当前筛选 | 单个日期输入 `queryDate` |
| 当前语言 | 中文/English |
| 当前页面能力 | 查询历史记录、表格展示、逐表导出、部分数据修改 |

前端脚本中维护了较大的 `gameTypes` 映射，将游戏类型 ID 映射到 PG、Tada、PP、OMG、自研游戏、Whot、Fish、Dice、Roulette 等名称。这说明游戏字典目前部分硬编码在页面脚本中，后续应迁移为 MySQL/BigQuery 统一字典。

## 3. 当前报表组织逻辑

当前页面大致采用以下层级：

```text
Lifecycle Pool v2
├─ 生命周期奖池汇总展示
├─ 生命周期详细奖池
├─ 按游戏汇总
├─ 按生命周期汇总（活跃用户）
├─ 按生命周期汇总（新增用户）
├─ 分生命周期展示留存（活跃用户）
└─ 分生命周期展示留存（新增用户）
```

### 3.1 生命周期奖池汇总展示

这是首页总览表，当前有 10 个字段：

| 指标 | 业务用途 |
|---|---|
| 总基础下注额 | 基础口径的下注规模 |
| 总完全下注额 | 完全口径的下注规模 |
| 总基础真实回报比 | 基础实际回报表现 |
| 总完全真实回报比 | 完全实际回报表现 |
| 总基础预期回报比 | 基础理论/预期回报 |
| 总完全预期回报比 | 完全理论/预期回报 |
| 总人数 | 当前统计范围人数 |
| 今日完全实际盈利调整幅度 | 当日实际盈利调整 |
| 当前完全实际盈利扣除幅度 | 当前盈利扣除/控制调整 |
| 修改 | 后台调整入口 |

该表适合改造成看板顶部指标卡，但“修改”不应与只读分析指标放在同一视图，建议单独放到配置/操作权限区域。

### 3.2 生命周期详细奖池

这是当前最宽的明细表，字段包括：

| 指标组 | 字段 |
|---|---|
| 维度 | 生命周期、游戏类型 |
| 配置/差异 | 差额、预期回报比、盈利比万分比、实际回报比万分比 |
| 基础口径 | 基础预期盈利、基础实际盈利、基础下注额、基础真实回报比 |
| 控制项 | 总破产保护金额、总个人盈利控制金额 |
| 完全口径 | 完全预期盈利、完全实际盈利、完全下注额、完全下注额占比、完全真实回报比 |
| 调整项 | 今日完全实际盈利调整幅度、当前完全实际盈利扣除幅度 |
| 操作 | 修改 |

该表的主要问题是 20 个字段同时展示，且将“监控指标、计算中间量、风险控制金额、可修改字段”混在一起，导致日常分析需要人工识别重点。

### 3.3 按游戏汇总

该表以游戏为主维度，包含基础和完全两套回报口径：

- 基础下注额、基础预期盈利、基础实际盈利、基础真实回报比、基础预期回报比、基础回报比差距。
- 总破产保护金额、总个人盈利控制金额、破产保护/下注、个人盈利/下注。
- 完全下注额、完全预期盈利、完全实际盈利、完全真实回报比、完全预期回报比、完全回报比差距、完全下注额占比。

该表是最适合业务看板的主体，应支持游戏排名、RTP 偏差排序、下注额贡献和异常下钻。

### 3.4 按生命周期汇总

活跃用户生命周期表和新增用户生命周期表结构基本一致，核心维度为生命周期，指标包括：

- 基础/完全下注额。
- 基础/完全真实回报比。
- 基础/完全预期回报比。
- 基础/完全回报比差距。
- 基础/完全预期盈利和实际盈利。
- 破产保护、个人盈利控制。
- 人均实际盈利、人数。
- 当日充值总金额、当日复充总金额、平均复充次数、平均流充比。
- 营收、TX 总金额、人均实际营收、TC 比。
- 折损系数、绝对破产人数、绝对破产次数、人均绝对破产次数。

这些字段同时覆盖游戏经济、用户生命周期、充值、复充、提现、营收和破产风险，业务价值较高，但需要按主题拆成“回报、资金、用户价值、风险”四组。

### 3.5 留存表

活跃用户和新增用户各有一张留存表，字段为：

- 生命周期。
- 日期。
- 人数。
- 次日留存、周期升级比例。
- 三日留存、周期升级比例。
- 七日留存、周期升级比例。

当前页面将留存和周期升级比例并列，但没有明确区分“留存 cohort”“生命周期升级 cohort”和“日期是否完整”，近期日期的 0 值可能是未成熟而不是实际为 0。

## 4. 指标组织逻辑与口径风险

### 4.1 基础与完全口径

页面同时展示基础和完全下注额、实际回报比、预期回报比。根据当前页面结构，完全口径应理解为在基础口径上纳入完整结算/调整后的统计口径，但 HTML 未提供公式定义，因此不能仅凭页面确认差额来源。

整合时必须增加：

```text
完全下注额 - 基础下注额 = 完全口径新增/调整下注额
完全真实回报比 - 基础真实回报比 = 完全口径回报变化
```

并按游戏、生命周期、日期拆解差异，而不是只展示总差额。

### 4.2 真实与预期回报比

- 真实回报比：应基于实际盈利/实际派奖与下注规模计算，但需要确认分子、分母和是否包含调整项。
- 预期回报比：来自游戏或生命周期配置，页面中可看到同一生命周期下不同游戏共享预期回报配置。
- 回报比差距：建议统一定义为 `实际回报比 - 预期回报比`，并同时保留百分点和绝对金额两种展示。

### 4.3 盈利比与回报比

页面同时有“盈利比万分比”和“实际回报比万分比”。这两个指标不能在迁移时合并：

- 回报比关注玩家回报/下注关系。
- 盈利比关注平台盈利/下注关系。

需在指标字典中明确正负方向，否则容易把“平台盈利率上升”和“玩家回报下降”误认为同一指标变化。

### 4.4 活跃用户与新增用户

页面分别输出活跃用户生命周期汇总和新增用户生命周期汇总。两者不能直接合计，也不能把新增用户表当作全量用户表。看板需在标题、筛选和导出文件中明确用户范围。

### 4.5 留存与周期升级比例

留存表中的 0 值需要拆分为：

- 真实无留存。
- 观察窗口未成熟。
- 数据缺失或默认填 0。
- 生命周期升级规则未覆盖该日期。

正式看板应使用 `N/A` 或“未成熟”显示，而不是统一显示 0。

## 5. 当前系统的主要问题

### P0：影响查询和日常分析

1. 只有单日期控件，无法直接查询连续 7 天或自定义日期范围。
2. 没有游戏筛选，用户需要在大表中人工找游戏。
3. 没有生命周期筛选，无法快速定位某个生命周期层级。
4. 七张表分散展示，每张表独立导出，无法一次导出统一数据集。
5. 20 个左右字段全部平铺，核心指标与控制参数混杂。

### P1：影响口径理解

1. 基础/完全、实际/预期、盈利/回报缺少可见定义。
2. 活跃用户/新增用户边界不够突出。
3. “修改”按钮和只读数据混在表格中，存在误操作风险。
4. 游戏 ID 到游戏名称的映射部分写在前端脚本，存在重复 ID、名称空格和字典漂移风险。
5. 未见完整日、数据更新时间、数据版本和回补状态展示。

### P1：影响性能和扩展

1. 页面一次性加载大量表格 HTML，明细数据和汇总数据同时返回。
2. 查询接口参数目前以日期窗口为中心，缺少游戏、生命周期、指标选择等服务端过滤参数。
3. 前端导出依赖浏览器生成 Excel，不适合大日期范围和大数据量导出。
4. 页面引入 Chart.js，但当前结构没有形成趋势、异常和对比图表。

## 6. 建议的目标报表结构

```text
Lifecycle RTP 看板
├─ 全局筛选：日期范围 / 游戏 / 游戏类型 / 生命周期 / 用户范围 / 自研联运
├─ 核心指标卡：下注额 / 人数 / 实际 RTP / 预期 RTP / RTP 差异
├─ 规模与回报趋势：日期 × 下注额 × RTP
├─ 游戏对比：游戏排名 / 下注额贡献 / RTP 偏差 / 异常状态
├─ 生命周期对比：生命周期 × RTP / 下注额 / 人数 / TC / TX
├─ 用户价值与风险：充值 / 复充 / 营收 / 破产 / 人均营收
├─ 留存与升级：活跃用户 / 新增用户分别展示
└─ 明细下钻：原始生命周期奖池记录和调整记录
```

### 6.1 全局筛选器

| 筛选器 | 说明 |
|---|---|
| 日期范围 | 单日、近 7 日、近 30 日、自定义；默认最近 7 个完整日 |
| 游戏项目 | 游戏 ID/名称多选 |
| 游戏类型 | PG、Tada、PP、OMG、自研、联运等 |
| 生命周期 | 0、1、2、3、4…N；支持汇总 |
| 用户范围 | 活跃用户、新增用户 |
| 数据口径 | 基础、完全、实际、预期 |
| 运营范围 | 自研、联运、外接游戏 |
| 数据状态 | 完整日、实时、补数、未结算、异常 |

### 6.2 核心指标卡

首屏只保留：

- 总基础下注额。
- 总完全下注额。
- 基础/完全下注额差额及差异率。
- 基础/完全真实回报比。
- 基础/完全预期回报比。
- 实际与预期回报比差距。
- 总人数。
- 数据更新时间和完整日状态。

盈利调整、破产保护和个人盈利控制放入风险与调整模块，不作为默认首屏指标。

## 7. 数据层整合方案

### 7.1 统一数据模型

建议在 BigQuery 建立以下模型：

| 表/视图 | 粒度 | 主要用途 |
|---|---|---|
| `dwd_lifecycle_pool_game` | 日期 × 用户范围 × 生命周期 × 游戏 | 游戏级基础事实 |
| `dwd_lifecycle_pool_adjustment` | 日期 × 生命周期 × 游戏 × 调整类型 | 调整、扣除、破产控制 |
| `ads_lifecycle_rtp_daily` | 日期 × 游戏 × 生命周期 × 用户范围 | RTP 看板汇总 |
| `ads_lifecycle_user_value_daily` | 日期 × 生命周期 × 用户范围 | 充值、复充、营收、TX、TC |
| `ads_lifecycle_retention_daily` | 日期 × 生命周期 × 用户范围 | 次日/三日/七日留存和升级 |
| `dim_game` | 游戏 ID | 游戏名称、类型、供应商、自研/联运 |
| `dim_metric` | 指标 ID | 指标定义、公式、单位、负责人、版本 |

### 7.2 指标统一计算

```text
基础 RTP = 基础实际回报金额 / 基础下注额
完全 RTP = 完全实际回报金额 / 完全下注额
RTP 差距 = 实际 RTP - 预期 RTP
完全下注差额 = 完全下注额 - 基础下注额
完全下注差异率 = 完全下注差额 / 基础下注额
TC 比 = 按正式定义计算，必须注明金额比或人数比
TX 率 = TX 用户数 / 正式定义的分母用户数
```

公式仅作为整合目标模板，正式上线前需与 GM 后端计算逻辑逐项对账。

### 7.3 API 与查询改造

现有接口可继续保留，但建议新增参数：

```text
startDate
endDate
gameIds[]
gameTypes[]
lifecycleDays[]
userScope=active|new|all
metricGroups[]=rtp|value|risk|retention
dataScope=self|joint|all
```

API 返回建议拆为 `summary`、`gameRows`、`lifecycleRows`、`valueRows`、`retentionRows`、`quality` 六个区块，避免前端用一份超大响应同时渲染所有内容。

## 8. Ares/起源平台整合方案

### 推荐架构

```text
GM Lifecycle Pool V2
        ↓ 数据同步/接口抽取
BigQuery 统一事实层与汇总层
        ↓
Ares 起源平台 RTP/生命周期看板
        ↓
业务筛选、趋势、下钻、导出、权限
```

### 分阶段迁移

1. **P0 数据接入**：同步 GM 的游戏、生命周期、下注、回报、人数和调整结果。
2. **P0 指标对账**：GM 与 BigQuery 同日同游戏同生命周期核对基础/完全 RTP 和下注额。
3. **P0 起源查询**：先上线日期、游戏、生命周期和用户范围筛选。
4. **P1 看板发布**：上线 RTP 趋势、游戏排行、生命周期对比、调整监控和留存。
5. **P1 明细下钻**：从起源看板下钻到来源表和调整记录。
6. **P2 统一运营**：GM 保留排障和修改能力，Ares 成为日常分析入口。

## 9. 业务与研发职责

### 研发/数据开发

- 统一 GM 到 BigQuery 的同步接口或任务。
- 建立游戏、生命周期、用户范围和指标字典。
- 固化基础/完全、实际/预期口径。
- 增加日期范围和服务端筛选能力。
- 建立分区、缓存、分页和异步导出。
- 保障权限、修改审计、接口日志和数据质量。

### 业务/分析人员

- 确认默认核心指标和展示顺序。
- 确认游戏分类、自研/联运范围和生命周期定义。
- 确认 RTP 异常阈值和告警级别。
- 使用标准数据集配置看板筛选、布局和常用视图。
- 验收 GM 与起源数据对账结果。

## 10. 验收标准

- 可一次查询至少连续 7 天数据。
- 日期、游戏、游戏类型、生命周期、活跃/新增用户范围可以组合筛选。
- 首屏默认只展示核心指标，详细指标可以按模块展开。
- GM 与起源在同一日期、游戏、生命周期下的下注额和 RTP 可对账。
- 基础/完全、实际/预期四类口径不混淆，差额可以下钻。
- 未成熟和不完整日期不以 0 伪装为真实值。
- 7 天查询的响应时间和导出耗时达到研发约定 SLA。
- 任何“修改”操作有权限控制、二次确认和审计日志。
- GM 与起源并行核对 7–14 天后，再将起源作为日常统一入口。
