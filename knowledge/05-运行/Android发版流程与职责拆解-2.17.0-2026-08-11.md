# Android 发版流程与职责拆解（2.17.0）

本条目将飞书《Android发版流程》中选中的 **2.17.0** 页签，整理为可执行的 Android 发版基线。原表同时保留 2.11.1 至 2.16.0 等历史页签；不同版本的配置、提审策略和渠道包范围可能不同，实际发版仍应以当期需求、变更单和审批结果为准。

## 一、端到端流程

```mermaid
flowchart LR
  A[发布输入确认\n代码、资源、数值、文案] --> B[测试服 Debug 包\n回归与兼容测试]
  B --> C[testRelease 预发包\n提审服状态与全量回归]
  C --> D[Release 包\n提审配置与 Google Play 提交]
  D --> E[审核通过与更新策略\n热更/强更配置]
  E --> F[正式服切换\n服务、H5、子游戏更新]
  F --> G[商店与渠道包回归\nGrafana 追踪与补偿]
```

| 阶段 | 关键动作 | 主要产物 / 放行条件 | 主负责人 |
|---|---|---|---|
| 1. 发布输入确认 | 确认客户端、服务端分支；美术资源；数值配置；英文文案与图标 | 发布内容清单、分支与配置冻结结论 | Kirito、brooks、yxlmwei、vito、dora |
| 2. 测试服验证 | 生成 Debug 最终包；连测试服；按本次要求验证热更/强更；小游戏更新；兼容、功能回归与旧包更新 | 测试服验证通过、线上一周活跃版本清单 | Kirito、James |
| 3. 预发与提审服验证 | 合并 `testRelease`；打 Preview 包；切换提审服；必要时停服、更新提审服及配置；检查老包兼容 | 预发包、提审状态配置、兼容性结论 | Kirito、brooks、Fcaptain、James |
| 4. 提审包与商店提交 | 合并 Release 分支、打 Release 最终包、提审服屏蔽功能、GPS/IP 提审配置、提交 Google Play | 可提审包、提审文案、提审环境验收 | Kirito、Fcaptain、Vito、James |
| 5. 审核通过与生产发布 | 确定正常/热更/强更策略；切回非提审状态；Release 包连线上；服务更新与兼容处理 | 更新策略、线上配置、生产发布确认 | Fcaptain、brooks、Kirito |
| 6. 发布后验证与渠道包 | Release 包回归；商店最新包验证；GPS/IP 线上状态验证；渠道包 CDN 刷新和回归；指标追踪 | 发布后验收记录、渠道包版本确认、监控结论 | James、Kirito、Fcaptain、brooks |
| 7. 异常处置 | 对线上需安抚的玩家发放紧急邮件补偿 | 事件记录、补偿配置与结果 | Fcaptain |

## 四、关键控制点与数据观察

### 必须有明确放行记录的节点

1. **输入冻结**：代码分支、资源、数值、公告和英文文案全部确认后，才进入 Debug 最终包。
2. **兼容策略**：必须基于“线上一周活跃版本”给出兼容结论；不兼容时明确采用功能开关、强制更新或其他方案。
3. **环境切换**：测试服、`testRelease`、提审服、线上服的状态、连接目标、GPS/IP 和功能屏蔽项，应有变更前后记录。
4. **商店提交**：Release 包、版本说明、审核配置、屏蔽功能和提审环境测试均通过后才允许提交。
5. **生产发布**：线上服务、H5、子游戏、热更/强更和渠道包必须按同一版本清单协同发布。
6. **发布后验证**：商店包、主要登录/游戏链路、更新链路、渠道包及 Grafana 指标均有结果后，才能关闭发布事项。

### 建议纳入发布后看板的最小指标集

| 维度 | 建议监控 |
|---|---|
| 更新链路 | 商店包下载/启动成功率、热更成功率、强更完成率、版本分布、热更失败与回滚次数 |
| 稳定性 | Crash/ANR、JS/客户端错误、首屏/登录耗时、接口超时、闪断重连失败率 |
| 核心体验 | 登录成功率、游戏进入成功率、局开始/结算成功率、支付与提现成功率 |
| 业务安全 | RTP、异常大奖/异常负值、游戏营收、提成比及异常波动；仅向有权限的管理层展示明细 |

## 五、流程现状分析与优化建议

### 已覆盖的有效控制

- 已覆盖从分支确认、测试服、预发、提审、上线到渠道包和监控的完整链路。
- 对旧包兼容、热更/强更、提审状态、GPS/IP 状态、渠道 CDN 和线上异常补偿均有明确任务，适合 Waje 多包、多环境的发布形态。
- 测试侧已包含一周线上活跃版本、旧包、闪断重连和商店最新包，能够降低“办公室可用、真实用户不可用”的风险。

### 当前缺口与建议

| 问题 | 风险 | 建议动作 |
|---|---|---|
| 仅记录“主负责人”，没有审批/协作边界 | 配置、停服、强更或补偿的最终决策人不明确 | 在每个发布单增加 RACI、放行人和替补人；涉及资金、KYC、RTP、提现和合规的变更按 L3 管理。 |
| 分支、包体、配置、服务器状态分散在多行 | 无法快速复盘“哪个包连接哪个环境、用了哪套配置” | 为每个版本建立 `Release Manifest`：版本、commit、包 hash、环境、配置 diff、开关、热更量、回滚版本、责任人与时间。 |
| 环境切换与配置变更缺少前后值和回滚项 | 误配后难以定位、恢复或审计 | 任何 GPS/IP、功能屏蔽、付费弹窗、公告、热更/强更、渠道包配置均记录旧值/新值、生效时间、执行人与回滚步骤。 |
| 测试项有重复和源表文案不一致 | 执行遗漏或误解 | 将“提审状态/非提审状态”“渠道包回归”模板化；每次版本复制 checklist 后仅填写差异项，并由 QA 标注证据链接。 |
| 发布后仅写“Grafana 数据追踪” | 不能判断线上是否真正稳定或影响收入 | 预先定义监控阈值、观察窗口、告警负责人和停止/回滚条件；关联版本、渠道包和核心业务指标。 |
| 渠道包逐个手工刷新、回归 | CDN 缓存、包版本和配置易不一致 | 维护渠道包矩阵（包名、版本、CDN 刷新时间、热更版本号、回归结果）；可逐步自动化版本校验与 CDN 回源验证。 |

## 六、需人工确认的源表问题

1. 源表中分支名“插鱼分支”及部分子游戏升级说明存在缩写/表述不完整，归档时保留其原意；应由客户端负责人确认标准分支命名。
2. “线上服切到非提审状态”一行的事件描述仍写为“切换到提审状态”，与任务名冲突；应修订原表。
3. `whotgame` 回归行的第 1、2 条仍出现 `xender` 文案，疑似复制残留；应改为对应渠道包名称。
4. `vito` 与 `Vito` 的姓名大小写不统一；流程模板应统一人员标识。
5. 审核环境的具体功能屏蔽、GPS/IP、Whot/免费转盘等配置属于版本化、敏感配置，不应固化为跨版本默认值；每次发布必须由当期产品、合规与发布负责人确认。
