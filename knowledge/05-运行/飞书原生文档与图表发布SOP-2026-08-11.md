# 飞书原生文档与图表发布 SOP｜2026-09-01

飞书主文档：[飞书原生文档与图表发布 SOP｜数据分析报告产出规范](https://ksg964l11fam.sg.larksuite.com/wiki/IUF5w2YJnieFWqkkITOlmmacghc)

## 目标

将本地 Markdown、HTML、结构化指标和图表数据，高效发布为可搜索、可复制、可评论、可持续更新的飞书原生文档与表格。避免整页截图，也避免在浏览器 Canvas 中逐格录入。

## 团队阅读版默认规范

后续项目文档默认延续“结论前置、图表解释、文字简洁、附录下钻”的版式：

- 首屏先放目标、范围、核心结论和待确认项；
- 复杂关系优先用原生 Mermaid 流程图/架构图，精确指标用表格；
- 正文控制在可快速扫读的范围，详细字段、类型、枚举、SQL 和验收用附录承载；
- 表格默认不超过 4 列；字段较多时按公共字段、页面模块、服务端事件、枚举规则拆表；
- 用信息块表达“目标、排除范围、风险、待补证”，不使用整页截图替代正文；
- 所有指标写清名称、定义、算法、分母、数据来源、成熟规则和异常护栏；
- 文档发布后必须 API 回读结构和内容，视觉上再检查流程图、表格换行、移动端截断和链接跳转。

当前真金内嵌 Ludo V2 已按此规范作为示例：3 张流程图、核心指标表、分组字段附录和 P0 质量门禁。

### 埋点设计默认基线

自 2026-08-20 起，后续埋点设计以当前用户修订后的《For You 游戏推荐数据指标与埋点设计》为内容和版式基线：

- 以实际产品范围为边界，只保留当前需求必需的指标、事件和字段；删除与当前范围无关的扩展内容；
- 正文先给产品链路、核心指标和实施结论，详细字段、类型、枚举、SQL 和验收放入附录；
- 指标必须写清定义、算法、分母、数据来源、统计粒度和拆分维度；
- 埋点必须区分端侧行为与服务端事实，明确 Android/H5/iOS 差异、事件关联键和待补证项；
- 优先复用现有事件和字段，只有现有契约无法覆盖时才新增事件；
- 飞书文档保持简洁、重点突出，优先使用流程图、指标表和分组字段表，不堆叠泛化说明；
- 若用户后续修改该基线，最新明确修改优先于历史方案，旧内容只作为历史参考，不自动带入新设计。

当前参考文档：`knowledge/02-数据/ForYou游戏推荐数据指标与埋点设计-2026-08-20.md`。

## 本次问题复盘

本次耗时的根因不是内容量，而是执行路径选错：浏览器中的飞书表格主要由 Canvas 渲染，DOM 不提供稳定的单元格节点；高分屏下还存在 CSS 坐标与设备像素不一致。逐格点击会引入焦点丢失、选区漂移、粘贴拆分、超时和重复写入，最终出现“只有一个子表、URL 混入 C3”的失败产物。

暴露出的流程问题：

- 开始前没有先确认是否存在官方写入 API、CLI 或连接器；
- 没有设置“浏览器交互次数/失败次数”止损线；
- 把浏览器同时当作数据写入器和视觉验收器；
- 写入后只看页面外观，没有通过 API 回读结构和数值；
- 临时方案没有立即沉淀为可复用脚本。

## 工具优先级

```text
Lark 官方 CLI / 授权 API
  → 批量写 Docs、Sheets、Wiki 和原生图表
  → API 回读校验
  → 浏览器只做最终视觉验收

授权 API 暂不可用
  → 导入结构化 XLSX
  → API 或人工核验工作表和图表对象

浏览器 UI
  → 只用于登录授权、权限确认和视觉 QA
```

硬性止损规则：

- 需要连续操作 3 个以上单元格、区块或文档节点时，直接切换批量 API/CLI；
- 同一定位动作失败 2 次，或浏览器写入超过 5 分钟仍未形成稳定闭环，立即停止 UI 写入；
- 用户要求“原生图表”时，验收标准是图表 API 能返回真实图表对象，截图不算完成；
- 写操作成功响应不等于完成，必须有回读和视觉双验收。

## 安全与授权

- 使用 Lark 自建应用的最小权限，文档和表格操作显式采用用户身份；
- App Secret 通过隐藏终端输入交给官方 CLI，并由 macOS 钥匙串保存；
- 用户 Token、App Secret、Cookie 和密码不得进入项目文件、Git、命令日志或知识库；
- 发布脚本不读取、不接收、不持久化凭证，只调用已授权的 `lark-cli`；
- 变更前记录目标 URL、工作表清单和修订信息，避免误写其他文档。

## 标准发布流程

### 0. 首次绑定（只需一次）

```bash
python3 scripts/setup_lark_cli.py
```

按提示输入 App ID 和 App Secret；Secret 输入过程不回显，不进入 shell 历史，也不写入项目。脚本会立即调用服务端验真，只有显示“绑定并验真成功”才进入后续用户授权；仅本地保存但服务端返回 `client secret is invalid` 不视为完成。

### 1. 内容中间层

先将报告拆为可复用的内容中间层：

```text
章节与标题
信息块与状态标签
原生表格
流程图/UML
指标数据集
图表规格
来源与时间窗口
```

主文档保留结论、结构和阅读路径；明细字段字典和图表数据下钻到专题文档或伴随表格。

### 2. 写入前预检

```bash
lark-cli config show
lark-cli sheets +workbook-info --url "<表格 URL>" --as user --format json
```

检查工作簿、子表名称、行列范围、现有图表和写入身份。小表全量读取，大表按窗口读取；参与公式、排序或筛选的列至少采样 50 行。

### 3. Dry-run

```bash
python3 scripts/publish_lark_tracking_v2.py
```

默认在本地校验 3 个 typed table、样式和图表规格，不产生远端写入。官方 CLI 即使使用 `--dry-run` 也会先检查应用配置，因此未绑定阶段不把它当作本地校验器；绑定完成后再进入真实 API 预检与执行。

### 4. 批量发布

```bash
python3 scripts/publish_lark_tracking_v2.py --execute
```

发布器一次完成：

- 重建 `overview_kpi`、`event_quality`、`quality_gate`；
- 保留数字、百分比和空值类型；
- 应用表头、对齐、边框、列宽、行高和冻结规则；
- 创建 `event_quality` 原生横向条形图；
- 回读 3 个子表并校验行数；
- 回读图表列表并校验标题；
- 将不含凭证的审计结果写入 `data/outputs/lark-publish/YYYY-MM-DD/`。

### 5. 文档发布

文档结构优先使用飞书原生 H1/H2/H3、信息块、四列以内表格、流程图和任务清单。图表数据存放在关联表格，正文通过原生关联能力引用；旧版本只增加顶部历史说明和 V2 链接，不删除原内容。

### 6. 双重验收

API 验收：

- `+table-get` 返回 3 个目标子表；
- `overview_kpi` 4 行、`event_quality` 4 行、`quality_gate` 5 行；
- `GAMEEND` 为 112,635,044 / 7,030,603 / 6.24%；
- PV、MV、ASSET 缺失的计数保持空值，不用 0 代替；
- `+chart-list` 返回标题为“GAMEEND 是当前异常率尖峰”的图表对象。

浏览器验收：

- 桌面端和移动宽度下无明显截断；
- 表头、百分比、长文本换行和风险色正确；
- 图表不遮挡源数据；
- 主文档可搜索、复制、评论，正文不是图片；
- V2 和两个历史版本之间的跳转有效。

## 本项目目标与时效

# 数据分析报告产出规范（合并版）｜2026-08-20

本章节适用于 Waje 产品、用户、版本、渠道、活动、性能、KYC、投放和专题分析报告。飞书云文档是主阅读版本，Markdown 是项目存档；HTML/PDF 仅在明确提出时生成。

## 8. 分析前：先锁定决策问题

报告开始前必须写清：

1. 本报告要判断什么；
2. 哪些数据可以支持或否定这个判断；
3. 最终需要产品、研发、运营或数据团队采取什么动作。

版本、游戏或功能上线分析，默认回答：上线后是否改善核心指标、是否覆盖全部渠道、留存与付费是否同步、哪些变化可能由活动/投放/风控/故障造成。

首页核心结论必须包含专项主题，不能只写渠道排名或总体均值。

## 9. 标准分析框架

### 9.1 前后窗口

涉及上线或优化时，优先使用等长窗口：

```text
上线前窗口 → 上线节点 → 上线后窗口 → 渠道/包体/运行形态对比 → 结论与行动
```

默认记录：

- 上线前、上线后起止日期；
- 数据源修订号和读取时间；
- 参与比较的渠道、包体和运行形态；
- 同期活动、投放、风控、故障、埋点和版本事件。

### 9.2 分组维度

至少拆分 H5自然、PWA自然、H5 Facebook、H5 Google；需要时增加包体、版本、设备、媒体和活动维度。

H5/PWA自然流量不得直接合并判断产品优劣，必须同时比较规模、D1/D3/D7、付费率、首充率、C-T和运行入口。

### 9.3 指标链路

```text
新增规模 → D1/D3/D7/D15/D30 → 阶段衰减 → 付费率/首充率 → C-T或真实LTV → 行动建议
```

### 9.4 TC、RTP与资金异常专项

当报告主题涉及提充比升高、提现异常、Bonus、游戏回报或疑似羊毛时，固定采用：

```text
宏观资金与RTP核验
→ 游戏/渠道/版本/人群拆分
→ 高TC与大额中奖尾部贡献
→ Bonus与资产来源解释
→ 受限用户级账本核查
→ 正常波动 / 奖励影响 / 需复核 / P0资金完整性异常
```

- 不得仅凭高TC、单日RTP或少数大额提现认定Bug、刷子或游戏异常；
- 平台TC、首充后T+k TC和用户TC必须分别定义分母；T+k分母应使用窗口内全部成功现金充值，不能只用首充金额；
- RTP使用有效下注和最终派奖的服务端事实，不能替代提现、资产或账本解释；
- 只有出现无来源资产、余额不守恒、重复结算或订单/账本矛盾时，才升级为P0资金完整性异常；
- 玩家级明细只可在受限环境按匿名用户键核查，正式报告仅呈现脱敏聚合和原因分类。

详细口径与门禁见 [[../02-数据/Waje-TC异常、RTP与资产流水诊断框架-2026-08-28]]。

## 10. 统计口径与数据门禁

### 10.1 留存

- **所有面向业务的图表、表格和正文统一使用 `Dn Day` 命名。** `D1 Day` 为注册/首次访问当天，`D2 Day` 为次日，`D3 Day` 为第3个自然日；通用算法为 `Dn Day = cohort_date + (n - 1) 个自然日`。
- 不得直接复制不同平台的 `D1`、`D3` 等原始字段名。每个来源接入时必须登记“来源字段 → Dn Day → SQL 日期偏移”的映射：例如 Waje 生命周期“次留”映射 `D2 Day`、“3日留”映射 `D3 Day`；GA4 旧查询的 `D0+1` 映射 `D2 Day`，`D0+3` 实际映射 `D4 Day`，不得误写为 `D3 Day`。
- 数据源未按该映射重算前，相关结果标记 `blocked·Dn Day口径待重算`；禁止仅替换图表文案而不改变计算日期偏移。
- 每张留存图或表必须在就近备注中说明 cohort 的定义、`Dn Day` 的自然日算法、活跃事件范围，以及“应用回访 / 同游戏复玩 / 留存”的差异。
- D1、D3、D7、D15、D30只统计已经达到对应观察天数的注册用户；
- 未达到观察天数、源表无值或样本不足时显示 `N/A`；
- 不将未成熟用户当作流失，不补零；
- 前后比较优先使用等长窗口；
- 阶段衰减必须使用同一批注册用户：

```text
D1→D3 = 1 - D3 / D1
D3→D7 = 1 - D7 / D3
D7→D15 = 1 - D15 / D7
D15→D30 = 1 - D30 / D15
```

### 10.2 付费与价值

- 新增付费率、首充率、付费人数按来源口径分别展示；
- 分母或用户范围未确认一致时，不制作“新增→付费→首充”漏斗；
- 不用“新增人数－付费人数”推导免费用户；
- C-T只能作为来源价值字段做方向性对比；
- 没有订单收入、退款、奖励成本和统一币种分母时，不命名为真实LTV。

正文只保留结论，例如“Google累计C-T参考值最高，Facebook明显偏低”；具体口径放在就近备注。

### 10.3 数据质量门禁

出现以下任一情况，先标记 `N/A`、`部分数据`或`待核验`，不得继续推断：

- 日期缺失、重复或窗口不连续；
- 渠道、包体或版本映射未通过成熟样本验证；
- 前后窗口长度不一致；
- D7/D15/D30未达到观察天数；
- 付费分母、C-T来源或收入口径不一致；
- 活动、投放、风控、故障与版本节点高度重叠。

## 11. 正文结构与表达

### 11.1 首页

固定包含标题、数据范围、观察日期、3—5条核心结论和待行动项。核心数字、短板、增长和关键论断使用加粗及浅蓝/浅绿/浅黄/浅红高亮。

首页不放长篇方法说明、完整事件日志、复杂口径解释和“为什么选择这个窗口”等过程内容。

### 11.2 专项章节

按以下顺序组织：

```text
专项核心结论 → 关键数据 → 图表/表格 → 业务判断 → 优化动作
```

轻量化、版本或功能上线类报告必须包含：

- 上线前后等长窗口结果；
- 不同渠道/运行形态结果；
- 留存、付费和价值是否同步变化；
- 影响判断的活动、投放和故障因素；
- 是否可以形成因果结论。

### 11.3 附录

统计期间更新事件、字段解释、数据质量、公式、C-T边界、未成熟数据和待补埋点统一放在正文结论之后，并使用明确标题，如“附录：统计期间主要调整内容”。

### 11.4 面向业务读者的表达规则（强制）

最终报告要让业务、产品和研发直接读懂“能否下结论、为什么、下一步做什么”。避免只对分析人员有意义的术语。

| 不推荐写法 | 正式报告写法 | 使用原则 |
|---|---|---|
| 未成熟 | `未达到D3/D7/D15统计口径` | 必须写明具体观察日；`N/A` 旁注明原因，不把它写成流失或数据为零。 |
| 不直接写成产品优劣 | `不能直接下产品定论` | 同时说明不可比来源，例如入口、运行形态、流量结构或版本不同。 |
| 可观察 / 小样本 | `可观察`、`小样本（n=…）` | 状态必须紧邻数值和分母；样本不足时不使用强结论。 |
| 当前期 | `短期观察`、`截至…的累计追踪` | 说明数据截至日期，避免“当前”在后续阅读中失效。 |
| 首日/复访不成熟 | `D3未达到统计口径` | 对新上线游戏使用“上线后第N日”而非与老游戏累计值直接比较。 |

另外：

- 报告标题与章节标题要准确反映对象。若一组同时包含轻量化与非轻量化游戏，必须以最新产品游戏映射表为准；不得沿用“轻量化4款 / 非轻量化5款”等历史示例。当前Top Games口径为轻量化7款、非轻量化2款；分类变更时先更新映射表，再更新图例、表格、结论和本地存档。
- Top Games 是产品配置分组，不是天然的流量排名；必须在表头或就近说明中写明分组标准、游戏代码、窗口和观察状态。
- “结论与后续计划”优于泛化的“结论与行动”：每条结论后应落到可验证的产品、研发、数据或运营计划。
- 结论先写证据和范围，再写判断；禁止把页面浏览、路由进入、事件缺失或分组差异直接解释为游戏体验、加载性能或产品效果。
