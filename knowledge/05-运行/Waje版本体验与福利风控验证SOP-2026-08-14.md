# Waje 版本体验与福利风控验证 SOP｜2026-08-14

## 1. 目标与触发原则

每个确认发布的 H5、APP、热更、小游戏或关键运营/数值版本，都必须重新执行：

`发布证据 → 体验回归 → 数据质量核对 → 上下版对比 → 福利/资产风险验证 → 发布结论`

正式发布的唯一自动触发证据是 `Release Manifest`（`status=released`）。配置工作簿 revision、会议纪要、需求文档或聊天消息只能形成**候选信号**，不能代替实际上线确认。

Release Manifest 最少字段：

```json
{
  "release_id": "h5-2.18.0",
  "version": "2.18.0",
  "status": "released",
  "released_at": "2026-08-15T10:00:00+08:00",
  "source": "发版记录或已确认发布单",
  "surfaces": ["H5"],
  "change_summary": ["新手引导", "9003 优化"]
}
```

文件放入 `data/incoming/release/` 后，版本监测器会生成对应的体验与数据对比任务。清单不应包含账号、密码、Cookie、Token、手机号、支付信息或用户明细。

## 2. 每版交付物

| 交付物 | 作用 | 最低要求 |
|---|---|---|
| Release Manifest | 锁定版本、范围、发布时间和变更 | 版本/构建、端、包/渠道、配置 revision、变更、回滚版本 |
| 体验观察 JSON | 保存可比较的用户可见事实 | 无个人标识；按新手、留存、游戏、福利、资产、帮助记录 |
| 体验与数据对比报告 | 对比上一确认版本 | 体验差异、完整日指标、数据质量、P0/P1、回归结论 |
| 奖励风控回执 | 验证资产、资格和幂等性 | 单账户/测试环境、服务端证据、无生产套利行为 |

当前基线为 `prod-h5-baseline-2026-08-14`。由于页面没有暴露正式版本号，且样本是留存访客会话，它只是体验基线，不能替代正式发版 Manifest 或 Day 0 基线。

## 3. 体验矩阵

### 3.1 账户与新手主线

1. 新建 Day 0 测试样本：注册、登录、欢迎资产、引导、Mail、Daily Chip、任务、首局。
2. 留存样本：大厅、搜索、收藏、活动、账户、客服、帮助、版本升级与回流。
3. 资金与资产：余额类型、Coins/BonusChip、首充触点、绑定门槛、流水与资格说明。
4. 每条路径必须记录：版本、包/渠道、配置 revision、时间、结果、失败码、可见文案和对应事件/流水键。

### 3.2 游戏与系统模块

- 每个高优先级玩法至少一条正常最小闭环：`进入 → 可操作首帧 → 选场 → 下注 → 局内操作 → GAMEEND → 奖励/流水 → 余额`。
- 覆盖自研/重点玩法、第三方槽机、捕鱼、Crash、棋牌和 Coin Game；不以单局结果推导 RTP。
- H5 必测首屏、iframe/子游戏加载、弱网重试、返回大厅、活动弹窗、支付/提现入口与账户恢复提示。

## 4. 版本数据对比规则

1. **窗口**：发布前后各 7 个完整自然日；未完整日、全零异常日和未成熟 cohort 不进入结论。
2. **分层**：端、版本/构建、包体、渠道、归因媒体、地区、设备档位、网络、游戏、场次、资产类型、生命周期天数。
3. **核心指标**：启动/登录、游戏进入、首帧、首局、首注、匹配、GAMEEND、真实 RTP、资产流水、充值、提现、任务领取、D1/D7、付费/LTV。
4. **数据质量**：事件入库率、异常率、重复率、必填空值率、枚举错误率、延迟、`BET → GAMEEND → ASSET` 对账率。
5. **结论约束**：体验差异是线索；版本效果结论只以 BQ/服务端认证事实、稳定数据窗和明确分母给出。

## 5. 福利、数值与反薅羊毛测试

这里的“反薅羊毛”是授权 QA/风控验证，不是设计或执行获利策略。

| 维度 | 受控验证 | 通过标准 |
|---|---|---|
| 幂等性 | 同一账户正常重复点击、刷新、重登、网络重试 | `user + campaign + period` 最多一笔奖励 |
| 资格隔离 | 新手、首充、每日、邀请、Coins、BonusChip 的前置条件 | 服务端资格键、时间窗和次数限制一致 |
| 资产隔离 | 现金、奖励资产、Coins、流水和提现资格 | 资产类型、可用范围、有效期和提现限制一致 |
| 版本切换 | 热更、配置切换、回滚后重进活动 | 已领取状态不重置；不重复发奖、不丢奖 |
| 游戏结算 | 下注、结束、奖励、流水 | 可按 `round_id/unique_id + trace_id` 对账 |
| 风控联动 | 绑定、支付、提现、设备/账户限制 | 规则命中可解释、可审计，误拦截可复核 |

禁止事项：多账号或虚假身份、绕过手机号/KYC/反作弊、并发或脚本刷奖励、伪造支付、规避提现规则、在生产环境反复尝试领取或以外部提现获利。发现疑似问题时，立即停止该路径，在测试/预发环境使用受控数据复现，并由研发/风控修复后回归。

## 6. 风险评分与优先级

以“风险覆盖算法”排序，而非以提高玩家收益为目标：

```text
risk_score = 3×资金影响 + 3×可重复性 + 2×资格绕过可能性
           + 2×资产/流水不一致 + 1×版本切换影响
```

- **P0**：现金/奖励错账、重复发奖、提现资格绕过、下注/结算/流水不可对账。
- **P1**：任务或首充错误、资格状态不透明、版本切换重置、关键漏斗事件缺失。
- **P2**：帮助文案、弹窗频控、规则展示、非核心埋点和体验一致性。

## 7. 自动化与人工协作

- `scripts/run_release_experience_watch.py`：每天检查发布清单和配置 revision；只在 `status=released` 的清单出现时创建版本任务。
- `scripts/release_experience.py`：对两份脱敏体验观察 JSON 生成结构化差异与 Markdown 对比报告。
- 自动化只负责发现、建档、数据准备和非资金的正常体验检查。涉及真实支付、身份证明、提现或任何高影响资金操作，必须采用明确授权的测试/沙箱环境并由人工承担最终提交。
- 新版本体验完成后，用 `release_experience.py --baseline ... --candidate ... --release-id ...` 产出正式对比报告，并刷新知识图谱。

## 8. 发布结论门槛

- [ ] Release Manifest、版本/构建、端/包/渠道和配置 revision 均已确认。
- [ ] 新手、留存、核心游戏、福利、钱包、支付/提现门槛已完成对应体验证据。
- [ ] 关键事件和资产流水按版本维度可用并已通过质量门槛。
- [ ] 奖励幂等、资格隔离、资产类型、配置切换和结算对账回归通过。
- [ ] 发布前后完整日数据无 P0 异常；若有 P1/P2，明确影响范围、负责人、截止时间和回滚/止损条件。
