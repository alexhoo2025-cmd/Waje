### 1.2 H5 被确认为高优先级增长与体验课题

会议判断：APP 的日活和收入增长遇到瓶颈，H5 具有较大增长空间，但当前数据表现与体验均不足。明确的主要问题是：

1. 游戏加载引擎与网页资源偏大；弱网、低端机和高流量成本环境下，用户可能在进入首局前流失。
2. H5 D7 留存衰减快；纪要提及刷子流失、设备性能差是候选原因，尚不能视为已验证归因。
3. H5 的本地化题材与元素不足，和竞品存在产品设计差距。
4. 轻量化游戏已陆续上线，后续是否扩大投入应以数据效果验证为依据。

### 1.3 资源管控需要形成正式产品规范

会议提出将游戏资源体积前置为设计约束，并纳入美术与技术规范；可采用首屏分段加载、游戏中按需加载、可选下载大资源、音频复用/音乐库等方案。

> 待确认冲突：会议正文表述“300K–500K 上限”，会议待办表述“资源不超过 300K”。本知识库暂不将任何数值写成已生效标准；建议以 `≤300K` 作为待评审目标，并按首包、首屏、总资源、压缩后下载量四种口径分别验收。

### 2.2 H5 性能与新手链路的观测设计

```text
投放/自然来源
  → H5 落地页可见
  → 资源请求与首屏加载
  → 大厅可操作
  → 游戏入口曝光 / 点击
  → 游戏加载成功
  → 首局开始
  → 首局完成
  → 首充 / 后续留存

每一步均按：终端 · 设备档位 · OS/浏览器 · 网络类型/质量 · 地区 · 包体/版本 · 渠道 · 游戏 · 资源版本 分层。
```

**核心指标建议（首页不超过 10 项）**

| 指标 | 定义/口径 | 用途 |
|---|---|---|
| H5 首屏可见率 | 首屏可见用户 ÷ H5 启动用户 | 衡量入口到可用页面的损失 |
| 首屏 P50/P90 加载时长 | 从加载开始到首屏可见；按设备/网络分层 | 定位弱网、低端机和资源问题 |
| 游戏加载成功率 | 成功进入游戏 ÷ 游戏加载开始 | 区分入口点击与加载失败 |
| 新用户首局开始率 | 首局开始新用户 ÷ 新注册用户 | 衡量新手主路径可达性 |
| 新用户首局完成率 | 首局完成新用户 ÷ 首局开始新用户 | 衡量游戏可玩性和过程故障 |
| 新用户 0 局占比 | 统计窗口内 0 局新用户 ÷ 新注册用户 | 轻量化项目的直接结果指标 |
| 崩溃/关键错误率 | crash 或关键 error 用户 ÷ 启动用户 | 版本质量护栏 |
| D1 / D7 成熟留存 | 只纳入达到观察日的 cohort；未成熟显示 N/A | 判断长期价值，不受未成熟样本污染 |
| 首充率 | 首充成功新用户 ÷ 新注册用户；需标明成功/退款口径 | 验证商业化变化 |
| 授权可观测覆盖率 | 已授权、可进入行为分析样本 ÷ 启动用户 | 解释数据代表性，不代替行为指标 |

### 2.3 必须写入 PRD 和埋点评审门槛的内容

会议已明确新的文档规范应包含版本信息、变更日志、背景、范围、详细功能、非功能需求、埋点等。对涉及数据的需求，以下字段应成为发布门槛：

1. 目标指标、反指标和观察周期；不得只写“优化体验”或“提高留存”。
2. 事件名称、触发条件、属性字典、用户去重键、终端/版本字段、失败码与数据用途。
3. 功能开关、实验分组、配置版本和发布时间，以支撑发布后归因。
4. 资源验收字段：首包/首屏/总资源大小、资源版本、资源加载策略、压缩后下载量。
5. 数据授权与隐私边界：未授权用户不可补采行为数据；报表必须展示覆盖率和样本限制。
6. 埋点验收：测试环境事件校验、生产环境数据新鲜度、缺失率、与页面/服务端日志的对账规则。

## 4. 建议的下次评审清单

1. 确认本周提审包的版本号、两个功能开关、测试结论和发布日期。
2. 确认性能监控 P0 埋点清单、负责研发、测试验收人和首个数据回流日期。
3. 固化轻量化游戏清单、每个游戏资源版本/上架日/入口位，并定义上线评估窗口。
4. 对资源大小标准进行一次书面裁决：阈值、统计口径、例外、验收角色和不通过处理。
5. 确认“未授权上报用户群体”的合法观测边界；数据产品只输出覆盖率/偏差说明，不绕过授权采集用户行为。
6. 把用户分层需求中的“分层规则—策略—触达—结果”字段与数据平台/BQ表结构对齐。
