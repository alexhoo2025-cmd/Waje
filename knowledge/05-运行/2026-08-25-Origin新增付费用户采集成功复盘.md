# Origin 新增付费用户采集成功复盘（2026-08-25）

## 结论

本次相较上次成功的关键，不是单纯增加等待时间，而是把“筛选是否正确”和“查询结果是否已经刷新”拆成两个独立质量门禁，并使用 Chrome DOM/键盘接口完成虚拟下拉和多页面并行采集。

Google 商店 2026-07-13 新增人数为 Origin 4,078、本地保护基线 4,077，属于用户已确认可接受的单值源端微差。该差异已留在成熟样本修订证据中；7/26 及以前本地历史没有被改写。

## 上次失败的主要原因

1. Origin 下拉框是虚拟列表，首屏只渲染少量候选项。把当前可见项当成完整目录，导致内部值与显示标签错位。
2. 选择筛选条件后，结果表会延迟刷新。仅检查日期或行数，会把上一组筛选的旧表误认为新查询结果。
3. 没有要求 `aria-activedescendant`、内部选项值、显示标签和查询后内容指纹同时一致。
4. 发现异常样本后只做了停止，没有继续执行同一筛选复查、剩余候选搜索和源端版本差异判断。
5. 采用单页面串行操作，查询等待期间无法并行处理其它已确认任务。

## 本次成功因素

### 1. 筛选目录完整化

- 通过 DOM/键盘遍历虚拟下拉，而不是读取首屏可见项。
- 记录内部值与显示标签的对应关系：Facebook=`80`、Google 投放=`81`、Google 商店=`84`、AppStore=`58`。
- 每次选择后同时回读内部激活项和页面显示标签。
- 修正了 `PAWAJEBETH5 → wajebetH5`、`PAWAJEIOS → wajeios` 等实际页面别名。

### 2. 成熟样本矩阵

- 每个 Sheet 先查询 2026-07-12 至 07-13。
- 同时核对新增人数、付费率/人数、留存、TC、TX、首充等字段。
- 对 Google 商店 4,077/4,078 这种小差异记录为明确修订证据，不静默放行。
- 对 pww 的较大历史差异保留为源/基线修订项，不覆盖保护历史。

### 3. 查询刷新门禁

- 点击实际可操作的查询组件，而不是只点击“查询”文字节点。
- 日期控件使用当前可见日期面板和精确日期 `title` 选择，避免结束日期错选到下月。
- 每次查询至少连续读取两次完整表格内容。
- 日期集合、行数和内容指纹稳定后才标记 `ok`；否则标记 `query_stale` 或 `query_unstable_or_incomplete`。

### 4. 并行和分段采集

- 30 天拆成 5 个窗口：7/27–8/02、8/03–8/09、8/10–8/16、8/17–8/23、8/24–8/25。
- 使用 8 个已登录页面并行处理 8 个 Sheet，减少页面等待对总耗时的影响。
- 共完成 40 个正式窗口，每 Sheet 获得 30 个唯一日期。

### 5. 写入前后隔离

- 先固化原始 DOM 表格快照、筛选回执、窗口哈希和 source-data，再写 Excel。
- 输出新副本，原输入文件不动；飞书同步按本次要求跳过。
- 7/26 以前逻辑值哈希写前写后复核一致。
- 更新范围的 0 值单独清理，保留 zero-ledger；源快照仍保留原始 0。
- 写入后重新导入，通过 XML/Artifact 回读、字段、日期、样式、行高、列宽和错误扫描。

## 可固化为标准门禁

```text
完整选项目录

→ 7/12–7/13 成熟样本矩阵
→ 点击可操作查询组件

→ 分段并行采集
→ source-data/receipt/hash 固化
→ 本地新副本写入
→ 7/26 历史保护 + zero-ledger
→ 重新导入和格式验收
→ 再决定是否同步飞书
```

## 本次仍需保留的注意事项

- Origin 历史数据可能发生小幅重算，不能把任意历史差异都当作筛选错误，也不能未经证据覆盖保护区间。
- 近期留存字段的空值/0 值要区分“未成熟”与“查询失败”。
- 日期正确不等于查询成功，必须检查内容指纹。
- 视觉渲染器本次超时，但独立逻辑/格式验收通过；后续应继续保留有界超时并单独标记视觉阶段状态。
