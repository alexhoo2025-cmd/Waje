## 2. 今日任务链路还原

### 2.1 GM Lifecycle Pool v2 (Joint) 生命周期数据

**正确来源**：`Lifecycle Pool v2 (Joint)`，不是普通 `Lifecycle Pool v2`。

**实际操作链路**：

```text
已登录 GM 页面
  → 选择一个日期
  → 点击“查询历史记录”
  → 等待 3–4 分钟
  → 确认四个区块已返回
  → 导出汇总 / 详细 / 分游戏 / 活跃周期
  → 内容与行数校验
  → 新副本写入
  → 读回、勾稽、格式抽检
```

**有效经验**：

- 每个日期只能由页面上的 `查询历史记录` 真实触发；直接改输入框值会被页面状态回滚，不能作为查询证据。
- 查询等待期间不刷新、不重复点击。页面慢不是失败信号，重复点击才会制造队列和结果混淆。
- 3 个独立页面并发最合适：每页只负责一个日期，完成后立即归档四个导出，再投入下一日期。
- 导出文件不能按“下载顺序”归档。必须按“查询日期 + 四类报表 + 表头/内容哈希”归档。
- 详细奖池的写入范围必须限定生命周期 0–4；活跃周期限定生命周期 1–4；完整导出仍用于跨表勾稽。

**容易出错的点**：

| 风险 | 现象 | 正确控制 |
| --- | --- | --- |
| 报表入口混淆 | 普通 v2 与 Joint 数据口径不同 | URL、页面标题、左侧菜单名称三项同时确认 |
| 查询未真正触发 | 页面仍显示默认日期的数据 | 查询后检查表格日期集合而不是只看 Loading 消失 |
| 多页并发失控 | 标签页筛选相互混淆、重复下载 | 固定 3 页队列，每页绑定唯一日期与运行记录 |
| 日详情行错写 | 生命周期或游戏数不匹配 | 写前按 `5 × 游戏数`、4 行活跃周期以及跨表金额勾稽 |

### 2.2 起源 BQ-新增付费用户分析

**正确操作链路**：

```text
读取工作簿映射合同
  → 选择产品 Waje Special、TC 逻辑 累计利润(C-T)
  → 选择精确分包/媒体/渠道

  → 新 Excel 副本更新
  → 重导入逐项验证与历史哈希验证
```

#### PAWAJEBETH5 纠错案例

第一轮把别名和 `facebook` 关联，导致新增用户人数只有十几人；正确结果是数千人。最终确认：

| 检查项 | 7/12 | 7/13 | 结论 |
| --- | ---: | ---: | --- |
| 正确来源新增人数 | 3,322 | 3,161 | 与受保护历史完全一致 |
| 分包渠道 | `wajebetH5` | `wajebetH5` | 精确匹配 |
| 归因媒体/渠道 | 空 / 空 | 空 / 空 | 不允许从 Sheet 名推断 `facebook` |

样本中的终身、留存、付费率、TC/TX 等衍生指标出现 20 项源端重算差异。处理原则是：

- **身份字段必须严格一致**：日期、区服、新增人数是筛选确认的硬门槛。
- **重算指标必须显式记录**：写入 `source_revision`，列出基线值、当前来源值、字段、日期和原因。
- **受保护历史绝不回写**：即使当前来源重算了 7/12–7/13，也不修改 7/13 及以前工作簿数据。
- **正式窗口使用当前正确来源**：本次只将正确来源用于 7/14–8/17。

这比“所有字段必须完全相等”更符合运营报表的真实情况：前者用于确认筛选身份，后者用于追踪源端的历史修订。

## 3. 成功经验：应当固化为默认行为

### 3.1 查询、归档、写入分阶段

最有效的做法不是让浏览器一直开着等待全部完成，而是把工作拆成独立、可恢复的阶段：

| 阶段 | 产物 | 成功判定 | 失败后的恢复点 |
| --- | --- | --- | --- |
| 查询 | 页面日期、筛选条件、结果日期集合 | 结果日期恰等于所选窗口 | 从该页面重新提交，不影响已完成窗口 |
| 原始归档 | 原始导出/可见表格、字段表头、哈希、回执 | 日期完整、字段顺序正确 | 保留有效导出，只补失败窗口 |
| 数据合同 | `source-data.json` | 映射、样本、窗口、行数完整 | 不写 Excel；先补合同 |
| Excel 更新 | 新副本 | 只改目标日期/Sheet | 输入原件始终可回退 |
| 验收 | 读回、哈希、样式、错误扫描 | 所有门槛通过 | 不重新采集，只重跑写入/验收 |
| 飞书同步与格式 | 数据回读、百分比显示、行高 | 界面已保存 + API/可见抽检 | 不重新生成本地数据 |

这种切分将“慢查询”“数据错误”“格式错误”“渲染慢”隔离，避免一个后段问题触发全链路重做。

### 3.2 输入工作簿不可变、新输出可审计

本次有效的保护措施：

- 从不覆盖输入工作簿；只生成带日期范围的新副本。
- 每次输出记录输入 SHA-256、输出 SHA-256、来源清单 SHA-256。
- 检查 7/13 及以前受保护前缀的逻辑哈希。
- 检查其他 Sheet 的 worksheet XML 未变，避免“只改一个 Sheet 却误伤整本”。
- 新增日期行从相邻行克隆样式，避免日期、百分比、金额和条件格式变成 General。

### 3.3 把来源名称当作合同，而不是文本猜测

已固化的合同例子：

| 本地 Sheet/业务别名 | 精确分包渠道 | 归因媒体 | 归因渠道 |
| --- | --- | --- | --- |
| PAWAJEBETH5 / wajebetH5 | `wajebetH5` | 空 | 空 |
| WajeSpecial-facebook | `WajeSpecial主包` | `facebook` | 空 |
| pww | `wajeH5pww` | `facebook` | 空 |
| wajeH5ga-googlewords_int | `wajeh5ga` | `googleadwords_int` | 空 |

规则：

1. 名称相似只可产生候选，不能直接写入。
2. 候选必须经过成熟样本的身份字段验证。
3. 用户确认的名称别名必须立即写入映射合同和失败手册。
4. 下次运行只读取合同，不重新凭直觉解释名称。

| 失败/低效事件 | 直接原因 | 根因 | 后续强制规则 |
| --- | --- | --- | --- |
| PAWAJEBETH5 数据量级错误 | 多选了 `facebook` | 从名称推断筛选，而没有先用样本验证 | 分包、媒体、渠道三项都必须写入合同；三项空值也必须显式记录 |

| 浏览器操作效率低 | 多进程/多标签页，控制页与可见页可能不是同一页 | 浏览器状态被当成单一状态机 | 每次写入前确认“当前可见标签页、URL、Sheet、筛选值、已保存状态” |

| 飞书行高局部异常 | 曾有连续自定义行高（50px / 31px） | 表格批量操作未做行高收尾 | 数据区行高以 27px 为基准，写后抽检边界行与尾部 |
| 生命周期飞书无法接口回读 | macOS Keychain 临时访问阻断 | CLI 凭据存取依赖环境 | 不执行 keychain 降级；先用界面保存状态和视觉抽检，待凭据恢复后补 API 回读 |
| 宽表 PNG 渲染超时 | 渲染引擎处理宽表慢 | 把重型渲染放在交付关键路径 | 先完成读回/哈希/XML 样式验证；渲染超时标记为 `qa_pending`，不重新采集 |

## 5. 浏览器、接口与插件：正确的职责边界

### 为什么不能把浏览器自动化当作完整 API

当前内部系统没有被授权的、稳定的 Origin/GM 数据导出 API。出于安全和合规，不能从浏览器读取 Cookie、Token，也不能调用未公开接口。因此，浏览器自动化只能安全地承担：

- 使用已存在登录态；
- 操作可见筛选、日期控件、查询和公开导出；
- 读取可见表格、下载状态和页面显示值。

它不适合：

- 逐格更新工作簿；
- 在慢查询期间反复点击；
- 根据浏览器的“Loading 消失”推断数据正确；
- 把一个标签页的状态假设为另一个 Chrome 进程中的状态。

### 接口应承担什么

- **飞书读取 API**：读取 Sheet 清单、行高、单元格显示值、回读验证，效率高且稳定。
- **飞书写入 API**：一旦 `sheets:spreadsheet:write` 审核通过，应使用 `rows-resize`、`cells-set` 和 `styles-put` 批量完成行高和格式，不再依赖悬浮菜单。
- **本地脚本**：只处理已落盘的原始数据，负责日期覆盖、类型转换、样式克隆、哈希与异常扫描。

结论：**浏览器负责“拿到正确可见数据”，脚本负责“高效、可验收地更新”，接口负责“稳定同步与回读”。**

## 6. 下一次执行的标准作业流程

### A. 运行前（3–5 分钟）

1. 明确日期范围、时区、输入文件和新输出文件名。
2. 打开映射合同，确认每个 Sheet 的分包/媒体/渠道，其中空值必须显式写为 `null`。
3. 为本次运行创建 `run_id`、原始快照目录、`source-data.json` 和 `run-log.json` 路径。
4. 读取输入工作簿：Sheet 顺序、表头、最后日期、受保护历史哈希、模板行样式。
5. 确认 Origin/GM 页面已登录且当前页面就是可控浏览器中的可见页面。

### B. 查询与原始归档

1. Lifecycle：固定 3 页并发、1 日/页、30–45 秒轮询、完成即导出四份原始文件。
2. Origin：先 2 天样本；正式查询默认连续 7 天/窗口、2–3 页并发、20–30 秒轮询。
3. 每个窗口必须记录：筛选条件、页面 URL、提交时间、完成时间、结果日期、字段表头、原始文件哈希。
4. 未满足行数/日期/字段条件的窗口标记 `blocked` 或 `degraded`，禁止补零。

### C. 数据门槛

1. 身份字段：日期、区服、新增人数必须与成熟样本严格一致。
2. 衍生指标：若来源重算，生成 `source_revision`；不得静默放宽所有校验。
3. GM Lifecycle：四表的行数、生命周期、游戏唯一性与下注/盈利/人数勾稽必须通过。
4. 合同不完整、样本不通过、来源字段变化、日期缺失/重复时停止写入。

### D. 本地更新与验收

1. 新副本写入目标日期与目标 Sheet，绝不改输入文件。
2. 续写行复制相邻同类行的完整样式；比例、金额、日期都保持数值类型。
3. 重导入后检查：来源值、日期唯一、历史哈希、Sheet 顺序、非目标 Sheet、公式错误。
4. 数值验证通过后再做边界和尾部视觉 QA；渲染超时只标记 `qa_pending`，不回退正确数据。

### E. 飞书同步与格式治理

1. 先同步数值，再检查显示格式；比例字段必须显示为百分比，不能显示长小数。
2. 所有数据区行高统一 27px；保留表头、列宽、条件格式和数据值。
3. 写入后通过 API `sheet-info` 回读；API 不可用时，必须保留界面“已经保存到云端”和边界截图证据，并在恢复后补回读。

## 7. 可量化的效率与质量指标

后续每次手动运行都应记录以下指标，连续 4 周后可决定是否投入 API/插件改造：

| 指标 | 目标 | 计算方式 |
| --- | --- | --- |
| 筛选一次通过率 | ≥ 95% | 首次样本验证通过的 Sheet / 全部 Sheet |
| 错误筛选拦截率 | 100% | 写入前被样本拦截的错误筛选 / 发现的错误筛选 |
| 重复查询次数 | 0 | 同一窗口重复提交次数 |
| 原始快照完整率 | 100% | 有回执、表头、日期集合、哈希的窗口 / 完成窗口 |
| 本地写入一次通过率 | ≥ 95% | 不需重跑写入的成功输出 / 输出总数 |
| 非目标 Sheet 误改数 | 0 | XML/哈希变化的非目标 Sheet 数 |
| 格式回归数 | 0 | 百分比/行高/日期格式异常数 |
| 从查询完成到交付的时间 | 持续下降 | 写入、验收、同步阶段耗时 |

### 本次实际执行经验
