# 知识图谱与代码图谱诊断报告

## 技术摘要

当前项目的图谱生成链路可正常执行，但实际能力仍处于“文件关系图”阶段：知识图谱主要依赖 Markdown 双向链接，代码图谱主要是文件/资产级关系，尚未覆盖资讯采集、定时抓取、数据清洗、分析任务、报告生成和 Agent 调度之间的执行依赖。

评估基线（2026-08-03，报告生成前）：28 个节点、37 条关系；其中 19 个知识节点、9 个资产节点，26 条双向链接、11 条普通文件链接。所有已生成关系的端点均存在，但图谱有 11 个连通分量，最大分量仅包含 18 个节点，存在 10 个孤立节点。

结论：当前系统“能运行、可导航、可作为知识库起点”，但还不适合作为分析项目任务编排、脚本维护和自动化执行的可信图谱。优先级最高的是修复链接解析与旧索引断链，然后建立资讯采集—数据处理—分析—报告—知识库更新的脚本体系，并为每个任务记录输入、输出、依赖、调度和失败恢复方式。

## 1. 运行与覆盖检查

| 检查项 | 结果 | 判断 |
|---|---:|---|
| 图谱生成命令 | 成功 | `python3 tools/build_graph.py` 可运行 |
| 节点/关系 | 28 / 37 | 规模较小，适合当前项目 |
| 节点类型 | 知识 19、资产 9 | 分类过粗，缺少指标、事件、任务等类型 |
| 关系类型 | wikilink 26、link 11 | 以文档导航为主 |
| 已生成关系端点缺失 | 0 | 当前 JSON 内部完整 |
| 连通分量 | 11 | 主图之外存在多个孤立节点 |
| Markdown 文件属性 | 20 个文件中 16 个有 frontmatter，15 个有 type | 仍有索引、参考和欢迎页未纳入统一元数据 |

### 当前已覆盖的高价值内容

- 产品、竞品、数据平台、埋点地图和起源语义层已经形成基本关联。
- 起源平台盘点中已经沉淀了数据质量、ROI、LTV、报表、埋点和权限边界。
- `tools/build_graph.py` 可扫描 Markdown 链接以及 Python/JavaScript/TypeScript 相对导入。

### 当前未覆盖的关键内容

- H5 真金游戏的稳定、流畅、本地化、低端机和弱网验收标准尚未形成独立知识节点。
- 指标、事件、页面、模块、报表、数据源和业务结论之间还不是结构化实体关系。
- 当前仓库只有 `tools/build_graph.py` 一个项目脚本，没有发现资讯收集、定时抓取、数据清洗、分析脚本、报告生成脚本或 Agent 编排脚本。
- 因此当前没有可供代码图谱追踪的脚本调用链、任务依赖、输入输出和调度关系。

## 2. 主要问题与影响

### P0：链接解析规则会低估或误判关系

当前脚本把“不以 `.` 开头”的普通 Markdown 链接按项目根目录解析，但 Markdown 相对链接应以当前文件所在目录为基准。结果是 `knowledge/README.md` 到现有 `knowledge/02-数据/...` 文件的链接被漏识别，同时部分指向根目录资产的链接又可能被误判为有效。

按正确的 Markdown 相对路径语义复核，当前存在 26 个目标不存在的链接引用（包含重复引用）；另有 2 个知识库内实际存在的路径被脚本误判为无法解析。`knowledge/README.md` 与 `knowledge_README_updated.md` 还保留大量已经不存在的历史文件链接。

**影响：**图谱边数被低估，Obsidian 导航入口不一致，Agent 可能把过期资料当作可用知识。

### P0：知识库入口重复且缺少唯一事实来源

当前同时存在 `knowledge/README.md` 和根目录 `knowledge_README_updated.md` 两个历史索引；前者包含旧资料清单，后者也存在重复内容和失效链接。新增资料没有统一回填到一个 canonical MOC。

**影响：**用户不知道从哪里进入，知识维护容易出现重复、过期和遗漏。

### P0：分析项目的自动化脚本体系尚未形成

扫描范围虽包含 `.py/.js/.ts/.html/.json`，但当前项目实际只发现 `tools/build_graph.py`。没有资讯收集、定时抓取、数据清洗、分析、报告生成和任务编排脚本，因此现有图谱不能回答：哪个任务生成哪个报告、某个数据源变化会影响哪些分析、失败后如何重跑、哪些任务依赖外部数据。

**影响：**当前只能维护文档和资产关系，不能有效支持分析项目的自动化执行、任务复用和代码变更影响分析。

### P1：孤立节点过多，但系统没有区分“有意孤立”和“异常孤立”

当前孤立节点包括模板、工具脚本、语义层参考文件、`.vscode/settings.json` 以及 Obsidian 默认欢迎页。其中模板和工具可以是有意孤立，但语义层 references 理应连接到对应的技能说明或数据平台节点。

**影响：**图谱健康度无法自动判断，孤立节点会被误认为未维护内容。

### P1：图谱没有时效、可信度和来源健康检查

现有 frontmatter 有 `status/updated/sources` 等字段，但生成器没有校验：来源是否存在、更新时间是否过期、结论是否有证据、指标是否有口径、平台快照是否为完整日。

**影响：**知识图谱可以导航，但不能保证知识适合直接用于产品和数据决策。

## 3. 建议的目标架构

### 知识图谱

将文件关系升级为业务实体关系：

```text
产品/玩法 → 用户旅程 → 指标 → 数据平台/报表 → 证据 → 结论 → 任务/实验 → 结果
```

建议至少支持以下实体类型：`product`、`gameplay`、`platform`、`metric`、`event`、`report`、`source`、`issue`、`decision`、`task`、`experiment`。

### 分析项目代码与任务图谱

未来脚本体系形成后，建议形成：

```text
数据源 → 采集脚本 → 原始资料 → 清洗/标准化 → 分析脚本 → 报告/看板 → 知识库 → Agent/任务
```

其中 H5 真金游戏是分析对象，相关脚本应重点沉淀：产品体验、弱网稳定性、充值/下注/结算/提现、竞品资讯、用户反馈和性能指标。

## 4. 优化路线

### P0：本周完成

1. 拆分 `resolve_markdown_link` 和 `resolve_wikilink`，分别使用 Markdown 相对路径与 Obsidian 链接规则。
2. 增加 `link-audit.json` 或 `link-audit.md`，输出断链、误链、重复链接和孤立节点。
3. 确定唯一入口，例如 `knowledge/00-索引/项目首页.md`，把两个旧 README 改为重定向说明或归档索引。
4. 清理历史索引中的失效链接；保留暂时缺失的资料时，标记为 `待补充`，不要伪装成已存在文件。

### P1：一至两周完成

1. 建立 H5 真金游戏专题节点，记录低端设备、弱网、页面状态、资金请求幂等、白屏、崩溃和恢复标准。
2. 建立指标与埋点实体：指标定义、计算公式、数据源、时间粒度、负责人、更新时间和可信度。
3. 将起源语义层 references 改为可解析的 Markdown 链接，打通平台盘点、语义层、埋点地图和报表目录。
4. 为节点增加 `freshness`、`confidence`、`owner`、`source_status` 和 `last_verified`，在生成阶段进行校验。
5. 将模板、工具、配置、欢迎页标记为 `structural` 或加入排除规则，避免与业务知识孤立节点混在一起。

### P2：脚本体系形成后完成

1. 使用 AST 或静态分析建立 Python/JS/TS 脚本的模块、函数、import、CLI 参数和文件读写关系。
2. 解析任务配置、定时配置、数据源清单和报告清单，建立脚本到数据源、分析结果和报告的血缘。
3. 建立任务版本、运行记录、失败原因和重跑入口，支持“某个来源更新后需要重跑哪些任务”的查询。
4. 在脚本体系成熟后，再接入 Tree-sitter/LSP，补充函数级依赖和复杂代码调用关系。
5. 增加 CI/本地检查：断链、重复节点 ID、缺少必填属性、过期来源、生成文件与脚本不一致时阻断发布。

## 5. 建议的自动化验收标准

- 图谱生成成功且输出时间不超过设定阈值。
- 所有关系的 source/target 都存在。
- 断链数量为 0，或每条都明确标记为 `待补充`。
- 业务知识节点必有 `type/status/owner/updated`。
- 指标、埋点和结论节点必须有来源或验证计划。
- 关键 H5 资金链路节点必须能关联到需求、埋点、报表和监控指标。
- 生成结果包含 `schema_version`、`generator_version`、`source_hash` 和 `generated_at`。

## 6. 限制与待确认问题

- 本次为本地文件和生成脚本审计，未能在 Obsidian UI 中完成视觉交互验证，因为当前 Computer Use 权限未授予；已验证配置 JSON、脚本语法、图谱输出和关系端点。
- 未读取 H5 业务源码、SDK、CI、数仓、SQL 或线上监控，因此不能评估真实运行时性能和函数级代码依赖。
- 需要确认 `waje_data/欢迎.md` 是否为临时 Obsidian 默认文件；确认前不建议删除。
- 需要确认旧 README 中缺失的专题文件是否位于其他分支、外部资料库或已废弃。
