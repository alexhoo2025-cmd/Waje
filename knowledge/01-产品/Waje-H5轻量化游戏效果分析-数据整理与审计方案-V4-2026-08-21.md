# Waje H5轻量化游戏效果分析 V4：数据整理与审计方案

> 数据审计日：2026-08-21；起源产品：Waje Special。本文是后续专题分析的正式取数、对账和结论边界，不重复生成已有新增用户留存与付费结果。

## 核心判断

当前可以可靠回答两类问题：

1. **不同渠道和运行形态的新增、留存、付费、局数和价值表现是否不同。** 这部分以起源 BQ 服务器报表为准，新增用户数据直接复用既有 V2 基线。
2. **轻量化游戏的入口、开始、结束和结算是否存在行为断点。** 起源敏捷分析已有相关事件，可先建立聚合漏斗。

当前不能直接回答“某一款轻量化游戏导致留存或付费提升”：缺少标准化 `game_id`、入口位、加载完成、可下注、真实版本、配置版本、设备网络和前端异常等关联字段。此类结论只能标为观察性关联，不能写成因果。

<callout emoji="⚠️" background-color="light-red" border-color="red">
<p><b>当前最大技术阻断：</b>起源“设备监控”报表的 BigQuery 查询报 <b>Column name app_id is ambiguous</b>，页面性能、网络、版本和游戏体验均为 No Data。修复前不能将轻量化问题归因至低端机、弱网或设备版本。</p>
</callout>

## 一、分析决策与比较框架

本专题要判断：轻量化游戏是否改善下列链路，且改善是否覆盖 H5自然、PWA自然、H5 Facebook、H5 Google。

```text
合格新用户
→ H5首页/游戏入口曝光
→ 入口点击
→ 游戏开始
→ 游戏结束/结算
→ 当日复玩与局数深度
→ D1/D3/D7留存
→ 首充/复充与价值
```

比较分两层：

| 层级 | 比较方式 | 目的 | 结论边界 |
|---|---|---|---|
| 轻量化组合效果 | 上线前 2026-06-16—07-13 vs 上线后 2026-07-14—08-10，等长28天 | 观察组合上线后的整体方向 | 同期有KYC、投放、活动和故障，只能说明关联变化 |
| 单游戏效果 | 同端、同渠道、同版本下，实际进入目标游戏的用户与可比用户对照 | 识别Limbo、Keno、Color Dice、Hilo、Plinko的行为差异 | 必须具备game_id、入口、版本和会话关联后才可执行 |

新游戏节点：Limbo 9008于7月14日上线、7月15日下线、7月16日恢复；Keno于7月23日上线；Color Dice 9003于7月29日上线；Hilo、Plinko于8月21日上线。Hilo、Plinko的D1/D3/D7均暂不具备观察条件，统一显示 `N/A`。

## 三、当前审计发现

### 1. 新增用户基线可复用，但付费口径必须拆开

既有 V2 已完成 H5自然、PWA自然、H5 Facebook、H5 Google 的同日注册用户留存、来源付费率、首充率和 C-T 参考值分析。本轮不重新导出或改写这些数据。

保留以下规则：

- 新增付费率、`新增付费人数 ÷ 新增人数`、首充率分别展示；不可构造“新增→付费→首充”漏斗。
- C-T为来源累计利润字段，用于同口径方向比较；没有订单收入、退款/冲正、奖励成本和统一币种分母时，不称为真实LTV。
- 四渠道共同完整日期截至2026-08-16；H5自然虽到8月17日，正式横向比较仍统一截止至8月16日。

### 2. 起源敏捷分析能够建立一段漏斗，但中间可玩环节缺失

事件中心已发现：Web页面加载时长、Web元素点击、Web浏览页面、模块曝光、模块点击、游戏开始、游戏结束、XZ结算奖励、用户首充和支付成功。

这意味着可先分析：

```text
入口点击/模块点击 → 游戏开始 → 游戏结束 → 结算奖励
```

但没有`game_ready`、`bet_ready`、前端错误、重试、Web Vitals、标准`game_id`和真实H5版本。因此“点击但没玩起来”的问题尚不能精确拆分为资源加载、权限、弱网、玩法放弃或下注失败。

### 3. 游戏BQ报表的H5筛选尚未通过结果验证

现场在 `BQ-游戏概况` 选择 `wajeh5ga + googleadwords_int` 后，结果行仍显示全产品级 `Waje Special` 规模。当前不能判断是筛选映射、查询触发还是报表维度问题；在使用成熟日期与已知H5样本完成核验前，不引用任何“按H5 Google筛选”的游戏参与、局数或收益结论。

### 4. 设备监控是最优先的数据修复项

设备监控已具备设备健康、核心业务链路、页面性能、稳定性、网络质量、设备与版本、游戏体验和异常告警八个页面；筛选项含手机品牌、浏览器品牌、APP版本、终端、时间周期和分包渠道。

但当前后台SQL出现 `app_id` 字段歧义，所有指标返回 `No Data`。在修复并回填至少14个完整日之前，不能输出“低端机、网络、版本导致轻量化效果变化”的结论。

### 5. GA4可解释流量结构，不能解释游戏闭环

GA4在2026-08-20已验证90天页面、来源、设备、浏览器、操作系统和会话聚合可用；2026-08-21已确认连接 `waje-analytics-readonly`，仅开启每日导出、无事件排除、未开启用户数据导出。当前Sandbox尚未出现 `analytics_504208609` 数据集，首张日表生成前仍以GA4聚合报表为准。游戏加载、可玩、首局、结算、前端异常、网络、真实版本和`game_id`仍缺。

GA4与起源只能在同日期、渠道、端和设备分组层面进行交叉验证，不能拼接用户级身份。

| `fact_game_funnel_daily` | 日期×游戏×渠道×端×阶段 | game_id、事件、入口、端、版本 | 曝光、点击、开始、结束、结算 | 部分可用 |

## 五、质量门禁与取数规则

| 门禁 | 规则 | 不通过时处理 |
|---|---|---|
| 完整自然日 | 使用所有来源共同完整的最后一个自然日；当前日不参与趋势 | 标记`immature`，不补0 |
| 留存成熟度 | D1/D3/D7/D15/D30仅纳入已达到对应观察天数的同日注册用户 | 显示`N/A` |
| 同源对账 | 起源与飞书/Excel同筛选新增人数需完全一致；比例差≤0.01pp | 停止更新并保留差异证据 |
| 漏斗单调性 | 后一阶段用户数不得高于前一阶段 | 超过0.5%即标记`blocked` |
| 事件关联 | 入口点击→游戏开始/结束关联率目标≥98% | 不足时不得解释为玩法偏好 |
| 关键字段 | game_id、端、渠道、版本、配置版本完整率目标≥99% | 不能做单游戏或版本判断 |
| 价值口径 | C-T与真实收入分开 | 不将C-T命名为LTV |
| 跨源比较 | 起源与GA4使用统一时区和日期边界 | 仅比较趋势/覆盖率，不要求用户数相等 |

## 六、起源敏捷分析取数模板

### 模板A：入口到游戏开始

`Web元素点击或模块点击 → 游戏开始`，转化窗口30分钟；按分包渠道、归因媒体、终端、页面/模块属性和游戏属性切分。

用途：区分“用户没被入口吸引”与“点击后没进入游戏”。

### 模板B：游戏开始到结算

`游戏开始 → 游戏结束 → XZ结算奖励`，转化窗口30分钟；按`game_id`、玩法、渠道、端和版本切分。

用途：定位已启动后的中断、异常结算或玩法流失。

### 模板C：游戏开始后的留存

以“游戏开始”为起始事件，以“用户活跃事件/游戏开始”为回访事件，查看D1、D3、D7。起始事件必须按目标`game_id`过滤。

用途：判断进入某游戏与后续活跃是否相关；未补齐用户进入前特征时，只能说明关联。

### 模板D：局数深度与后续留存

使用 `BQ-局数分布及留存`，固定比较0局、1局、2–3局、4–10局和11局+。

用途：验证轻量化是否真正降低0局和提升首局后的持续参与。

## 七、P0修复与埋点需求

| 优先级 | 问题 | 要求 | 验收指标 |
|---|---|---|---|
| P0 | 设备监控SQL失败 | 统一或显式限定`app_id`来源，修复后回填14日 | 无`app_id is ambiguous`；各页可返回数据 |
| P0 | 无可玩链路 | 新增`game_load`、`game_ready`、`bet_ready`、失败码和重试事件 | 点击→可玩关联率≥98% |
| P0 | 无单游戏关联键 | 事件写入`game_id`、`round_id`、`entry_context_id`、`session_id` | 可按游戏串联入口、首局、结算 |
| P0 | 无版本/配置复盘 | 写入`h5_build`、`release_id`、`config_version` | 可拆分上线前后、灰度和回滚 |
| P1 | 无设备/网络归因 | 写入设备档位、浏览器/WebView、网络类型、RTT、下行 | 可定位低端机与弱网问题 |
| P1 | 价值口径不统一 | 提供成功支付、退款/冲正、奖励成本和统一币种收入 | 可计算真实D7/D30 LTV |

## 八、交付与下一步

本轮交付的是数据整理、审计和取数框架，不是新的轻量化效果结论报告。

后续正式分析按以下顺序执行：

1. 数据开发修复设备监控SQL。
2. 导出游戏、玩法、局数、收益、场次和TC详情的聚合数据，并登记每个筛选和时间窗。
3. 按敏捷模板运行入口、首局、结算和留存查询，不保存书签。
4. 刷新GA4聚合数据；若BigQuery每日导出可用，补充事件参数和页面性能审计。
5. 通过质量门禁后，产出“轻量化游戏效果分析V4”飞书主报告和Markdown存档。
