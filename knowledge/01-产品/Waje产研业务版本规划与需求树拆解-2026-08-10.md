# Waje 产研业务版本规划与需求树拆解｜2026-08-10

## 1. 文档范围与采集说明

本笔记整理 Lark《产研业务版本规划》目录及其公开可见的版本/需求子页面，覆盖 1.0.0—2.19.0 版本主线，以及用户分层、投放归因、Ares、外呼客服、活动奖励、财务数据、版本发布和渠道接入等需求。

- 采集入口：[产研业务版本规划](https://ksg964l11fam.sg.larksuite.com/wiki/HSuvwP8nHi0eOjkVJyHlxnTkgWb)。
- 采集日期：2026-08-10；页面以当前可见目录和正文为准。
- 文档性质：需求池、版本目录、PRD、原型和实现方案混合，不等同于已上线功能或生产数据事实。
- 安全处理：页面中出现的像素 ID、访问令牌、服务账号密钥等配置内容未复制到知识库；只保留其业务用途和字段类型。
- 版本状态：`规划中`、`进行中`、`草稿`、`已完成`来自页面标题，未进一步用发布报告或代码版本核验。

## 2. 一句话结论

Waje 的版本演进不是单纯增加玩法，而是沿着“投放获客 → H5/APP 首次体验 → 首充与游戏 → 用户分层运营 → 触达与奖励 → 复充/留存 → 财务与投放归因复盘”的经营闭环逐步补齐基础设施。当前 2.19.0 的核心转向是把规则型用户分层升级为“模型人群 + 通知/奖励闭环”，但需求文档仍处于产品定义、原型或局部建设阶段，数据事件、接口契约、验收指标和生产状态尚未统一。

## 4. 需求树与能力地图

### 4.1 用户生命周期与场景运营

核心流程已经明确为：

```text
判断用户场景状态
→ 匹配运营策略
→ 计算奖励档位
→ 选择触达渠道
→ 发放权益/发送消息
→ 记录触达结果
→ 回收转化数据
```

基础场景包括：

| 场景 | 页面定义 | 运营目标 | 应追踪的后续指标 |
|---|---|---|---|
| 新注册未首充 | 注册后 N 分钟内未充值 | 促成首充 | 首充率、首充时延、首充金额、首充后下注率 |
| 首充后未游戏 | 首次充值后 N 分钟内未投注 | 引导进入核心玩法 | 充值后首局率、进入玩法时延、首局后 D1 留存 |
| 首充未复充 | 首充后 M 分钟内未发生第二次充值 | 刺激复充 | 复充率、复充时延、D7 付费留存 |
| 活跃未充值 | 当日登录/游戏但未充值 | 促进付费 | 活跃转付费率、触达后充值率、增量成本 |
| 充值未游戏 | 当日充值 M 分钟后仍未投注 | 促进付费后的游戏转化 | 充值后下注率、首局耗时、余额消耗/回流 |
| 当日赢钱/输钱 | 按当日投注与回收判断净结果 | 促进复投或安抚留存 | 净输赢、复投率、流失率、奖励成本 |
| 历史高价值沉默 | 历史充值/投注高但近期未活跃 | 召回 | 召回率、召回后付费、召回成本、回归后留存 |

文档中给出了一套基础计算示例：

```text
当日累计投注 N = sum(n1 + n2 + ... + nn)
当日累计回收 M = sum(m1 + m2 + ... + mm)
当日收益率 P = M / N
```

这里的 `P` 更接近用户级当日回收/投注比，不能直接替代理论 RTP，也不能与 GM 的基础真实回报比、完全真实回报比混用。后续必须明确用户收益率、游戏 RTP、平台 GGR/净收入的口径边界。

### 4.2 用户分层 1.0 → 1.1 → 1.2

- V1.0：把场景模板、通知渠道、奖励和 H5/APP 奖励提醒/领取弹窗放进运营后台，目标是建立规则型触达闭环。
- V1.1：页面元信息标注为 P0、产品定义与交互原型、L1 需求与原型验证；明确基于 V1.0 增量迭代，且不代表接口、真实数据、模型服务或生产上线已经完成。
- V1.2：引入用户预测模型，把产品事件、用户属性、时间范围、基础人群、模型和执行周期作为输入，输出人群快照、模型批次、单用户预测结果、模型人群和用户场景。

这意味着未来分析必须保存“人群快照/模型批次/策略版本/触达批次”，否则无法判断某次奖励或通知带来的真实增量效果。

### 4.3 投放、Ares 与素材数据

投放侧逐步形成如下链路：

```text
素材库 Material_ID
→ 广告平台广告/素材层级
→ URL 参数（如 m_id、utm_source）
→ H5/APP 注册与行为事件
→ 归因平台/投放消耗
→ 素材、脚本、标签和员工绩效分析
```

《投放素材数据体系》明确推荐以唯一素材 ID + URL 参数打通 Meta/Google 与站内数据。Ares 的《流量分配机制&落地页配置》则定义主链接跳转到次链接，并按流量比例控制用户量，同时要求记录主链接/次链接的人数和次数。

需要特别注意：页面中出现的渠道参数、像素配置和归因应用字段只作为“字段/用途说明”保留，具体令牌和密钥不得进入知识库、报表、日志或代码。

### 4.4 财务、支付与经营报表

财务报告需求明确区分两类结果：

| 口径 | 时间依据 | 用途 |
|---|---|---|
| 流水口径 | 真实收付款时间 | 现金流、账户余额、对账 |
| 财务口径 | 业务真实发生时间、计提和分摊 | 管理报表、利润分析和经营判断 |

预期接入银行流水、OPay/PalmPay、充值明细、付款审批、报销表、Excel/CSV、Lark 表格和 API 同步数据。每个来源需要维护来源名称、来源类型、同步方式、字段映射和清洗规则。

这与当前数据平台的 MySQL/BQ 分工可以对齐：系统权限、事件定义和配置放在 MySQL；统计事实、流水和聚合结果放在 BQ；看板通过统一语义层消费，禁止把客户端订单意图当成财务事实。

### 4.5 H5 留存与用户调研

《Wajegame H5 留存低问题盘点&用户调研》已经按队列拆解留存问题：

- H5 进入后未开始游戏：为什么没有进入首局？
- 首局后流失：为什么首局没有带来继续玩的动力？
- 当天多局但次日未回：为什么没有形成次日回访？
- 充值后流失：支付、提现、信任、输赢体验哪一环出问题？
- 广告点击后快速离开：投放承诺和实际 H5 是否不匹配？
- 活跃留存用户：他们为什么愿意留下？
- 创建/未创建桌面快捷方式：快捷方式是否影响回访和信任？

该拆法可直接转成留存诊断漏斗：

```text
广告点击
→ H5 加载成功
→ 注册/登录
→ 进入玩法
→ 首局开始
→ 首局结束
→ 次日回访
→ 充值
→ 复充/持续游戏
```

### 4.6 外呼、客服、代理与社交增长

外呼系统从 1.0 到 1.6 多次迭代，关注手机号扩展、任务分配/预分配、绩效计算和客服用户信息；代理模式从模板化配置逐步进入业务运营。活动侧包含转盘概率抽奖、非洲杯预测分奖、邀请好友、奖励模板和活动复制。

这一能力群的共同问题是“触达动作有记录，但转化和成本回收需要统一口径”。外呼任务、客服会话、邀请关系、奖励发放、充值和投注需要统一使用用户 ID、活动 ID、触达批次 ID 和归因 ID。

### 4.7 版本、渠道和风控基础设施

- 版本发布：多版本发布基础功能、商店打包、OPPO/小米/传音渠道包，说明版本差异已经是经营分析维度。
- 归因：Adjust 的 ICM 排查文档要求 SDK、Google ODM、概率模型、归因窗口和 post-install 事件协同配置；这些是文档要求，仍需研发按实际账户和 SDK 版本核验。
- 风控：2.18.0 纳入用户封禁、提现记录入口和国家 IP 限制，说明生命周期运营必须与提现风控/封禁状态联动。
- 商店反馈：Google Play Developer API 需求希望接入评论数据，作为渠道和产品体验反馈来源。

## 5. 版本演进的核心判断

### 判断一：产品重心由“活动功能”转向“用户经营系统”

1.0—1.5 以活动、外呼、投放和落地页为主；1.6—1.11 开始增加业务打点、财务、素材、留存和行为预测；2.18—2.19 则把用户分层、通知中心、奖励和预测人群纳入后台。下一阶段的核心不是继续堆活动，而是验证每个场景是否产生可归因的增量收入、留存和风险收益。

### 判断二：数据链路已经出现，但还没有统一的经营主键

文档中同时出现用户、素材、渠道、广告、订单、奖励、外呼、模型批次和流量分配等对象，但尚未看到统一的主键/事件版本/策略版本规范。建议至少统一：`user_id`、`event_id`、`campaign_id`、`material_id`、`attribution_id`、`order_id`、`reward_id`、`segment_snapshot_id`、`model_batch_id`、`touch_batch_id`。

### 判断三：需求成熟度差异大，不能按“版本标题”判断上线

部分页面明确标注 P0、PRD、原型和 L1；部分页面只有标题或截图；部分已完成版本仍需通过发布报告、代码版本、事件接收和数据结果验收。因此知识库和周报需要同时记录：需求状态、开发状态、发布状态、数据可用状态、业务结果状态。

### 判断四：生命周期运营必须以数据闭环为验收条件

“能配置场景/奖励/通知”不等于“能优化生命周期”。最小可用闭环应能回答：触达了谁、为什么触达、发了什么、成本多少、是否领取、是否下注/充值、增量是多少、是否引发投诉/提现/风险。

## 6. 与现有起源/GM/数据平台的对接建议

### 6.1 统一事件与事实层

| 业务对象 | 推荐事实源 | 起源事件/数据对象 | 关键对账点 |
|---|---|---|---|
| 用户注册/登录 | 服务端用户事实 + 客户端行为 | `REGISTER`、`LOGIN` | 用户 ID、设备 ID、渠道和时间 |
| 玩法过程 | 游戏服务端结算 | `GAMESTART`、`GAMEEND`、`BETREWARD` | round、下注、派奖、币种、版本 |
| 充值/提现 | 支付/账务服务端 | `ORDER`、`ASSET`、`WITHDRAW` | 订单状态、回调、冲正和到账时间 |
| 奖励/任务 | 奖励服务端 | `GETITEM`、`USEITEM`、`FINISHTASK`、`RECEIVETASK` | 奖励来源、资产类型、批次和过期时间 |
| 投放/素材 | 归因平台 + Ares | URL 参数、素材/活动配置 | material、campaign、渠道和归因窗口 |
| 生命周期运营 | 运营后台 + 用户行为事实 | 场景、策略、触达、转化 | 快照、策略版本、触达批次和实验组 |
| 财务 | BQ 财务事实层 | 流水/财务宽表 | 真实收付款时间 vs 业务发生时间 |

### 6.2 需要补齐的公共字段

```text
user_id / uuid
event_id / event_version
server_time / client_time / timezone
app_version / h5_version / package_name
channel / sub_channel / campaign_id / material_id
session_id / round_id / order_id
asset_type / currency / amount / status
strategy_id / segment_snapshot_id / model_batch_id / touch_batch_id
request_id / trace_id / error_code
```

### 6.3 建议的核心看板

1. 生命周期漏斗：注册、首局、首充、复充、D1/D7 留存，按包、渠道、素材、版本和场景切分。
2. 场景运营看板：人群规模、触达率、领取率、下注率、充值率、增量收入、奖励成本和投诉/提现风险。
3. 投放素材看板：消耗、点击、注册、首充、LTV、素材/脚本/标签、流量分配和 Ares 落地页转化。
4. 资金与财务看板：充值/提现成功率、回调延迟、流水口径、财务口径、余额、冲正、渠道对账差异。
5. 玩法与 RTP 看板：有效局数、下注额、派奖额、实测 RTP、理论 RTP、异常局、版本和供应商。
6. 运营后台效率看板：配置耗时、任务处理耗时、通知发送成功率、奖励到账率、人工介入率。

## 7. 优先级与验收建议

### P0

- 用户分层 1.0/1.1 建立最小闭环：场景快照、策略版本、奖励批次、通知批次、触达结果和转化回收必须可查询。
- 统一资金和玩法事实：客户端订单/奖励事件与服务端订单、账务、`GAMEEND`/结算数据对账；明确 Chip、BonusChip、真实支付和赠送资产的口径。
- 投放归因字段治理：素材 ID、campaign、渠道、落地页、包版本和归因平台字段必须贯通，禁止把具体密钥/令牌写入配置仓库或分析产物。
- H5 首局漏斗补齐：加载成功、注册、进入玩法、`GAMESTART`、`GAMEEND`、首充和次日回访必须有可分层的失败原因。

### P1

- 建立 2.19 预测人群的离线批次和实验框架，至少支持模型版本、样本时间窗、预测结果、入组规则和对照组。
- 将财务流水口径与财务口径分别建模，提供对账差异、来源、清洗规则和人工修订记录。
- 把 H5 留存调研队列转成固定 SQL/看板：未开局、首局后流失、充值后流失、广告快速离开、快捷方式用户。
- 将 Ares 流量分配的主/次链接、流量比例、人数和次数纳入可回放的实验记录。
- 建立版本验收矩阵：需求、开发、发布、事件、数据、业务结果六个状态分开维护。

### P2

- 接入 Google Play 评论、客服、外呼、活动和代理数据，构建用户声音与经营结果的关联分析。
- 将用户等级、邀请、概率活动和代理权益统一为权益/奖励账本，减少每个活动单独定义资产和流水。
- 对运营后台配置建立权限、变更记录、回滚和灰度能力，支持高风险奖励、提现和封禁操作审计。

## 8. 验收指标建议
