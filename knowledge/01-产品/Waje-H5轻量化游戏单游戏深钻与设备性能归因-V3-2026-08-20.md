# Waje H5 轻量化游戏单游戏深钻与设备性能归因 V3

## Executive Summary

当前 V2 报告只能说明“上线阶段内，H5/PWA 各渠道的新用户留存与付费指标发生了什么变化”。它不能回答：**哪一款轻量化游戏改变了哪些用户行为、改变是否来自游戏本身或性能改善、以及改变是否最终提升价值。**

原因是现有主数据只有“注册日期 × 渠道/端”的日汇总，缺少 `game_id`、入口、加载、首局、设备、网络、真实版本及配置版本。V3 将报告从“渠道阶段对比”收缩为三个游戏的行为归因深钻；在新事实数据接入前，任何单游戏效果仅能标记为 `blocked`，不能输出因果结论。

## 1. 分析对象与正确比较

| 游戏 | 上线/变更事实 | 不能忽略的干扰项 | V3 比较窗口 |
|---|---|---|---|
| Limbo 9008 | 7月14日上线；7月15日下线；7月16日恢复 | 上线后存在中断，不可把 7月14–16 视为稳定上线期 | 稳定恢复后 7/17 起；与上线前同星期基线比较 |
| Keno | 7月23日上线 | 同日 H5 2.1.14、KYC 人脸识别及 APP 2.16.0 上线 | 仅比较实际进入 Keno 的用户与可比未进入用户；不能用全站阶段均值归因 |
| Color Dice 9003 | 7月29日上线 | 7月26–28 存在风控配置调整；随后页面/运营变更持续发生 | 以实际入口曝光、点击和首局为起点，做同端同渠道的事件时间分析 |

每个游戏必须以实际 `game_id`、上架/下架时间、资源版本、入口位和配置版本作为分析主键；“轻量化游戏”不能只作为一个总标签。

## 2. 每款游戏的深钻漏斗

```text
合格会话
  → 大厅/入口曝光
  → 游戏卡点击
  → GAME_LOAD 开始
  → GAME_READY
  → BET_READY
  → 首局创建
  → 有效下注
  → 首局结算
  → 当日复玩 / D1 / D7 / 付费结果
```

### 每游戏必出指标

| 层级 | 指标 | 口径 |
|---|---|---|
| 覆盖 | 入口曝光用户、点击率、入口位份额 | 仅合格可见曝光；按 `entry_context_id` 去重 |
| 可玩 | 点击后加载成功率、`GAME_READY` 率、`BET_READY` 率、P75/P90 准备耗时 | 点击用户为分母；服务端和客户端时间戳对齐 |
| 行为 | 首局率、有效下注率、首局结算率、每用户局数、复玩率 | 有效局和结算以服务端事实认证 |
| 价值 | 首充率、复充率、D1/D7 留存、D7 价值字段 | 仅成熟 cohort；来源价值字段不替代订单收入 |
| 护栏 | 崩溃/JS 错误、黑屏、超时、重复请求、异常 RTP/结算 | 与同端同版本非轻量化游戏对照 |

## 3. 归因方法：先拆“是否进入”，再拆“进入后体验”

### 3.1 比较组

每款游戏固定三组，所有组在同一注册/活跃日期、端、渠道、版本和设备层级内比较：

1. **曝光未点击组**：验证入口与游戏吸引力。
2. **点击但未可玩组**：定位加载、性能、权限或网络阻断。
3. **可玩并完成有效局组**：观察游戏玩法、首局体验、复玩和价值结果。

如未做随机实验，结论只能写为“关联变化”；不写“游戏导致留存提升”。对照组优先为同一端、渠道、版本下未进入目标游戏但进入其他同类轻量化游戏的用户。

### 3.2 事件时间窗口

- **上线前基线：** 每游戏稳定上线前 14 天，按星期对齐。
- **上线后短期：** 上线后第 1、3、7 天，剔除下架、维护、投放封禁和重大版本故障时段。
- **行为归因：** 点击后 30 分钟内、同一用户、同一游戏、同一会话/入口上下文优先直接关联。
- **留存归因：** 只使用成熟 D1/D7 cohort；当期未成熟统一显示 `N/A`。

## 4. 设备与性能合并分析

报告不再把设备性能放在附录，而是作为“点击后未可玩”的解释主线。

| 维度 | 必须字段 | 对应问题 |
|---|---|---|
| 运行形态 | H5/PWA/APP WebView、APP/H5 版本、发布版本 | 哪个端/版本回归 |
| 设备 | 品牌、型号、OS、内存/设备档位、浏览器/WebView | 是否集中于低端设备 |
| 网络 | 网络类型、RTT、下行、运营商、切换/断网 | 是否由弱网导致加载或下注失败 |
| 页面与游戏性能 | 页面 ready、资源大小、`GAME_READY`、`BET_READY`、Long Task | 用户在哪个性能阶段流失 |
| 稳定性 | JS 错误、白/黑屏、资源错误、重载、SDK/请求错误 | 是否为技术故障而非玩法偏好 |

每款轻量化游戏都要输出“性能健康组 vs 性能异常组”的点击后可玩率、首局率、复玩率和付费率；未做实验时仅描述相关性。

## 5. 数据接入：当前状态与 P0

### 当前可用证据

- 渠道/端级新增、D1/D3/D7、来源付费率和 C-T 字段。
- 上线事件时间线：Limbo、Keno、Color Dice 的日期与部分干扰项。

### 当前缺口

- 无 `game_id`、游戏入口曝光/点击、加载、可玩、首局、有效下注、结算事实。
- 无设备、网络、页面/游戏性能、错误及恢复字段。
- 无真实 H5/APP 版本、发布版本、配置版本和入口位。
- 无法把单游戏行为与留存、付费、设备性能可靠关联。

### P0 数据接入与验收

| P0 项 | 最小事件/事实 | 验收标准 |
|---|---|---|
| 游戏发布台账 | `game_id`、供应商、上架/下架、资源/配置/入口版本 | 任一游戏的上线范围与稳定窗口可确定 |
| 入口与行为 | 曝光、点击、`entry_context_id`、加载、`GAME_READY`、`BET_READY` | 点击→可玩链路关联率 ≥98% |
| 服务端游戏事实 | 首局、有效下注、结算、退款/冲正 | 有效局/结算与客户端入口可关联 |
| 设备性能 | `surface_type`、端/发布版本、设备/网络、性能和错误 | 可按游戏、端、版本、设备、网络下钻 |
| 数据质量 | `event_uid`、`session_id`、`trace_id`、入库时间 | 必填字段完整率、重复率、延迟可监控 |

设备与性能数据接入应与轻量化游戏专项并列为 P0：没有该数据，无法区分“用户不喜欢游戏”和“用户根本没能玩起来”。

## 6. V3 报告结构

1. **结论摘要：** 仅回答单游戏是否出现可验证行为变化；没有证据时明确 blocked。
2. **游戏发布与分析范围：** 每个 `game_id`、上线时间、版本、入口位、剔除事件。
3. **单游戏行为漏斗：** 曝光→点击→加载→可玩→首局→结算。
4. **单游戏性能归因：** 设备/网络/版本/错误与可玩、首局、复玩的关系。
5. **单游戏留存与价值：** 成熟 cohort 的复玩、D1/D7、首充/复充；不以来源 C-T 替代订单价值。
6. **数据质量与待补证据：** 缺失字段、关联率、异常日期、不能做因果结论的原因。

渠道只是每张单游戏表的切分维度，不再作为报告主体。

## 7. 当前报告的使用边界

现有 V2 仍可保留为“渠道/端阶段观察”资料：H5 自然和 Google 的留存变化、Facebook 投放质量及 PWA 差异可用于发现异常方向。但不能作为轻量化游戏、性能优化或单一发布的因果评估。

在 P0 游戏行为和设备性能事实接入前，V3 不输出“Limbo/Keno/Color Dice 提升或降低留存/付费”的结论。
